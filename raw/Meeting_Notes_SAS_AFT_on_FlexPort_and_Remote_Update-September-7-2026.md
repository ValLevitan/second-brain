# Meeting Summary — SAS on Flex-Port — engineers alignment
**Date:** September 7, 2026, 10:02–10:33 AM Eastern
**Duration:** ~31 minutes
**Attendees:** Val Levitan (organiser), Pavel Frolov, Evgeniy Alekseev, Dzmitry Chudzinau, Andrei Klimovich
**Raw transcript:** [[Meeting_Transcript_SAS_AFT_on_FlexPort_and_Remote_Update-September-7-2026]]

## Summary

Val's opening line set the purpose: connect the Flex-Port through the SAS protocol and get away from all the acrobatics of connecting through counters and bill acceptors. He was blunt about the consequence — the Flex-Port project goes with SAS, JVL drops the flexible connection, and JVL will not address the part of the market that today sits on old machines.

Evgeniy asked whether SAS goes into the current Flex-Port software or becomes a separate project. Val said the current one. Pavel added that no new menu is needed; the user flow and screens change slightly but stay roughly as they are. Evgeniy then pressed on what that means in practice — the machine can have three interfaces, and they must all be supported by one firmware. Val said he could not answer that. Pavel supplied the shape: keep everything in one piece of software and configure the Flex-Port for how it should work. If it is told to work over SAS, the EBDS and identifier-related code simply is not loaded; counters are either not counted at all, or counted only for statistics and never as an element of paying money out. Evgeniy confirmed that was what he meant.

Dzmitry raised the protocol question for Georgia and Pavel confirmed it: AFT, not the TITO mode that the test firmware supported. Those are different commands, and AFT transactions now have to be implemented. Dzmitry then asked for the PIN to be made optional, which Pavel turned into the requirement — optionally request a PIN, and where a location is configured to run without one, all its tickets are accepted automatically. Andrei Klimovich added the matching change on the funds side: loading money from the wallet to the machine also has to be configurable, because today there is a partial load where the player picks an amount. Pavel described both paths — either show the screen offering $50, $20 or everything, or, where the location is set to credit everything, skip that screen entirely and credit it all, and the same in reverse. Andrei confirmed that was exactly it. When Andrei asked what actually changes in player behaviour because of SAS, Pavel's answer was the PIN.

Evgeniy asked for this to be written down somewhere. Pavel said the meeting is what produces it — they voice the changes here, and afterwards the tasks or a document describing them can be generated automatically. Evgeniy then asked Dzmitry to produce an AFT command document like the TITO/SAS one he had made before, which Dzmitry remembered and did not object to. Dzmitry suggested letting Claude take it on across both projects at once.

Pavel reported the experiment he ran on Friday: he took the SAS firmware the two Evgenys had built and tried adding AFT to it. He thinks that should be finished — run test credits and cashouts over AFT — because once that works the minimal command set becomes clear and can be documented. He then said he would probably take the larger part of the SAS implementation himself, since Evgeniy can only work on it at weekends. Evgeniy confirmed he is on vacation this week and also has the Wi-Fi work. Pavel's view was that Wi-Fi is the better use of Evgeniy's time and the higher priority — the layout, working out the QR-code protocol, decrypting it, applying the settings and connecting to the network — while SAS can be parallelised locally because they have several machines and several ports.

Val moved to process. He wants capabilities, requirements and features, referring back to what he raised at the previous meeting. Andrei Klimovich said the capabilities coming from him would be the ones tied to user experience, particularly the PIN and whether it is present. Val corrected the terminology — those are use cases — and laid out the chain: add the use cases, attach capabilities and requirements to them, and at that point Andrei's function ends. Pavel then takes those capabilities and breaks them into features. A feature branch is opened, and when a commit is made the code goes in and with the code go the prose and the data contracts. Pavel accepted, and noted he will have to reverse-engineer prose onto the Flex-Port code that already exists, working with what Vladimir is building — the skills and plugin for generating prose — producing retroactively a list of the capabilities that relate to Flex-Port plus the changes needed now and the new ones to be built. Pavel also thought they can probably stay within the existing protocols and WebSocket commands on the Flex-Pay and Flex-IQ side, except where Wi-Fi settings need to be compared or passed, which needs thought.

Val's priority statement was about robustness rather than features. He listed what concerns him: handshakes, heartbeat, hard-bad states, and anything that has hung, frozen, jammed, failed to connect or failed to be detected. He would rather add less functionality but have all the error-recovery and service items in front. Evgeniy thought it was all implemented; Dzmitry corrected him — implemented, but not verified. Evgeniy was confident the heartbeat is definitely implemented and put error handling at maybe 80%. The group agreed it has to be verified and completed.

Val checked the memory reduction against his need to change firmware on the fly. Evgeniy said that functionality stays: programs and graphics currently take about 10 MB, and he is leaving 16 MB — two blocks of 16 rather than the current two of 64 — so roughly 60% used, with no plans to add much graphics. Val agreed it was reasonable. Evgeniy volunteered the reason for the cut, which is price: the chip currently designed in was last quoted to him at $148, which he found astonishing. He attributed the memory price spike to the AI hyperscalers rather than to any one person; Val made a joke about Musk and then explicitly noted for the transcript that it was a joke.

Val then asked whether firmware can be updated on the fly on ports, on Flex-IQ and on Flex-Pay. Pavel said Dima is finishing that system, and Dzmitry said for Flex-IQ he thinks they will manage by release time. Andrei Klimovich asked twice which release was meant and got no real answer — "some release" — so this remains vague. Pavel said Flex-Pay will be essentially the same but needs work.

That exposed the real gap. Remote firmware update is not implemented on the Flex-Port at all. Pavel was clear: the protocol was designed, Dima made some version of it, but nothing has been implemented on the Flex-Port side and nobody has tested it. Evgeniy said he had tested a remote update about a year ago, against a simulator he wrote himself rather than over USB. Pavel then said the task sits with Evgeniy Yavorsky and he has not started it. Val's response was to take it off him — he said plainly that he does not want tasks sitting with Yavorsky because he finds it very hard to work with him. Evgeniy Alekseev volunteered to implement the remote update after the Wi-Fi work, and believes the internals are already there — receiving data, writing it, restarting — with something possibly incomplete on the WebSocket session side.

Pavel proposed the verification approach: build the positive path first, then think through what can cause failures — connection or internet dropping, a reboot happening mid-transaction — and work those cases through actively with Claude, since those are what lead to error states. Andrei Klimovich added the screen itself, since a touchscreen can stop responding. Evgeniy noted there is an existing table of errors the Flex-Port emits and part of it is handled today, but new ones may appear and Claude may surface more options. Everyone converged on remote software update being mandatory: in real conditions they will certainly find things and will need to fix errors on working devices remotely. Evgeniy remarked it had seemed a priority a year ago; Andrei Klimovich's reply was that it is a priority now too, everything is constant.

On the virtual test system, Evgeniy pressed his standing request again — with a program on a computer instead of physical hardware, checking something like the remote update would be far faster. Val said they had agreed Pavel would finish that within a week or two. Evgeniy offered a smaller version: Dzmitry could build a bare tool exercising just the remote update without needing Flex-Pay, even a command-line interface rather than a GUI. Pavel proposed going further — a virtual machine fully emulating the ARM processor with the same build used on the machines, plus simulation of some devices whose state could be set by command — and falling back to simpler options only if that fails, since the simpler options do not cover the full functionality. Dzmitry thought running it in Docker or in a daemon mode with simulated data would be easier. Pavel agreed to try the full emulation route first, and Evgeniy asked for some buttons or a graphical interface to send and receive.

Andrei Klimovich closed with Flex-IQ business. On the IQ build that activates cards by barcode, promised for Monday, Dzmitry said it is ready and he uploaded it that day. Andrei asked for the link so he could install it; Dzmitry said he had checked it on his own terminal and it works, but staging is preferable because the data there is more truthful, and someone would send the link. They confirmed the transaction had gone through Dwolla and money was withdrawn, but Andrei cannot see on the bank side whether the money arrived and thought Nathan would need to. Andrei then asked whether the UI and screen changes he had specified the previous week are in this build or come separately; Dzmitry thought probably not on the screens, since Sergei may not have finished. Andrei explained why he was pressing: JVL has to send InComm video and screenshots of the full flow so InComm approves the device. Pavel said he would find out what remains for Sergei and thinks he should finish it that day. Andrei also asked about receipt printing after card activation.

Dzmitry then asked whether the whole flow still makes sense if JVL is moving away from MudaGoose, which prompted Andrei to ask Val whether they still want to install at some locations on MudaGoose at least for now. Val said he does not think so, and asked Andrei to think about it for a day or two and discuss it, since Val would be on site the following day — and asked to be reminded, since he forgets. Left open. Pavel asked for the meeting transcript and Val said he would send the transcripts of all of the day's meetings.

## Decisions Made

- **Flex-Port moves to SAS** — JVL drops the flexible bill-acceptor and counter connection and will not address the part of the market still on old machines. (Val Levitan)
- **SAS goes into the current Flex-Port software, not a separate project.** (Val Levitan)
- **One firmware supports all three interfaces, selected by configuration** — a SAS-configured unit does not load the EBDS and identifier code, and counters are used for statistics only, never as an element of paying money out. (Pavel Frolov; Evgeniy Alekseev confirmed this was his intent)
- **Georgia runs over AFT, not TITO** — a different command set from the test firmware, and AFT transactions have to be implemented. (Dzmitry Chudzinau, Pavel Frolov)
- **PIN entry becomes optional per location**; where a location is set to run without a PIN, its tickets are accepted automatically. (Dzmitry Chudzinau proposed, Pavel Frolov specified)
- **Loading funds from wallet to machine becomes configurable** — either show the partial-load amount screen, or credit everything and skip the screen. (Andrei Klimovich, Pavel Frolov)
- **Error recovery, handshaking and error detection are MVP and come ahead of extra functionality** — Val would rather have less function and all the service items first. (Val Levitan)
- **Flex-Port memory is cut from two 64 MB blocks to two 16 MB blocks**, keeping on-the-fly firmware change; about 10 MB is used today, driven by the chip now quoting $148. (Evgeniy Alekseev; Val Levitan agreed it is reasonable)
- **Remote software update is mandatory for Flex-Port** — in real conditions errors will have to be fixed remotely on working devices. (Pavel Frolov, Evgeniy Alekseev, Andrei Klimovich; agreed by all)
- **Evgeniy Yavorsky is taken off the remote-update task** — Val does not want tasks sitting with him. Evgeniy Alekseev takes it after the Wi-Fi work. (Val Levitan)
- **Evgeniy Alekseev does Wi-Fi first; Pavel Frolov takes the larger part of the SAS/AFT implementation** — SAS can be parallelised locally across several machines and ports. (Pavel Frolov)
- **Process chain confirmed** — Andrei writes use cases and attaches capabilities and requirements; Pavel breaks capabilities into features; a feature branch is opened; commits carry code plus prose and data contracts. (Val Levitan; Pavel Frolov accepted)
- **Verification approach: build the positive path first, then work the failure cases through with Claude** — connection loss, mid-transaction reboot, unresponsive touchscreen — against the existing Flex-Port error table. (Pavel Frolov, with Andrei Klimovich and Evgeniy Alekseev)
- **Virtual test system: attempt full ARM emulation with the production build plus simulated devices first**, falling back to simpler options only if it fails. (Pavel Frolov; Dzmitry Chudzinau's Docker or daemon-mode option is the fallback)
