## Summary

A working session to lock a shared picture of how the transactional platform gets tested across CI/CD, and where AI fits. Andrei, Pavel and Irina aligned in a morning call first; Andrei turned it into a one-page diagram and presented it.

**The testing model (Andrei's diagram).** Read left to right, from code entering its branch to the artifact reaching production. Three big categories — unit, integration (contract tests are a special case), and end-to-end — plus code security.

- **Stage 1 — push to branch (service's own repo):** unit tests + static checks. Fast.
- **Stage 2 — PR to main (same repo):** full unit set + contract tests (the contract is generated from the code, so a breaking change shows up early) + code-security scan (GitHub built-ins, CodeQL/Dependabot). Claude code review runs here too.
- **Stage 3 — integration in a temporary CI environment:** several live services together (e.g. payment + billing), a full build as a dry run before staging, DB migrations (a new schema must not break the running app), resilience (e.g. billing connecting to Dwolla), building the flex-IQ device `.so`, equipment simulation. This is the CI/CD boundary.
- **Stage 4 — deploy to staging (a full copy of prod, real QA terminals):** image vulnerability scan (open question), full integration + e2e, and the cloud↔terminal junction on real hardware. A successful run writes an entry into the platform manifest — a fixed, tested combination of versions = a release.
- **Load testing:** optional, on demand, rare. Then deploy to prod.

**Continuous Delivery, not Deployment.** Andrei stressed the Action can deploy on its own, but a human decides what to deploy and when — not auto-ship on every passing change.

**AI and automation.** Pavel's main point: today components are built separately and only return to the integration repo when finished, which serializes the work and slows everyone. They want tests written in parallel. Idea: when a capability/requirement is committed to the integration repo, AI — which knows the linked repos — creates dependencies, triggers the relevant repos, and generates mocks/stub APIs so a test can be built before the real components exist. Irina noted a capability is just a short, high-level sentence; good requirements must sit under it.

**Val's framing of the loop.** Product writes capabilities → requirements → acceptance criteria, with AI help. If the e2e tests build on those same acceptance criteria and a requirement was missed, the test surfaces it. Val's rule: *"we don't generate bugs, we fix the tests"* — when a test fails, go back and fix the requirement / acceptance criteria, not patch around it. The earlier the mismatch is caught, the better.

**Where things stand.** Some unit tests exist. Contracts were generated by hand, but not yet by the artifact-building Action — still to finish. Code security and Claude code review are in place. Integration tests partly exist and need review; some (DB migration, Dwolla connection) only the developers can write. E2E exists only as manual tests — no automated e2e yet.

Val praised Andrei's one-page presentation strongly and asked Irina and Pavel to present the same way.

## Decisions Made

- **Adopt Andrei's CI/CD testing model** (unit / contract / integration / e2e across the four pipeline stages). *(Endorsed by Val)*
- **Treat the pipeline as Continuous Delivery** — a human decides what and when to deploy. *(Andrei; endorsed by Val)*
- **Start automated e2e now**, against the transactional product (currently in Alpha), from the team's tomorrow morning. *(Val)*
- **Aleksey Khamin (Lesha) writes the automated e2e tests, AI-driven — nothing by hand.** *(Val)*
- **Andrei Bosik pairs with Lesha to supply the requirements and acceptance criteria** the tests build against. *(Val)*
- **E2E tests run in GitHub Actions, never on tester machines.** Val was emphatic; Andrei agreed.
- **Image vulnerability scanning at staging is deferred** — not a blocker for now. *(Val, Pavel)*
- **Next meeting: Friday, June 5, 8:00 AM Eastern**, adding Lesha to the four current participants. *(Val, Irina)*
