# Meeting Summary — Clayton / Lena / Val — IP MCP Model Regression
**Date:** April 28, 2026, 1:58 PM Eastern

**Attendees:** Clayton Chancey (Cowork/Anthropic), Lena Zhukova (JVL), Val Levitan (joined ~23:30)

## Summary

This was a working session focused on diagnosing and resolving a model-driven regression in the **IP MCP** server that Clayton has been building for Lena's JIRA ticket-creation workflow. Context: at the previous session (~2 weeks prior), the tool had performed badly — it failed to upload images correctly and created duplicate JIRA issues. That same day, Anthropic released **Opus 4.7** as the new default model in Claude Cowork. Clayton committed to figuring out the failure offline. He spent the intervening period running benchmarks in partnership with Anthropic across multiple of his projects (including a parallel project for a university economics department) and concluded that Opus 4.7 is materially worse than 4.6 at this specific class of task. The session was the first re-test after that finding.

Clayton's diagnosis, which he repeated for Val mid-call: the failure mode is around **multi-needle retrieval / multi-needle threading** — tasks where the model must extract many specific data points from a long, dense input (in this case, a meeting transcript that doubles as the prompt) and act on them precisely. Opus 4.7, per Anthropic's own comparisons, performs significantly worse than 4.6 in that regime. Clayton's reading is that 4.7 follows instructions more literally and handles ambiguity worse, which suits programming work but degrades knowledge-worker flows where the model has to interpret intent. He noted Aaron Bockelie has reported no problems with 4.7 — but Aaron is doing different (coding) work. He also speculated that Anthropic's defaulting of users onto 4.7 was partly compute-cost driven.

The team's first end-to-end test of the day was run inside Cowork against a previous game-dev transcript (no new game-dev meeting had been recorded since last time). Lena was instructed to switch the model selector to **Opus 4.6** explicitly. The behavioural difference was visible immediately: 4.6 picked up the asset-loading tool that 4.7 had been ignoring, walked through the tool-embedded instructions properly, and began creating test JIRA tickets. Clayton observed that he believes 4.7 was essentially executing only the user prompt and disregarding the auxiliary instructions baked into each MCP tool, while 4.6 picks them up — which is the steered behaviour his tool design assumes.

The test surfaced one real bug, unrelated to the model: image attachments were returning **404 errors**, and the tickets that were claimed to have attachments were not visible on the production JIRA instance. After tracing it, Clayton identified the root cause — **the MCP server's create endpoints and its read/attach endpoints were targeting different JIRA instances** (sandbox vs production). The tool was creating tickets in sandbox but the read/search/attach calls were going against production, so freshly-created tickets couldn't be located or attached to afterwards. Lena confirmed by checking the sandbox UI that the child work item with the attached image did exist there. Clayton then live-prompted his Claude Code session to fix this by routing all create/read/attach endpoints to the same configurable JIRA instance.

While Clayton's Claude Code session was running the fix and rebuilding the Windows binary, Val joined. Clayton summarised the situation for Val. Val challenged the architecture from two angles: (1) is the complexity here driven specifically by Lena being on Windows? and (2) could the multi-needle threading task be decomposed into smaller deterministic sub-operations? Clayton answered no on both. Cowork now properly supports mounted Windows drives — that gap, which existed three weeks ago, has been closed by Anthropic and JVL's own work — so Windows is no longer the differentiator. On decomposition: Clayton argued that breaking the workflow into discrete deterministic steps would require building an orchestration engine that approaches the complexity of an LLM itself, because each sub-decision is dependent on the success/failure of others, and the team's editorial decisions about ticket structure / image choices / naming conventions vary per game and per discussion — there are no stable rules to extract. The high-context inference path through 4.6 is, in his view, the more durable approach precisely because it tolerates editorial drift in the source material. Val asked how reliably 4.6 works now. Clayton's answer: "always worked pretty high for us" — the only blocker had been image upload, which today's session crossed. Val asked Clayton to circulate the recording at the end of the meeting and dropped off.

After Val left, the fixed build was committed to the JVL GitHub, pulled down on Lena's machine, and re-tested. The re-test prompt asked for at least **10 JIRA tickets** based on Twin Bison features, each with the relevant comp-art image. The tool produced **11 tickets**, each with image attachments, and Lena spot-checked them visually — the feature list and image attachments were accurate. Lena said this was the same quality she had previously seen during the Dragon Base structure work using a prior transcript. She noted she did not request user stories under each feature this time; she wants to test that branch herself.

The meeting closed with planning. Lena will spend the rest of the week running her own prompts against the tool — including stories-under-features and cross-checking ticket descriptions — and report back. They will reconvene **Thursday (April 30, 2026)** with the goal of flipping the tool to production. Lena raised two functional gaps she wants closed before propagation: (a) **delete issue** support, and (b) **archive issue** support — for example, archiving all IPs under a market like Georgia or South Dakota when the team is done with that market. Currently she has to context-switch into Aaron's separate MCP add-on for deletes. Clayton confirmed there is no delete-issue tool in the IP MCP today (it can delete a release and remove issues from a release, but not delete an issue), said it is simple to add, and stated his Claude Code instance had already finished writing the delete tool by the end of the call. He committed to also adding archive.

Lena also asked how propagation to her two team leads will work after go-live. Clayton said Andrei will handle the rollout to the team leads (they are also on Windows, so the same provisioning instructions apply), and he will update the IP MCP repository's GitHub documentation to cover installation and configuration so Andrei can do it remotely.

Lena suggested they record one more short team meeting tomorrow (April 29) to re-validate the full transcript-to-GitHub-to-JIRA pipeline end-to-end before production cutover.

## Decisions Made

- **Model pinning:** Lena's IP MCP workflow will run on **Opus 4.6**, not 4.7, because of the latter's degraded performance on multi-needle retrieval tasks. (Decided by Clayton, accepted by Lena and Val.)
- **JIRA instance routing fix:** All IP MCP endpoints (create, read, search, attach) must target the same JIRA instance, configurable per environment. The previous mismatch where create went to sandbox and read/attach went to production is fixed in this session's commit. (Decided and implemented live by Clayton.)
- **Production cutover target:** Aim to flip from sandbox to production at Thursday's (April 30, 2026) meeting, contingent on Lena's interim testing not surfacing blockers. The cutover itself is a one-line URL change in the configuration. (Agreed by Clayton and Lena.)
- **Decomposition rejected:** The multi-needle inference flow will not be broken into deterministic sub-steps. Reasoning: the loss of editorial flexibility and the orchestration cost outweigh the brittleness of model-dependence. (Clayton's position, not contested by Val after discussion.)
- **Tool gap closures:** Add **delete-issue** and **archive-issue** tools to the IP MCP before production cutover. (Lena requested, Clayton committed.)

## Open Questions

Anthropic's deprecation runway is typically long (>=1 year), and OpenAI similarly retires models 2-3 years out, so 4.6 is not at imminent risk, but the underlying question — "how does Lena know when to upgrade in the future" — remains unresolved.
- **User stories under features:** This session's test only generated features with attached images; it did not generate the story hierarchy underneath. Lena will test that branch herself before Thursday.
- **Provisioning to team leads:** Will be handled by Andrei after Clayton publishes the install/configuration documentation to the JVL GitHub repository. No timeline locked beyond "before/after production cutover."
