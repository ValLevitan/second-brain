## Summary

**Meeting purpose (Pavel's framing).** Pavel opened by stating the goal: define the direction of automated-test evolution at JVL over the next 6 to 12 months, and identify concrete experiments anyone in the room could run to validate a hypothesis. He laid out four problems with the status quo:

1. The existing test framework was purpose-built for "Igor Pomni" — what is now becoming the NOVA gaming platform — and does not transfer cleanly to other projects (server-side, payment terminals, recyclers).
2. The QA team is constrained: they do not spend 100% of their time writing new automation, they also have to maintain existing tests, and products keep evolving, so test coverage rots toward uselessness.
3. The framework cannot keep up with the number of parallel products in development.
4. A large portion of test work involves real hardware (button presses, USB insertion, dispensers) and resists automation.

Pavel's proposed direction is to move beyond using AI just to help write test code, and instead use AI as an agent that *performs* the QA's job: a QA or developer would describe a test intent in plain language (e.g., "I want to validate JIRA-X using test plan Y"), and the agent would propose a plan, generate any skills or tools it needs, run the tests, and write a report. The agent should keep a history of test sessions so prior solutions can be reused.

**Alexander's pushback on "universal framework."** Alexander argued that a universal cross-product framework is unrealistic. Each product (NOVA, Flex_Recycler/Flexplex, Posso, etc.) has its own project-specific classes and libraries. Playwright is already a universal underlying protocol — anything truly cross-product would have to live as a library (e.g., a printer-testing library, including a virtual printer implementation) that individual product test suites import. He also drew the line that a virtual printer doesn't actually test the printer — it only tests the interaction with the printer. To find truly common pieces, you have to try writing tests in two projects (e.g., NOVA + one other) and look for what overlaps.

**Val's reframing — anchor to the repo standard v5.1.** Val challenged the framing that Alexander and Pavel were debating two compatible things. He argued they were talking past each other. Val tied the discussion back to the repository structure work Alexander (with Aaron Bockelie) had locked in v5.1 of the JVL repo organization standard: that structure is dynamic, with data contracts that change in each repo as code is added, and that already proved structure-by-design doesn't work statically. The same insight should apply to E2E tests — they cannot have a fixed framework structure either. Val's stronger claim was that the meeting title itself was wrong: this isn't about building a "framework," it's about finding *an approach* to writing and running tests. He further argued that the AI should be given the data contracts, protocols, and code, and figure out tests on its own, rather than being hand-fed instructions. Pavel pushed back that AI will not get it right on the first try, but Val countered that human developers also don't get it right on the first try — the AI just iterates faster.

**Hallucination and reverse-engineering.** Val cited his earlier point that Claude can reverse-engineer code from data contracts. Dzmitry replied he had tried this and the AI invents details that don't exist. Val attributed the hallucinations to incorrect or incomplete data contracts in the current repos (which v5.1 is meant to fix). Pavel corrected Val's mental model: LLMs are probabilistic — they output the highest-probability next token for the context, and that's where "hallucination" comes from. Alexander observed that humans also make errors when given the wrong specification; the AI's advantage is speed and iteration count.

**Test reporting and observability of AI test sessions.** The group converged on the need for AI test sessions to leave a durable record: not just text logs, but screenshots of state transitions ("here the server screen changed from 1 to 2; here a button was pressed"), so a session can be reviewed and replayed. Alexander warned this introduces a meta-problem: who tests the tests? A test written by AI that says "everything is fine" might actually cover nothing meaningful. He proposed embedding metrics or checkpoints so a human can observe mid-flow that the AI is doing real work (e.g., actually making the API call) rather than fabricating data. Pavel pointed to AI-on-AI review (a critic agent, analogous to Claude code review on a PR) as a partial mitigation but conceded full automation of test validation isn't yet possible. Ivan made the practical point that text logs remain essential alongside screenshots. Pavel agreed and added that two parallel agents running the same E2E might take different paths — one might find a bug the other misses, which is itself an interesting non-deterministic property worth exploring.

**Dzmitry's "platform" lens on E2E.** Dzmitry argued the discussion was too narrowly focused on a single subsystem (NOVA + L_G_S). The transactional system, by contrast, has a terminal plus ~10 server components, plus external integrations (Cerberus/Kulak for authorization, Business Central, an SMS service, twilio), plus real hardware. True E2E for that system means: the test platform must be able to (a) stand up server environments per the rules described in the standard, (b) work with terminals connected locally, (c) emulate the hardware where needed, and (d) check system-level signals like whether logs actually reach Grafana from a terminal. This is system interaction across services, not code interaction. Pavel responded that Dzmitry was effectively reciting exactly the kind of system description that would have to be given to (or learned by) the AI agent.

**Val's strategic objection — sequential dev-then-test.** Val pushed back hard on the implicit model of "developer finishes, throws over the wall to QA." He called this an outdated, "imprisoned" mental model that produces a permanent QA bottleneck. With CI/CD, the development-and-validation cycle is continuous; the meaningful question is what "the product is built" actually means when actions fire on every commit across many interdependent repos. Pavel conceded that fully eliminating the gap between "module released" and "module deployable to production" isn't realistic, but reframed the discussion as minimizing that gap. Val pressed: if AI can reverse-engineer the system from data contracts and protocols, and runs much faster than a human QA, why is the human-QA step in the loop at all when a developer (e.g., Alexander integrating a recycler) is the person closest to the hardware and the change? Val's strong position: the developer doing the integration should be using AI for validation in real time as part of development — that work is *development*, not testing, and the QA department exists by historical inertia rather than necessity, especially now.

**The cross-repo CI-trigger problem (origin of the discussion).** Val reminded the room that this whole conversation originated when Andrei Bosik asked how a release is declared "complete" in a CI/CD model. The current model has GitHub actions firing on each commit in each repo. Each action validates one repo. But there is no clear answer to: *what triggers the system-level test that the changes across N repos compose into a coherent platform?* Alexander suggested each completed action signals a "main" component that runs an overall integration test. Dzmitry countered that this is fragile when a single change must land across three repos to be consistent — the first two actions will fail by definition while waiting for the third. Sergey raised the resource-cost concern: spinning up a full transactional environment per pull request is expensive on GitHub runners. Evgeny suggested it could still be feasible with five flex-IQ-style stacks per PR but conceded it would consume significant capacity. No conclusion was reached.

**Agent personalities for negative testing.** Alexey raised the idea of treating the AI agent like an onboarding employee — it needs working memory, and over time it should learn which prompts produce which results. He extended this to multiple agent personas: a "competent player" for happy-path validation, plus aggressive variants ("drunk player," "monkey with grenade") for negative tests that hammer the system with unexpected inputs. Alexander expressed reservation about purely random negative tests; Irina and Evgeny defended pre-described boundary conditions (e.g., "PIN accepts 1–10 digits, reject anything else") as the right shape for negative tests. Ivan asked whether each engineer would train their own agent or whether the team shares one — left unresolved.

**Hardware verification — when is a re-test required?** Val pressed on when hardware re-verification is actually necessary. If a server-side change has no hardware impact, hardware tests aren't required. If a new device (e.g., flex_pay dispenser) is being grafted to existing hardware, that's a one-time bring-up effort, after which a software-only change shouldn't require manual hardware re-verification. Alexander conceded this in principle but warned of cases where seemingly trivial changes (a browser update breaking video on the device) cause real-world breakage that only manifests on actual hardware — so for products that ship as integrated metal devices, some hardware step remains unavoidable. Val argued the developer making the change should run that step themselves, not delegate to QA. Irina noted the well-known drawback of self-review: the author's eyes are not fresh.

**Closing — research assignment.** Evgeny proposed the group is "arguing about nothing" without enough information, and recommended a research phase: spin up multiple specialist AI agents on CI/CD and testing best practices, have them read industry literature, and come back with concrete options. Val endorsed this and added: use the transactional product as the experimental subject because it is in good shape today. Pavel proposed a follow-up meeting on Wednesday (May 27). Val expanded the assignment: every attendee independently does their own research, deliberately *without* coordinating with each other beforehand, so that diverse perspectives surface. Val asked Pavel to schedule the meeting for 6:00 PM Wednesday and to share this transcript.

## Decisions Made

- **No fixed-framework approach.** The group accepted Val's reframing that a single static testing framework is not the goal; the goal is a flexible AI-agent-driven approach grounded in the repo standard v5.1 data contracts. (Endorsed by Val, Pavel, and Alexander; no dissent.) Re-affirms the May 22 Part 2 architectural pivot.
- **Use the transactional product as the experimental base.** Val proposed and the group accepted that the transactional system — which is in good operational shape — will be the testbed for any new approach. (Decided by Val, supported by Evgeny.)
- **Independent research before next meeting.** Each attendee will independently research E2E testing approaches and AI-agent-driven testing without pre-coordinating with each other. Results will be brought to a follow-up meeting Wednesday May 27 at 6:00 PM. (Decided by Val.)
- **Follow-up meeting Wednesday May 27 at 6:00 PM Eastern.** Pavel to schedule. Meeting #2 of the 3-meeting cycle. (Decided by Val and Pavel.)
