# Meeting Summary — Continuous Integration Architecture (Payment Platform)

**Date:** April 17, 2026, 12:10 PM Eastern
**Duration:** ~2h 19m
**Attendees:** Val Levitan, Aaron Bockelie, Andrei Bosik, Alexander Biratko ("Sasha"), Evgeny Kharetski

## Summary

**Meta-repository walkthrough (opening).** Andrei shared screen and introduced a "meta repository" — a container repo that aggregates references to the other product repositories (`contracts`, `deploy`, `documentation`, `tests`). Noted it is a **beta version** prepared in collaboration with Dmitriy Chudzinau (Jima). Andrei stated the meta-repo currently uses *links* to other repositories rather than git submodules, because the team has experienced problems when using submodules. Sasha confirmed he built a command using this structure.

**Submodules debate.** Aaron asked pointedly what problems submodules cause. Sasha surfaced **detached HEAD problems** when attempting to push. Aaron pushed back: detached HEAD is a Git usage issue to fix before blaming submodules. Aaron argued the more fundamental question is whether developers *should* need to clone the entire tree — his position: **no**. A developer working on one service should clone only that repo and rely on Docker images from a registry for everything else, not rebuild the whole universe. The need to clone everything is an **architecture/interdependency problem**, not a tooling one. Aaron: "there is no right answer… it's what works based on the shape of the codebase."

**Clarification — this is not a monorepo.** Aaron recalled that in the previous meeting the team had discussed it as if it were a monorepo being broken up. Andrei corrected: "We found that this is a mistake. We do not have a mother repo." Repos are already independent; each builds a Docker image; the meta/integration repo is principally a **DevOps concern** for full continuous integration, not a developer-experience concern.

**Land-based equipment constraint.** Andrei raised that some repos (e.g., **payment terminal** firmware) cannot be run locally on a developer laptop — only Docker images make sense there. Aaron agreed there is nothing wrong with developers only consuming Docker images for those components.

**Zero Trust model introduction.** Aaron introduced the Zero Trust architectural model (popularized by Google) and spent a large portion of the meeting illustrating it with a diagram generated by Claude and a worked example: Sasha publishes a bar-chart rendering library; Evgeny consumes it; Andrei runs an analytics platform that integrates both. Each party:

- Owns their own concern and their own tests.
- Publishes a **contract** of what their module does (preconditions, post-conditions, invariants).
- **Pins versions** of dependencies rather than tracking latest ("you don't just run latest and hope for the best… we all pin versions — that's crazy otherwise").
- Does not consult peers on every change; communicates **breaking changes** via release notes — Aaron referenced Val's term from years prior, *"courtesy of disclosure."*
- Integration tests in Andrei's repo verify the combinations work; the platform ships a manifest of pinned versions that have been validated.

**Data contract — central disagreement.** The Minsk team (Evgeny and Sasha) had been operating under the assumption that **data contracts are static documents stored centrally in the meta/integration repo**, written first, then implemented. Aaron strongly disagreed on both points:

- **Contracts are not separate documents.** The contract IS the code surface — expressed via `Javadoc` for Java, `Swagger`/`OpenAPI` for REST endpoints, `GraphQL` introspection, `rustdoc` for Rust, etc. Aaron demoed Rust `cargo doc` output from his own Bluetooth headphone library to show what a generated contract looks like in practice.
- **Contracts live with the code, not in a separate repo.** "Why would you divorce the tests from the product itself?" Each service owns its own contract in its own repo. The integration/meta repo VERIFIES contracts; it does not STORE them.
- **Contracts are dynamic, not static.** "If you write it once, then your application will never change." The contract evolves with every feature change. Aaron: "A contract is dynamic and generated from the code as it's written and enforced by code tests."
- **Don't hand-write data contract markdown files.** "A contract is not a literal legal document written in markdown inside of your software. That's stupid."

Val translated this repeatedly into Russian for the Minsk team and confirmed they had been thinking of the data contract as a static `.md` document published once, with explicit versioned additions. Aaron's counter-model: publish the current generated contract as an artifact of every commit, referenced by JIRA/issue IDs inside the Javadoc itself to tie each function to the business capability it fulfills.

**Front-end / back-end ordering.** Sasha asked the concrete question: if the back end gets a new API, how does the front end learn about it? Aaron walked through an explicit time-ordered sequence which he also typed into the Teams chat:

- **Step 0 —** Business (Juan) decides a new capability is wanted.
- **Step 1 —** Back-end adds the new API endpoint and ships it with **unit tests asserting the endpoint's stableness.**
- **Step 2 —** CI/integration group adds **integration tests** for the new endpoint (testable, but incomplete because no front-end exists yet).
- **Step 3 —** Front-end implements the UI consuming the new endpoint.
- **Step 4 —** CI adds **end-to-end integration tests** covering front-end→back-end flow.

Aaron re-emphasized that the front end never trusts the back end — it just asserts the endpoint works at a pinned version. Back-end generally needs to lead because an exposed front-end with no back-end support breaks for users; patterns like "not supported yet" fallbacks add complexity.

**Val's pushback on requirements/capabilities.** When Aaron argued the "right" way is to start with requirements and capabilities, Val cut in sharply: "You just put the entire JVL at a standstill. We won't be able to produce one thing. Small companies don't have the infrastructure to take it from requirements and capabilities." Val asserted the real source of truth is **cash** — "If I cannot make cash, then nothing works. I don't care what theory you put in place." Aaron agreed: since code already exists, the contract already exists — "give me your code for Java and I'll create Javadoc and you'll have your contract." No upfront requirements work is needed; the contract is whatever the current code does, published via generated docs.

**What goes in the integration repository.** Toward the end, Val and Andrei worked through what the integration repo should contain. Andrei's articulation (which Aaron endorsed):

- **Deployment actions** to deploy release artifacts from service repos.
- **Docker Compose** files to run the environment on a developer machine.
- **Integration tests** (Andrei asked whether Helm charts belong here — Aaron confirmed yes).
- **Documentation** of integration behavior.
- **Helm charts** (for Kubernetes — Andrei mentioned K8s).
- **Terraform / infrastructure-as-code** (if infrastructure is defined in CI repo).
- **Monitoring setup.**
- A **page/manifest showing which version of each component is currently deployed** to each environment.

**What does NOT go in the integration repo:** data contracts (those belong in each service repo) and code itself. Val explicitly: "I don't believe there should be an integration repository" — then accepted the model once scoped to deployment/integration/tests only, not contracts or code.

**Claude per repository (emerging pattern).** Val asked how Claude will "develop on its own" as agents become more capable. Evgeny described testing an agent pattern where each repo has its own Claude that loads the context of that repo (CLAUDE.md, memory, etc.), and a developer's Claude can ask another repo's Claude for information (e.g., "what's your API?"). Useful **only if** the per-repo Claude is genuinely an "expert" in its repository — otherwise it's no different from just running Claude against the other repo directly. Sasha confirmed the mechanism works in testing but needs more validation on practical benefit.

## Decisions Made

- **Meta/integration repo uses links to service repos, not git submodules.** Rationale: submodules caused detached-HEAD problems and force downloading code developers don't need (e.g., payment terminal firmware on a cloud developer's machine). Team can switch back to submodules later if needed. (Endorsed by Andrei, Aaron, and the team.)
- **Data contracts are generated from code, stored in each service repo, not centrally.** Rationale: avoids the "divorce tests from product" anti-pattern; contracts stay in sync with code automatically; each service is the authoritative source of its own surface. (Aaron; accepted by Val, Evgeny, Sasha after extended debate.)
- **Integration repo scope is deployment + integration tests + infrastructure, not code or contracts.** Rationale: separation of concerns; integration repo's job is to verify and deploy, not to define. (Andrei articulated, Aaron confirmed, Val accepted.)
- **Implementation order: back-end → CI tests → front-end → E2E tests.** Rationale: back-end typically must exist before front-end can meaningfully integrate; fall-backs for missing back-end add avoidable complexity. (Aaron; typed into Teams chat for reference.)
- **Versions must be pinned, not "latest."** Rationale: Zero Trust model requires verifying known-working combinations; ships manifest of validated versions per release. (Aaron; confirmed by Evgeny and Sasha for their use of Postgres and Pixie pinning respectively.)
- **Team reconvenes Friday (April 24, 2026) after Aaron publishes updated CI architecture document.** Rationale: holiday schedule; Alexander unavailable Thursday; gives Minsk team review time. (Val and team agreed.)
