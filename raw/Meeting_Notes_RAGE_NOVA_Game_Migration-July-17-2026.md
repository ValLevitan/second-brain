## Summary

The meeting was about moving games from the old RAGE studio framework to the new NOVA framework (browser-based, Pixi engine). Val explained why: the design tools graphic designers use today no longer work with the RAGE studio, which was developed about 20 years ago. Development has become awkward, so a move to something new is needed. Pavel clarified that the Galaxy platform switch is not hard-tied to this — Galaxy can come later and in steps; the Kali Ochi game runs fine on the current CMS.

The group walked through what carries over and what doesn't. Sounds move as-is (same audio engine). Videos need reconversion (the old engine used a different alpha-channel format), and browser video playback is unreliable for precisely-timed elements like symbols — so Spine (skeletal) animations are preferred. Frame-by-frame Spine animations can be produced from videos almost automatically, especially if source files exist; skeletal ones need a designer and supervision. Scenes are the main work: the old RAGE scene format differs from Nova's simple JSON format. For Kali Ochi, designers built scenes in Unity and converted them; with AI (Claude), the Unity step could be skipped and scenes generated directly in the Nova format.

Two experiments were proposed: convert a RAGE scene directly to the Nova/Pixi format with AI, and convert a RAGE scene to Unity so designers could still edit it later. The group agreed direct-to-Pixi looks simpler, and Val said to go direct — a repeat edit of the same game is unlikely. Pavel recalled an earlier AI experiment that rendered an old game's scene in a browser with working transitions, which suggests the main game screens should convert without much trouble. The hard parts will be game-specific bonuses and custom logic.

On scope: the zones are Georgia, Nebraska and Texas (treated as one group), plus South Dakota, which needs full re-approval and stays on the old format for now. Counting versions: the latest 8 vertical multi-games for Georgia, 6 different games for Nebraska (Texas uses the same set), plus 7 new GA COAM v3 games — around 20 in total. Val prefers to start with the newest 8. Irina flagged that all existing games are vertical; horizontal layouts are needed, and Nova's flexible layout supports both only if designers define the layout rules per game — parallel designer work.

Val raised capacity: if the team can't absorb the conversion work, subcontractors are an option — he knows two companies in Ukraine, and two or three people could likely be found in Belarus (Alexander agreed people are available there).

Val pushed hard on standardization: today's RAGE games are probably each built differently because every designer did things his own way. Going to Nova, common elements (frame, bet deck, dashboard, wheels, messages) must be described once and be identical across all games — one skeleton. Evgeny said this is achievable if the team defines rules and data contracts, but the specifics of what to standardize still need work. Val closed the first half with the plan: create a Nova standard, build data contracts for one known game by reverse-engineering it, then plug in resources — the game should assemble itself. Val's mid-meeting takeaway: "this is easier than I thought."

The second half of the meeting (minutes 43–96) went deeper on four topics.

**Reuse and Kharetski's earlier demo.** Val asked whether the team is sure resources don't need redoing; Alexander said he is not sure. Val recalled the demo Kharetski showed him — building a game from ready pieces. Kharetski clarified that his demo applied only to new games built on Nova; it never touched transfers from RAGE, and nobody knows how RAGE scenes are built except the people who built them. On the Nova side, though, everything can be brought to common modules (bet deck, dashboard) with selectable arrangements, and Irina noted the current 7–8 games already share an identical bet deck and dashboard, differing mainly in progressive meters and logos per product. Evgeny's conclusion: separate the elements into modules and assemble games like a constructor — the bet deck module first has to be pulled out of Kali Ochi, where it is currently hard-wired.

**How to describe scenes.** A long debate on writing the standard. Evgeny proposed fixed arrangement variants per module ("variant A / variant B"). Val objected to templates: he wants everything described in words as capability requirements — describe one button thoroughly once, then say "the bet deck has six buttons." Pavel bridged the two: describe each variant once in full detail, then reference it. Then came the pixel question: who writes the coordinates? Alexander argued that AI does not see visual balance — you end up nudging elements back and forth — and that a person placing elements by hand is the practical ideal; Nova already uses relative coordinates, so layouts adjust themselves when the number of buttons changes. Evgeny suggested a middle path: let a person lay the scene out visually, then run a script or Claude to parse the layout into coordinates and generate the requirements automatically. Val's takeaway: place things visually first, then interpret the visual result into math and code; use AI wisely, up to a point.

**Resources: what can be reused and who converts them.** The group pinned the term down: static drawn images and fonts can be reused as-is; video must be reconverted (different alpha-channel format); transitions in Nova are Spine animations played over a screenshot — the principle is identical across games, but each game wants its own transition animation, so each must still be made; complex symbols (wilds, logos with effects, overlays) need separate individual work and probably redrawing. Pavel framed the real question as: what percentage of resources can be reused unchanged? Val called confirming resource reuse one of the main goals of the experiment. Irina asked whether conversion needs a developer or a designer; Alexander said nobody knows yet — the hope is that with AI practically anyone could do it, perhaps via AI-written conversion scripts. Pavel suggested packaging the process as an agent: one developer walks through all the steps once and writes the instructions, then the agent repeats them; Alexander cautioned that a human must still eyeball agent output ("the agent can be capricious"); Pavel countered that the agent can also act as the eyes — run the old game and the new scene side by side and validate at least the static objects itself.

**Task framing and assignments.** Kharetski summed up: run the planned experiments to see how much AI helps the transfer, then plan something serious from the results. Val reframed it: don't put the emphasis on AI. The task is to determine what it takes to move the games — split what can be taken and copied over from what must be made anew; automation is welcome but is step two. Pavel agreed — AI won't flag things like the Spine issues Alexander raised. Val put the scope in round terms at 21–25 games. On staffing: Alexander had a related task planned for July 20, but Pavel noted Alexander's current priority work means he won't get to migration before his August vacation. Two tasks were split out. The ARM-platform performance check — run Kali Ochi on the RK3568 or the new RK3588 board (which arrived the day of the meeting) and find the platform's limits — goes to Daniil, the new student developer, who is already fixing bugs on that game. The RAGE-to-Nova scene-conversion study goes to Igor Metelsky ("the best candidate after Sasha," per Pavel), starting Monday, with Evgeny and Alexander sitting nearby for questions; Val timeboxed it at one week, no more. Pavel will have both tasks in the schedule by Monday. Evgeny keeps his current queue (white label, standalone, dropping the progressive library, the data-center move). Alexander will still talk to Dima Khanda. Side note: Nova needs more testing on real hardware — it has seen little of it and bugs are being fixed now.

## Decisions Made

- **Convert RAGE scenes directly to the Nova/Pixi format, skipping the Unity intermediate step** — simpler, and re-editing the same game later is unlikely. (Decided by Val, supported by Pavel and Alexander)
- **Standardize common game elements into one identical skeleton for all games on Nova** — current per-designer variation is unacceptable. (Decided by Val)
- **Start migration with the newest 8 Georgia games; Georgia, Nebraska and Texas are treated as one group (~20 games counting all versions)** — Val prefers the 8 first. (Decided by Val with Irina's counts)
- **Leave South Dakota on the old format for now** — it requires full re-approval; migrate only after the new format is settled. (Decided by Val)
- **Galaxy platform transition proceeds separately and stepwise; it is not a precondition for Nova game releases.** (Clarified by Pavel, accepted by Val)
- **Build transitions as Spine (skeletal) animations over screenshots, not as video; keep video only where exact timing doesn't matter (e.g., backgrounds, very short clips).** Nova already works this way. (Val, confirmed by Alexander, ~00:49–00:51)
- **Scene layout workflow: a person places elements visually first; the visual result is then parsed into relative coordinates and written requirements — possibly by a script or Claude.** AI alone doesn't judge visual balance; Nova's relative coordinates make layouts adapt automatically. (Val's conclusion on Evgeny's idea, ~01:14–01:16)
- **Frame the migration task as "establish what can be copied over vs what must be rebuilt"; AI and automation are step two, not the focus.** (Val, ~01:27; Pavel agreed)
- **Assign the RAGE→Nova scene-conversion experiment to Igor Metelsky instead of Alexander — starting Monday July 20, timeboxed to one week.** Alexander is on priority tasks until his August vacation; giving it to the new student Daniil was rejected; splitting it between Igor and Anton was rejected. (Val and Pavel, ~01:29–01:36)
