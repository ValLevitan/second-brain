# Hardware follows the developer repo model; no monorepo (Oct 5 2026)

Set out by [[wiki/people/val-levitan.md|Val Levitan]] twice on Oct 5 2026: first to [[wiki/people/genadi-peari.md|Genadi Peari]] at the [[wiki/meetings/2026-10-05-design-to-msbc-zero-trust-repos-and-data-contracts.md|1:19 PM meeting]] [[raw/Meeting_Transcript_Design_to_MSBC_Zero_Trust_Repos_and_Data_Contracts-October-5-2026.md]], then to [[wiki/people/nathan-carver.md|Nathan Carver]] at the [[wiki/meetings/2026-10-05-nathan-carver-flex-pay-slim-bom-reverse-spike.md|1:58 PM call]], where the "no monorepo" point was ruled [[raw/Meeting_Transcript_Nathan_Carver_Flex_Pay_Slim_BOM_Reverse_Spike-October-5-2026.md]]. It is the model the [[wiki/decisions/2026-10-05-nathan-carver-runs-the-flex-pay-slim-bom-reverse-spike-and-flex-port-follows.md|Flex Pay Slim spike]] tests. For the software side of the same model see [[wiki/decisions/2026-09-04-data-contracts-closed-every-repository-by-september-11.md]] and [[wiki/topics/github-release-management-pipeline.md]].

## What was ruled

- **The developer model, as Val gave it.** "Each repository. Is equal to a Project in Jira… has zero trust state… one repository does not trust the next repository. There is no reference between one repository to the next repository." Each repo "has code in it, has pros in it. Has ADRs in it. And most importantly… Date the contract": "a description of what it can do… It only wants to specify what it can give output." It is "in a dot MD file. It's called data contract." From that, Claude Code "is able to put things together into entire code of the product… as well as… run end-to-end testing." [[raw/Meeting_Transcript_Design_to_MSBC_Zero_Trust_Repos_and_Data_Contracts-October-5-2026.md]]
- **The same for electromechanical design.** "at 100%, it works in development. I, I am 70% sure. that it will work for electromechanical design. We just have to play with it a little bit." He expects "You will never have to do bill of material… the substitutions will automatically just work out. The versioning will be automatically there"; for a supplier substitution, "All you have to do is in Github to put a new revision." [[raw/Meeting_Transcript_Design_to_MSBC_Zero_Trust_Repos_and_Data_Contracts-October-5-2026.md]] To Nathan: "In GitHub, we can start from a flat list of all the parts… Data contracts is a description of what a certain sub-assembly does and how it works. But from a… output perspective, because of zero trust." [[raw/Meeting_Transcript_Nathan_Carver_Flex_Pay_Slim_BOM_Reverse_Spike-October-5-2026.md]]
- **GitHub holds a flat list, not a BOM; the BOM is generated.** Genadi asked why a BOM already pushed to MSBC should be regenerated every time. Val: "It's always on Github, not not bill of material, not bill of material, flat list of parts… You, you can generate it on the fly from Github." His comparison, in Russian: GitHub Actions builds the code into an ISO file, which then "живет уже жизнью, постоянной жизнью. Пока чтото не поменялось в azor клауд… Но живёт он в азор… то же самое, как он буший в Microsoft m sbc clowd… Сортов чуд является гигант. Где он живёт или вазур потом или в эсбиси. Это уже мало что значит?" Genadi asked whether the build comes out the same each time; Val: "Одинаково… потому что… они подписаны под тике чекса." Genadi: "Окей мало. Хорошо, я не знаю. Может быть." [[raw/Meeting_Transcript_Design_to_MSBC_Zero_Trust_Repos_and_Data_Contracts-October-5-2026.md]] To Nathan the same image: the ISO image built by a GitHub action and posted on Azure "To me, it's the same as… final bill of material in MSBC." Nathan: "Yes." [[raw/Meeting_Transcript_Nathan_Carver_Flex_Pay_Slim_BOM_Reverse_Spike-October-5-2026.md]]
- **Data contracts carry the assembly logic.** Val: "power comes from a power supply… a power supply is connected to a PC board with a harness… the monitor is connected to a PC board… either to HDMI or to some other connector… That logic to me is data contract." The fine detail ("the threat for this particular screw") comes from the supplier's spec. Swap a part with a compatible contract and it works; if the contract changes, the system should say "please change the four screws and change the harness." Nathan: "there's terminology gaps between Genadi's world and GitHub and BC, but it's all the same… how they interface together." [[raw/Meeting_Transcript_Nathan_Carver_Flex_Pay_Slim_BOM_Reverse_Spike-October-5-2026.md]]
- **One project = one repo; no monorepo.** Nathan suggested limiting the number of repos "for management's sake… You could have a mono repo with. various projects inside it". Val: "No, if we have one monorepo, then JIRA doesn't work. because we want certain capabilities within a project. Project is described by capabilities… harnesses, for example, are good to discuss under one project." Nathan: "Okay. That makes sense to me." Val: "I don't feel that there is a huge issue with having more repos, like, so what?" Nathan: "if the agents are managing them or searching through them, they'll know where to go." [[raw/Meeting_Transcript_Nathan_Carver_Flex_Pay_Slim_BOM_Reverse_Spike-October-5-2026.md]]
- **Nathan's addition: each repo tells the agent how to search it.** "each repo would have like an overall spec describing what it has… The repo would also describe how to search for those things… the repos can instruct the agent how best to search their data for compatible devices." Val: "that's why I'm saying displays is 1 repo. Harnesses is another repo." His example: a vertical 43-inch machine will not get a 27-inch screen. [[raw/Meeting_Transcript_Nathan_Carver_Flex_Pay_Slim_BOM_Reverse_Spike-October-5-2026.md]]
- **Humans describe, agents execute.** Val's summary of "the hinging decisions": "We have a project which is equal to a repo. A repo has all the information that it needs, plus data contract, plus the pros… the execution comes from the agents. A human doesn't touch anything. A human only describes in words what is it that the human wants." The output can go to MSBC, production files "or maybe request for proposal". Supplier finances stay on the administrative side. [[raw/Meeting_Transcript_Nathan_Carver_Flex_Pay_Slim_BOM_Reverse_Spike-October-5-2026.md]]

## Genadi's reaction (1:19 PM)

He did not reject it, but did not accept it either: "Окей мало. Хорошо, я не знаю. Может быть." His practical point: between two jurisdictions the difference may be "в 3 харнеса… Которые… Меняются за 4 минуты". And: "У меня просто есть чувство, что мы немножко оторваны от реальности. У миши до сих пор нету репорта, с которым он работает" — see [[wiki/people/mikhail-perelman.md]] (Oct 5). Val: Mikhail's problem is real but "совершенно идёт параллельно." [[raw/Meeting_Transcript_Design_to_MSBC_Zero_Trust_Repos_and_Data_Contracts-October-5-2026.md]] The notes: "Genadi said 'OK' but still has doubts" [[raw/Meeting_Notes_Design_to_MSBC_Zero_Trust_Repos_and_Data_Contracts-October-5-2026.md]].

## How it sits against earlier rulings (evolution)

It restates the Sept-23 to Oct-1 line — GitHub is the source of truth, one flat list, only the finished BOM goes into MSBC ([[wiki/decisions/2026-09-23-the-bom-source-of-truth-is-the-latest-design-in-github-and-sync-runs-one-way.md]], [[wiki/decisions/2026-10-01-only-the-finished-bom-goes-into-msbc-the-configurator-is-ai-logic-outside-it-no-hybrid-and-the-pilot-is-the-flex-pay-slim.md]]). What is new on Oct 5 is the **form** of the Oct-1 "configurator": not a separate tool, but zero-trust repos with data contracts that agents assemble, as in software (inference from the two sources).
