# GitHub org naming convention and the JVL enterprise org list

**Decision (Feb 11 2025, Val + Aaron + [[wiki/people/andrey-bosik.md|Andrei]] + [[wiki/people/pavel.md|Pavel]]/[[wiki/people/alexander-biratka.md|Sasha]]):** JVL uses a **multi-organization GitHub enterprise** (confirming the prior day's direction), with a fixed naming convention and a finalized list of organizations. [[raw/Git_repo_structure_part_2_2025-02-11.md]] This builds on [[wiki/decisions/2025-01-20-github-orgs-mirror-value-streams.md]] (orgs mirror the Jira value streams).

## Naming convention

- **Organization names:** written in **plain English with capitals** and a **"JVL " prefix** (e.g. "JVL Platform"); GitHub then applies its own rules to form the URL slug (converting spaces to hyphens). Typing human-readable names lets GitHub enforce a consistent convention rather than engineers guessing hyphen-vs-underscore. Uppercase in the org URL is deliberately accepted for readability (Aaron overrode the GitHub docs' lowercase recommendation). [[raw/Git_repo_structure_part_2_2025-02-11.md]]
- **JVL prefix agreed** for org names (Andrei/Sasha wanted uniqueness; org names are globally unique on GitHub). Aaron argued for JVL **at the front** (sorts by the next letters); Alex noted a suffix sorts better — front prefix was adopted. [[raw/Git_repo_structure_part_2_2025-02-11.md]]
- **Repository names:** lowercase, hyphenated, **short and descriptive**, **no "JVL" prefix** and no "repo" suffix (e.g. `reels-math`, `shuffle-math`, `hold-and-spin`, `hal` for hardware-abstraction-layer). Aaron cited the Home Assistant org (100+ repos, minimal names) and warned that JVL-prefixing every repo would make the code hard to ever sell. Repo names are not globally unique (only org names are). [[raw/Git_repo_structure_part_2_2025-02-11.md]]
- Example full URL agreed: `github.com/JVL-Core-Technology/hal.git`. [[raw/Git_repo_structure_part_2_2025-02-11.md]]

## History — how the list emerged (Feb 10 part-1 meeting)

The org list was hammered out the **previous day** ([[wiki/meetings/2025-02-10-github-repo-structure-part-1.md]]). [[wiki/people/alexander-biratka.md|Sasha]] opened proposing **one organization, "or probably two"** (one company-wide + one private for the math sources), arguing GitHub **groups** handle rights more flexibly than organizations and that mirroring Jira in orgs "didn't work out"; Aaron called one-org "short-sighted" and pressed the scaling question; by the end the group "naturally arrived" at **five organizations — game development; online + land-based platforms (one org); math; observatory and orchestration platform; core tools** (core tools then = TEST360, diagnostic and design tools). [[raw/github _structure-pavel-aaron-andrei.md]] Val then sketched **responsible owners per org** — game development: Lena; platforms: Sasha; math: Efim; observatory & orchestration: Dima Chudinov; core tools: Pavel — and proposed a **sixth org, "core technologies"** (Flex Payment Solution, hardware abstraction layer + firmware, and possibly the distribution infrastructure folded in), noting Pasha doesn't actually manage TEST360, the diagnostic tool or design tools like Miranda. [[raw/github _structure-pavel-aaron-andrei.md]] On submodules, Andrei said the team uses **GitHub Apps** rather than deploy keys ("we don't use deploy case [keys], because deploy case has some restrictions when we need to create pair case for main repository to sub-module repository") — adding "these GitHub applications work only in one organization," an argument for fewer orgs at that point; Aaron countered that submodules can be referenced from any accessible repo and warned against baking in GitHub-only dependencies (the GitLab portability test). The cross-org access solution came the next day ("I work with GitHub application. I found a solution how we can have access to submodules if needed to another organization"). [[raw/github _structure-pavel-aaron-andrei.md]] [[raw/Git_repo_structure_part_2_2025-02-11.md]] The next day's part-2 session confirmed multi-org and finalised the 7-org list above ("As we said yesterday…"; Sasha: "I agree with yesterday's solutions"). [[raw/Git_repo_structure_part_2_2025-02-11.md]]

## Aug 18 2025 — reversal under discussion: consolidate the many orgs into ONE (or few)

Six months on, the multi-org structure is being **reconsidered in the opposite direction**. On the Aug-18 2025 4:30pm GitHub meeting ([[wiki/meetings/2025-08-18-github-org-consolidation.md]]; Val, [[wiki/people/andrey-bosik.md|Andrei Bosik]], [[wiki/people/pavel.md|Pavel Frolov]]; Russian) Val pushed to **collapse the several organizations into one, or very few**. This is a **discussion, not yet a locked decision** — the parent "orgs mirror the Jira value streams" premise ([[wiki/decisions/2025-01-20-github-orgs-mirror-value-streams.md]]) is what's being walked back. [[raw/Git_organization_management.md]]

- **Rationale (Val):** the mapping of orgs to value-streams/initiatives "never worked out cleanly" (Pavel agreed), and JVL naturally keeps evolving away from Jira anyway; managing many orgs is inconvenient for everyone (each org needs its own link structure), and "everyone insists on even a single organization" for JVL's headcount. One org **streamlines** work — everyone sees all repos, focuses on one place. [[raw/Git_organization_management.md]]
- **Cost:** restructuring itself is easy, but **many GitHub Actions must be rewritten** — especially cross-referencing ones (owned by Andrei, Pavel, Sergei Tsyganov, "Sasha"). Migration is critical items re-created (not moved). Estimated a couple of hours per person's actions. [[raw/Git_organization_management.md]]
- **Timing:** wait **~1–2 weeks** for people to return from holiday (the action's author edits it fastest); "no panic," schedule it deliberately. [[raw/Git_organization_management.md]]
- **Admin model shift:** with fewer orgs, ownership consolidates to **Andrei, Dima, Val and Aaron**; **Andrei alone** would issue rights/permissions. [[raw/Git_organization_management.md]]
- **Jira↔GitHub linkage:** Val clarified they still link **tasks at the *feature* level** informationally between Jira and GitHub, but **stop trying to force a logical parallel** between Jira projects and GitHub orgs. [[raw/Git_organization_management.md]]
- **Process discipline reasserted:** Val insisted the consolidation itself be justified by a **use case → requirement** ("if there's no user story, there's no task"), refusing "floating tasks in the air"; he asked the meeting recording be written up into the use case. [[raw/Git_organization_management.md]]
- **Next step:** Andrei + Pavel meet the next day to work out **correct org naming** and the source→target migration map; largest orgs today are "Cortex"(?) and the gaming platform. [[raw/Git_organization_management.md]]

## Sept 9–16 2025 — consolidation locked + a new kebab repo-naming taxonomy (4-session arc)

Six weeks after the Aug-18 discussion, a **four-session working arc** (Val, [[wiki/people/pavel.md|Pavel Frolov]], [[wiki/people/aaron.md|Aaron]], [[wiki/people/andrey-bosik.md|Andrei Bosik]]) moved the org consolidation from "under discussion" to **decided and entering execution**, and replaced the thin Feb-11 repo-naming rule with a full **kebab taxonomy**. Sessions run Sept 9 → 10 → 12 → 16; each has its own thin stub, the substance is sequenced here.

- **Sept 9** ([[wiki/meetings/2025-09-09-github-repo-naming-convention-tool.md]]). Established the repo-naming taxonomy: names are built **category → subcategory → component → variant**, in **strict kebab-case** — a word *inside* one taxonomy term is joined with an **underscore**, and **dashes join the taxonomy levels** (so listing repos parses cleanly). Abbreviation rule: **spell out** JVL-specific abbreviations (Aaron cited not knowing what "LGS" meant); keep only widely-known ones (API, GUI, OS). Aaron argued long/ugly names are a healthy signal a repo should be **merged into a larger repo** rather than kept separate. He began converting the naming spreadsheet into a **JSON file backing a validation tool** loaded into GitHub — a management repo whose actions flag wrongly-named repos, wrong permissions, stale accounts; potentially wired so a **Jira support-request** validates a name then a **webhook auto-creates** the repo. [[wiki/people/andrey-bosik.md|Andrei]] proposed a **separate "Knowledge" organization** for non-development repos (personas, CBSA, HR, accounting); Aaron pushed back ("consider what the word organization implies") — use **one** org with a `knowledge` category, since a second org fragments where people stash notes and forces content-shuffling between orgs. [[raw/review_git_structure-september-9-2025.md]]
- **Sept 10** ([[wiki/meetings/2025-09-10-github-repo-taxonomy-review-naming-rules.md]]). Refinement pass, Val playing "dictator" to force closure. Key rulings: the taxonomy is a **filter for valid names, not a definition of every repo you will build**; **do not plan repos for things that haven't happened yet** (local-gaming-server vs an Omni variant); collapse duplicate concerns (local_gaming_server + its GUI). Aaron wrote out **naming rules**: (1) match obvious names with the fewest kebabs, left-to-right (big → small); (2) if a repo must exist but doesn't fit the filter, **discuss why it exists** — it may belong as a branch or path in an existing repo; (3) commit positively to **merging** repos, since fewer repos generally means more clarity; (4) but **split** for separation of concerns when a repo becomes a catch-all; (5/6) some merges are technically complex — **set a due date** so the DevOps team can drive them. Named the CMS-replacement / orchestration-observation system a repo called **"platform flex back end"** (Val settled it over "Omni"; Aaron: Omni games *run on* the Flex system). Defined the planning-tab columns — **target organization, validated repo name, planned move date, planned action (merge / rename / delete / create), optional target repo, responsible person, inward/outward dependencies, description of work** — which then become **Jira issues** (the spreadsheet gets thrown away). Aaron's cost/speed anchor for the AI-supervised approach: he once billed ~$30k migrating ~500 repos data-center→GitHub in a week by letting an AI agent do the moves under supervision (external-consulting anecdote, not JVL economics). [[raw/git_repo_structure_review-september-10-2025.md]]
- **Sept 12** ([[wiki/meetings/2025-09-12-github-repo-org-archive-knowledge-federation.md]]). The **archive-organization debate**: [[wiki/people/pavel.md|Pavel]]/[[wiki/people/andrey-bosik.md|Andrei]] wanted a separate org to hold obsolete-but-retained code; Aaron argued **GitHub is not a backup strategy** — either keep code *alive* (maintained build pipeline, Dependabot, an owner) or truly archive it off-platform to tape and remove it, leaving a pointer. Framed it as an **IT-governance / grooming** discipline (Val: "like never cleaning your desk"). **Pavel conceded to continue "as is"** — all repos in the main org (one of two) — but flagged returning to it in ~2 years at ~200–600 repos; Val's takeaway was that a **regular grooming procedure** is the real answer. Other decisions: **re-enable Issues, Projects and Discussions** on repos where they'd been disabled; agreed **merges** (local-gaming-server + omni-local-gaming-server + utils into one; Flex-POS/Flex-Pay GUI modules into the main repo); **delete the CBSA repo** (Val: not shared with anyone); **keep personas** (general). The big architectural teaching was **knowledge federation / docs-as-code**: instead of a Knowledge org or a giant knowledge repo, each project keeps a `/docs` directory, and a meta repo called **knowledge** aggregates them via **git submodules + git filter-repo**, published through **MkDocs / Docusaurus** — "essentially a git-based Confluence." Also debated making **platform-AWS** a subcategory (`platform-aws-cluster`, version-controlled) — Andrei partly disagreed (cluster management vs deployment are different concerns; large repos slow some services). Val's monologue pressed Pavel/Andrei on *why they resist* a well-tried consultant method; and recounted **why the SVN→GitHub move stalled for graphics** — Omni wasn't ready, LFS was unresolved, Lena's team couldn't be convinced, Andrei wasn't yet git-trained, so they **parked graphics and started with core** (games still build from SVN via Jenkins — a company "split brain" Aaron wants closed). Undertaking: [[wiki/people/andrey-bosik.md|Andrei]] to produce a **written migration plan** by Tuesday. [[raw/git_repo_organization-september-12-2025.md]]
- **Sept 16** ([[wiki/meetings/2025-09-16-github-repo-migration-plan-review.md]]). Review of Andrei's change plan (he placed it in **Confluence**, RU + EN because most developers are Russian-native; Aaron noted it should live in git/`/docs`). Worked out **how to track the migration as work**: model GitHub itself as a product/capability, the **two target organizations** as features, and **one story per repository** (Aaron: write stories for the *end* structure, each repo atomically movable and backable-out; the current **~11 organizations** collapse to **2**). Aaron's ideal: the **first** repo changed should have been the GitHub-management repo, holding the change doc in `/docs` and a project tracking the per-repo stories — putting the low-level items in GitHub and the feature-level in Jira, exactly the two-camp split. Covered **secrets / variables / self-hosted-runner** migration: recreate **same-named** secrets in the target org (names are referenced in actions), use a **"GitHub Organization Secrets migrator"** tool — and explicitly **do not route secrets through an LLM/MCP** (only names, if anything). Change-management discipline stressed: per-repo analysis, ordering by dependency, notifying repo owners (Aaron's Ford Motor anecdote — 60,000 repos, a 12–14-person team on 3 shifts, every repo with a full plan). [[wiki/people/val-levitan.md|Val]] pushed hard for a firm schedule after judging only **one** prior undertaking done (the plan exists but lacks a solid schedule; secrets not fully collected; migration order not proposed) and set a **Friday** check-in against Andrei's ~2-week plan (≈1 org/day). [[raw/git_repo_structure.md]]

**Net effect on this decision.** The **naming convention survives and is elaborated** (the kebab category/subcategory/component/variant taxonomy supersedes the thin Feb-11 "short lowercase-hyphen, no prefix" rule). The **multi-organization structure is reversed**: the Feb-11 seven-org list mirroring the Jira value streams is **superseded** — JVL is consolidating to **~2 organizations** and, as of Sept 16, this is decided and entering execution (Andrei preparing target orgs + migration plan). This also **resolves the open flatten-vs-many-orgs question** carried on [[wiki/decisions/2025-04-03-jira-capability-level-and-github-mapping.md]] and walks back the parent premise [[wiki/decisions/2025-01-20-github-orgs-mirror-value-streams.md]].
