# Insert a "capability" level in Jira as the executive-demonstrable unit mapped to GitHub feature branches

**Decision (Val, worked out with [[wiki/people/aaron.md|Aaron]] over Apr 1–2 2025 and presented to the Minsk team Apr 3):** add a new level in Jira called **capabilities**, sitting **between feature and product**, as the unit an executive can understand and physically demonstrate. A capability is a **bundle of features** (roughly three–four features per capability); a JVL product is described by its capabilities. This resolves the Mar 31 "how do GitHub and Jira line up" homework (see [[wiki/meetings/2025-03-31-github-jira-alignment.md]] and [[wiki/projects/jvl-2025-plan-and-jira-roadmap.md]]). [[raw/gut_hub_jira_relationship-april-2-2025.md]] [[raw/github_jira_setup-april-3-2025.md]]

## Why capability, not feature (the Apr 2 breakthrough)

- Val had assumed a Jira **feature** maps one-to-one to a GitHub **feature branch**, giving him a clean "demonstrate this feature" checkpoint. [[raw/gut_hub_jira_relationship-april-2-2025.md]]
- Aaron showed with a diagram that this breaks: making one real feature work usually requires changes across **several repositories** at once (e.g. the application *and* a shared library), each a separate **story/branch** — so a Jira feature already maps to **multiple** GitHub branches, not one. The demonstrable thing is the **pull-request view** of everything that changed together. [[raw/gut_hub_jira_relationship-april-2-2025.md]]
- Val's resolution: "in my mind, I would connect Git feature branches to a JIRA **capability**… business mind, like mine, and those executives that I communicate with, we talk in capabilities… what should be demonstrable to us is a capability." Aaron noted he was **not** proposing renaming feature→capability; the point is that the demonstrable executive unit is the capability. [[raw/gut_hub_jira_relationship-april-2-2025.md]]

## Repository = product, and "a product is an artifact in motion" (Apr 1)

- Ground rule Aaron set and Val adopted: a **code base / repository is never a product**. Running the build produces an **artifact** (the ISO, executable, output files); "a product is an artifact **in motion**" — an artifact moved over time to market. So a Jira product/ownership item should **not** be equated with a code base. [[raw/git_jira_correlation-april-1-2025.md]]
- Working mapping Val settled on: **feature branch = a Jira feature; stories = the commits under it; when a feature branch is pulled into main, the feature is "done"; the sum of all features → the ISO → the product; repository = a product** (Val: "which I agree might be wrong"). Aaron pushed back that repository-per-product over-simplifies engineering reality — a repository is a **collection of deposits by concern** (library, service, application, firmware), not a product. [[raw/git_jira_correlation-april-1-2025.md]]

## The rules Val set for the team (Apr 3 lecture)

- **SVN → GitHub is locked** — "это уже решили… мы уже перешли" (already decided, already moved); not up for further debate. [[raw/github_jira_setup-april-3-2025.md]]
- Two tools only for this: **GitHub** (development camp) and **Atlassian Jira** (executive camp); **Confluence deliberately left out** of this discussion. Capabilities/features are the "clutch" coupling the two camps. [[raw/github_jira_setup-april-3-2025.md]]
- **Feature branches kept short — max one week.** [[raw/github_jira_setup-april-3-2025.md]]
- **Lengthen the sprint to ~3–4 weeks** (four "feels a bit much," two "too short") so a sprint can **deliver two–four features**; Val deliberately does not sit inside the sprint but controls **delivery of features** and watches commit velocity. [[raw/github_jira_setup-april-3-2025.md]]
- **Who writes what:** product managers ([[wiki/people/juan-martinez.md|Juan]], Val, or Felipe) describe **capabilities** and the user experience; [[wiki/people/pavel.md|Pavel]] sits with Juan to write **features**; **developers** (Val named Igor Metelski/"Мительский" and a "Харецкий"/Haretsky) write the **stories**. If features/stories aren't written down and forced, delivery goes chaotic and unplannable. [[raw/github_jira_setup-april-3-2025.md]]
- **"No test, no pull."** Val invited [[wiki/people/irina-makarych.md|Irina]] because a feature must be **testable**: when a feature opens, QA flags it for an automated test wedged **into the pull into main** — no passing test, no merge. Val's goal is for the engineers under Irina to write the tests themselves. [[raw/github_jira_setup-april-3-2025.md]]
- Val will pull the **ISO himself** — he asked [[wiki/people/andrey-bosik.md|Andrei]] to build him **GitHub Actions** so he can take a capability's code, load it on a machine, and read the capability. [[raw/github_jira_setup-april-3-2025.md]]
- **Repository = product** for now (e.g. **FlexPay is a repository**), though Val admits he still only "loosely" understands what a developer builds inside it (libraries, applications). [[raw/github_jira_setup-april-3-2025.md]]
- **AI/MCP tooling is what makes this possible** — Aaron gave Val a Jira/Atlassian **MCP** so Val can interrogate Jira in plain language ("summarize these features, what capability do they make; where are the scope gaps"), plus the **sequential-thinking MCP**; with Claude/Sonnet + ChatGPT this "diff table" of scope gaps is now easy, in any language. [[raw/github_jira_setup-april-3-2025.md]] [[raw/git_jira_correlation-april-1-2025.md]]

## The gears/clutch analogy and the role split (Apr 3 Aaron session)

On a long Apr-3 English one-on-one ([[wiki/meetings/2025-04-03-github-jira-capability-aaron-session.md]]; the transcript loops/duplicates heavily — facts taken once) Aaron and Val settled the *mechanism* coupling the two tools, extending this decision: [[raw/github_jira_integration_relationship-april-3-2025.md]]

- **Gears and a clutch:** Aaron drew an AI-generated gears animation — commits (fastest) → pull requests → stories → **features (purple, in GitHub)** → **capabilities (green, in Jira)** → product → value stream (slowest). Val "clutched to it." The **clutch** that couples green to purple is the **negotiation/agreement between the executive branch and the engineering branch** (Aaron: tangibly, the **stack-rank order of work in a sprint**). [[raw/github_jira_integration_relationship-april-3-2025.md]]
- **"Don't interfere with the sprint"** — once work is committed to a sprint you must step back and let people work; interfering "breaks everything" ("It's like trying to shift without using the clutch"). Contract negotiation happens *after* the sprint. [[raw/github_jira_integration_relationship-april-3-2025.md]]
- **Run the task list in GitHub, keep the source of truth in Jira (for now):** GitHub issues are a light task list ("they literally call them the same thing that JIRA calls them"); don't track stories/features in GitHub, only **branches of work**. A Git branch name is just a human label to a commit — "feature," "bugfix" etc. are social conventions Git doesn't enforce. Keep developers in their IDE, project managers in project-manager land ("if you ask developers to work in Jira, now they're Jira engineers and not writing code"). [[raw/github_jira_integration_relationship-april-3-2025.md]]
- **Role split:** [[wiki/people/juan-martinez.md|Juan]] = the **non-technical product manager** who ideates/aims capabilities; [[wiki/people/pavel.md|Pavel]] = the **technical product manager** who breaks capabilities into features (he doesn't write code); [[wiki/people/alexander-biratka.md|Sasha]] = the **architect/developer** (Aaron named Sasha the "architect of the Omni framework") who supplies feasibility, estimation, alternatives. "A blend of Pavel and Juan is one product manager." A **feature is born out of negotiation** to deliver a capability within a set time (~one week per feature) — "almost like negotiating MVPs." [[raw/github_jira_integration_relationship-april-3-2025.md]]
- Aaron's scale caveat: this whole approach works only for a **team under ~20 people** (JVL's dev org is under 20) — bigger and "you're just farming it off to India." Val's recurring exhibit: his AI-driven **cottage-office renovation** — recording the contractor walkthrough, feeding it to AI to find scope gaps and generate a signable quote — the same method he applies to reconcile feature branches to a capability. [[raw/github_jira_integration_relationship-april-3-2025.md]]

## Why it matters to Val (Apr 1, in his own words)

Val framed the whole exercise as being about his own comfort and control, not engineering elegance: "My function is to create alignment and symbiotic movement from requirements to code commit… unless I can smoothly and comfortably move between the requirements and the ISO image, everything else is immaterial to me." He recounted his prior company being sold to a billion-dollar American acquirer at ~30%/yr top-line growth and ~44% net margin, then hollowed out (margin to 10%, out of business in 15 years) after being moved onto **SAP** and split into departments — his cautionary tale against structure-for-structure's-sake. [[raw/git_jira_correlation-april-1-2025.md]]

## May 5–6 refinement — feature-as-temporary, capability-as-permanent, and Jira Product Discovery (decision-in-motion)

Three sessions with [[wiki/people/aaron.md|Aaron]] ([[wiki/meetings/2025-05-05-feature-granularity-aaron.md|May-5 feature-granularity]] and the [[wiki/meetings/2025-05-06-feature-jira-defining-and-reflection.md|May-6 defining + reflection]]) deepened this decision. All three transcripts loop/duplicate their own content — facts taken once. **No new structural ruling was locked** — Val repeatedly deferred a Jira refactor ("maybe it's a conversation for tomorrow… let's game it out… draw it out on a graph… definitely not this week"). What changed is Val's *understanding* of the levels:

- **A feature is temporary; a capability is permanent.** Val's prior mental model treated a feature as "a permanent anchor to a product"; Aaron reframed a **feature as a short, throwaway unit of deliverable work** that "falls away" once delivered/closed, while the **capability is the permanent description of the product**. What persists long-term after features close is the **capability + its requirements + the tests** embedded in the code repo (unit/integration tests are "your long-term persistent acknowledgment of that feature"). Requirements are the "control lever": you modify a capability only by revising its requirements. [[raw/feature_granularity_definition_aaron-may-5-2025.md]]
- **Features must be demonstrable in ~1–2 weeks; the minimum unit of proof is a passing test.** Trigger for the whole conversation: [[wiki/people/anton-leshkevich.md|Anton]] was working a story (LGS196, "Data center UI… leave save mechanism") under feature **LGS-14 (LGS Configuration GUI)** that is really feature-scale, and the board had **~100 open features** ("no fucking way a team of 10 to 15 people can track 100 features at once"). Aaron's rule: ask "what will you have **functional** at the end of the sprint?" — if the answer is "it can't be shown," demand a **passing test** as the minimum ("no test, no… you have an infinite feature"). The example feature "**initial setup screens for local gaming server**" was 92% complete, i.e. should have been split (guided-setup, core-parameter-config, etc. each their own two-week feature). Val prefers to speak in **one-week** increments because two-week estimates slip to a month. [[raw/feature_granularity_definition_aaron-may-5-2025.md]]
- **New vocabulary: component and the "double diamond."** A **component** = a cluster of related features (Aaron's Tesla example — the motors are a component of many sub-assemblies; and "the feature means a different thing depending on who you ask," from motor-lab engineers up to global sales). The **double diamond** = discover → define → develop → deliver; only the *deliver* portion is a software engineer's sprint. [[raw/feature_granularity_definition_aaron-may-5-2025.md]] [[raw/feature_reflection_jira-may-6-2025.md]]
- **Jira Product Discovery / PLM as the home for the top levels.** Aaron explained Jira **Product Discovery** grew out of Atlassian's **Jira Align** (a scaled-agile/SAFe portfolio product Atlassian acquired ~4–5 years earlier); it is a separate Jira **project type** (licensed) for **Product Lifecycle Management** — impact/effort scoring of ideas, then a "create delivery ticket" button that spawns features. Aaron's split: **feature and below = work management**; **above feature = discovery / product management**. [[raw/feature_defining_jira-may-6-2025.md]] [[raw/feature_granularity_definition_aaron-may-5-2025.md]]
- **The restructure direction Val is circling (not enacted).** Move the high-level Jira items (the blue **product**, red **initiative**, orange **value-stream** icons — all prefixed "IP") into **product-discovery projects**; make **capability** replace the product-line level and let the **initiative become the product**, with each initiative getting its own discovery project. Aaron cautioned this does **not** "free up levels for planning," that engineers never get control of the value stream, and that Jira Product Discovery is "just another project type." The team agreed to draw it on a graph and plan a Jira-config refactor later. [[raw/feature_granularity_definition_aaron-may-5-2025.md]] [[raw/feature_defining_jira-may-6-2025.md]] [[raw/feature_reflection_jira-may-6-2025.md]]
- Aaron also urged the **"discover → define → develop → deliver" phrasing** as a general flow to align technical and non-technical product ownership; Val said he couldn't fully absorb the diamond model yet but now understood features must become "more fluid and shorter and weaved into integration testing." [[raw/feature_granularity_definition_aaron-may-5-2025.md]]

## May 8 refinement — Compass as the engineer-side "second diamond", and the core-technology worked example

A May-8 Aaron↔Val session (three recorded segments — [[wiki/meetings/2025-05-08-capability-compass-mcp-aaron-session.md]]; the capability/Compass segments feed this decision) sharpened the model further. Still **no structural ruling locked** — Val: "I don't want to just try to throw all of these at once at the people working in the JIRA projects, because we're barely… treading water right now with sprints."

- **Atlassian Compass = the engineer-side counterpart to Jira Discovery (the "double diamond").** When Val opened the Jira **components** page it prompted him to "try Compass." Aaron explained: before Compass, Atlassian's model was that a project (a software product) has **components** tracked inside it — e.g. the local gaming server project has **five components: SAS, QR codes, progressive money system, setup GUI, and core** — "which sounds suspiciously like capabilities." About a year ago Atlassian began steering teams to move components into **Compass**, which then **connects the actual feature branches and committed work in the code repo back to those components** (a component built up by feature-complete work = a delivered **capability**). Aaron's framing: the **discovery-style Jira projects** are the "first diamond" (leadership/product-ownership view — defining the capabilities to work on); **Compass** is the "second diamond" (the engineering/developer view). "Compass and this discovery thing… they're kind of the two sides… the puzzle pieces… one is for the engineers and the other is for the product ownership. They connect together." [[raw/discovery_tracking_capabilities_compass_jira-may-8-2025.md]]
- **Where components have gone wrong:** the **core technology** project has "a lot of components… that are not really components. They're just… a mash of groups of subsets of to-do lists." Val's tangible next step: **pick one product to pilot the capability-first approach** — he named **remote initial setup (RIS)** / "the system that's inside of RIS" (its backend) — work with those people to define it capability-first, and explicitly tell them "this is different than how it's been worked before… let us know" if it feels the same or different. [[raw/discovery_tracking_capabilities_compass_jira-may-8-2025.md]] (RIS's Jira placement was earlier flagged as an initiative-name problem folded under "Slot Links" — see [[wiki/projects/jvl-2025-plan-and-jira-roadmap.md]].)
- **Val's own maturation on the levels (core-technology worked example).** In the product-capability-feature segment Val said capabilities are now easier for him to reason about for **physical/core-technology things than for theoretical games**, and worked a durable example: a machine's **coin acceptor / coin hopper / coin shoot** was once a capability; when **bill acceptors** arrived JVL added a bill-handling capability (funnels, stacker); later **coins were dropped entirely** — that capability "disappeared" — and a **ticket** capability (ticket printer, ticket acceptance/processing) was added. Removing coins was not one change but a set of **feature updates** (front panel without the hole, wiring/harness, software to stop counting coins). His conclusion: a **feature is temporary** ("the act of completion of the feature… should always be a short, demonstrable, testable cycle"), while its **effect** may last a long time — corrected mid-sentence from "lifetime" to "effect." [[raw/product_capability_feature-may-8-2025.md]]
- **RIS as a capability, features, and stories.** Val's clean illustration: for remote initial setup, the **capability** is "to remotely push the configuration onto a machine"; the **features** are selecting machines, selecting a configuration to apply, restricting who can apply them, and getting reports; a **user story** under the selection feature is "as a user, I don't want to scroll through 50 pages of machines. I want to just filter the ones I care about." As the engineer executes the stories and pulls the feature branch into main, he must ship a **test set** with it. [[raw/product_capability_feature-may-8-2025.md]]
- **The acute mistake being made (why GitHub gets over-complicated).** Val diagnosed JVL's current Jira organization: it tries to **attach features directly to a product** and to **define many future features ahead of time**, so **capabilities and features get mixed** (sometimes with a user story or to-do list piled in) — inflating a confused "feature+capability" blob that no one knows how to close or which repository to put it in, "which overly complicates the GitHub portion of our integration." [[raw/product_capability_feature-may-8-2025.md]]
- **Compass adoption is an agreement-in-principle, not enacted.** Val noted he'd first raised Compass "about six or eight months ago" and JVL "elected not to pursue it" because of the change-management cost; the May-8 view is that "there's more pieces in place than we realize to… adopt a capability-first approach," to be introduced gradually rather than all at once. [[raw/product_capability_feature-may-8-2025.md]] [[raw/discovery_tracking_capabilities_compass_jira-may-8-2025.md]] (This keeps the open question below open — the Jira restructure + Product Discovery + Compass adoption are all still direction, not ruling.)

## Open questions

- **Restructure Jira per the May-5–6 direction?** Should **capability** replace the product-line level, the **initiative become the product**, and the top levels (value stream / initiative / product) move into **Jira Product Discovery** projects? Direction agreed in principle, no ruling; a graph + refactor plan deferred. — [[raw/feature_granularity_definition_aaron-may-5-2025.md]] [[raw/feature_defining_jira-may-6-2025.md]] [[raw/feature_reflection_jira-may-6-2025.md]]
- **Flatten GitHub to one organization, or keep many orgs?** Unresolved. Aaron pushed hard to **flatten all repos into one org** with a naming convention (e.g. `framework-omni-renderer`), citing Block/Square keeping ~30 repos in one space, and warned Val's per-org control is "a precarious knife edge." Val **refused to flatten** — he cannot achieve executive alignment without the org/concern structure — but conceded there are "too many orgs" today and that people are already committing into an unvetted new org ("wild west"). Aaron's model of the org level = a **concern** (manufacturing, finance, marketing, sales, HR), with repositories under it named by purpose (library/service/application/firmware). This revisits, and does not yet supersede, [[wiki/decisions/2025-02-11-github-org-naming-and-structure.md]] and [[wiki/decisions/2025-01-20-github-orgs-mirror-value-streams.md]].
