Durable points (single source):

- **HFM-339 concretised — add a "cancel-transaction" message to the WSS protocol.** The current FlexPort↔FlexPay **WSS** protocol has only a two-phase **request → confirm** transaction (phase 1 proposes, phase 2 confirms) and no way to say a transaction *didn't* complete. To handle the over-limit bill-return, Yavorski (with [[wiki/people/dmitri-chudinov.md|Dima Chudinov]], the prior week) decided to add a **"cancel transaction" / "cancel"** message — done the same way as the **SMIB protocol's existing cancel ("hensel/cancel") command** — so a returned bill ends the transaction cleanly instead of hanging. Yavorski wrote the **draft of the new message**; Pavel to review with Dima whether existing error-handling already covers the case before it goes into the protocol. [[raw/Flex-Port, Flex-Smib, Flex-POS sync and planing meeting.md]]
- **The task tree behind it.** **HFM-340** = implement the two-phase-confirmation protocol (due ~Thursday this week). **HFM-353** = the multi-denomination *chain* logic (send/confirm each bill in sequence). **HFM-351** = the **user screens** — Yavorski proposed ~3: a **progress** screen ("$50 of $95 → $70 of $95…"), a **remaining-on-ticket** screen after the last bill, and a **limit-reached** screen (a deliberately neutral "limit" message — Val: JVL doesn't know *why* the machine stopped accepting, e.g. a bill the machine's setup disallows, so a neutral message is correct). **HFM-352** = reporting (small). Yavorski to finish drawing the screens or hand them to a designer. Whole chain **~3 weeks = end of December**. [[raw/Flex-Port, Flex-Smib, Flex-POS sync and planing meeting.md]]
