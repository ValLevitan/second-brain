**Session 5** of the recurring fast-pacing / general-alignment stand-up series — sequenced to the [[wiki/meetings/2025-09-10-fast-pacing-alignment-standup.md|Sept-10 opener]] (s1), [[wiki/meetings/2025-09-17-fast-pacing-alignment-standup-spec-prototyping.md|Sept-17 spec-prototyping]] (s2), [[wiki/meetings/2025-09-24-fast-pacing-alignment-standup-pipeline-interviews.md|Sept-24 pipeline-interviews]] (s3) and the [[wiki/meetings/2025-10-01-fast-pacing-standup-reverse-omni-tests.md|Oct-1 tests-first flip]] (s4). Durable points:

- **Current-products status (Irina).** Fiery/Sling is the current focus; **Jackpot Trash/Rush** is queued next; "Extensive" is parked on the shelf; a **Golden Husk** clip was handed over the day before; and JVL is now **taking Jackpot Rush Georgia into work** — specifically the progressive-functionality changes. [[raw/fast-pacing-stand-up meeting-october-10-2025.md]]
- **The AI-from-code experiment confirmed the hypothesis, not a surprise.** Pavel ran **~2 meetings** feeding meeting transcripts + code analysis to the AI and got "quite a lot of inaccuracies" — not usable raw, everything must be re-read and corrected. Val's response: this is exactly what they expected going in ("the first pass would be dirty… nothing new discovered"). Method lesson (Pavel): **don't ask the AI to do everything at once** — pose **smaller, more focused questions** so it returns manageable pieces easier to review and fix, rather than a pile of documents. Next he'll try feeding the AI the meetings **plus a real game plus the LGS** for richer context. (Continues the Oct-1 read-aloud/iterate loop.) [[raw/fast-pacing-stand-up meeting-october-10-2025.md]]
- **Val's delegation lecture — stop carrying it all yourself.** Val pressed [[wiki/people/pavel.md|Pavel]] on why he takes the whole spec/test job on his own shoulders instead of splitting it and handing pieces to the developers (educated people who know their own code). He rejected "if you want it done well, do it yourself" as a **40-year-old wrong lesson** — "take the right people who can do it for you." His diagnosis: Pavel is **shy to hand out work whose outcome he isn't 100% sure of**; but every new game/undertaking contains something unproven — the fix is to **discuss the direction** with a developer (who then agrees it's likely right) and **let them build the piece themselves**, freeing Pavel to manage more and letting people learn (they don't value work handed to them finished, and learn nothing). Val also suggested **allocating people more dedicated time** rather than the ad-hoc "1–2 hours a day when they get to it." [[raw/fast-pacing-stand-up meeting-october-10-2025.md]]
- **Test hooks now being built (Anton Leshkevich).** Pavel has **tasked [[wiki/people/anton-leshkevich.md|Anton Leshkevich]]** with building the test **hooks** ("крючки") — the same blocker flagged Oct-1 — and asked the developers to **rewrite their test cases in a concrete request form**: "my program requests such-and-such hook → receives this data → analyzes it → passes it to another hook," rather than abstract "we should check element X." That makes clear, from the test-framework side, which hooks are needed. A **Tuesday meeting** is booked to discuss these test cases. [[raw/fast-pacing-stand-up meeting-october-10-2025.md]]
- **UI test-automation progressing (new Alexander × Biratka).** The **new "Alexander"** (Tumanov by the Sept-24/Oct-1 new-hire context — inference) is now working closely with the **"old Alexander," [[wiki/people/alexander-biratka.md|Sasha Biratka]]** (transcribed "Сбер атка"/"пиратка"), and has learned to drive the UI from the test side — clicking buttons, recognizing elements by coordinates, working with events. Pavel: the idea of writing tests for the game, the UI and components "is quite viable — it needs developing." [[raw/fast-pacing-stand-up meeting-october-10-2025.md]]
- **Spec is the missing unifying layer (Val).** Val's point: they keep advancing tests off tribal knowledge, but the framework should be **documented → turned into a specification → tests tied to the spec**, because "tests can't be bound to the framework's raw knowledge." The spec is the joining element between framework and tests. Pavel's nuance: for the framework itself, a spec matters more so **developers understand how to use the components** — the thing to test is the **game realized on the framework**, and a game's spec source is its **GD/JD (game-design doc)** plus general game rules / JVL-lab requirements. [[raw/fast-pacing-stand-up meeting-october-10-2025.md]]
- **The feature-level GitHub workflow, spelled out (Val).** Game development is split into three streams — **Concept (Accept) → Design → Production**. JVL visually tracks stages down to the **feature** and deliberately **stops recording anything below feature level** (stories); a few exceptions remain un-migrated. A feature is taken into work by **pressing a Jira button → a feature branch opens in GitHub**; the person doing the stage (Michael, Lena) builds the required **artifact** — an **abstract**, a **comp** (one-screen mock), math — commits it to the repo, iterates as often as needed, then opens a **pull request**; the person who requires that stage's output does the **review**. Every stage should carry a **test**, because a physical artifact must be built to requirements and requirements are testable. Val's belief: an abstract and a comp **can be described in words as a specification** (colours, field widths, plot) — "everything, broken into parts, can be written as a spec." [[raw/fast-pacing-stand-up meeting-october-10-2025.md]]
- **The "shmorgasbord" list (Val's central directive).** Val wants a single **list ("shmorgasbord" — a German/Swedish smorgasbord/buffet image) of everything the framework and the data center watch and exchange** — all the values/fields/variables modules pass to each other — i.e. the menu of everything that needs a spec. First build the list (looking at what the framework and data center actually observe); then hand pieces out to people to **describe/spec each item** (he named the **Metelski + Kharetski + Leshkevich** combination as who can do it). Over ~**half a year** the list gets mostly covered "in the process of the work" — but only if it is **written down, assigned, given a due signal and a repository to commit to**; otherwise "we'll never do it." [[raw/fast-pacing-stand-up meeting-october-10-2025.md]]
- **Two concrete example tests (Val).** (1) Give **[[wiki/people/igor-metelski.md|Igor Metelski]]** — who wrote the board-code that updates credits/wins/bets — a test, using the test framework, that **verifies those calculations are correct**; a **universal** test that should run the same on any game. (2) Give **[[wiki/people/evgeny-kharetski.md|Kharetski]]** (transcribed "корецкий"/"хорватскому"/"халецкий" — the Koretski/Khorvatsky garble per §4 registry, LGS/backend context) a **game-history check**: emulate a player, add money, spin, and verify every meter shown in game history matches what actually happened. End-to-end tests can be written **without** intermediate unit tests; unit tests / technical documentation still help new developers onboard. [[raw/fast-pacing-stand-up meeting-october-10-2025.md]]
- **Where the spec lives — next to the code (segment 2).** Pavel's next step (restated in segment 2): collect the list of **all fields/variables in the current game plus the data-center variables** that can change (from settings or during play) → a **repository of small hooks/components that can be queried**, then simple tests first (does a component exist, by coordinate; catch an in-game event) building up to complex LGS↔game flows — assign tests to people and have each developer produce the **spec for the module/behavioral function they own** (each test ≈ a **use case**, and a use case is part of the spec). **Irina** would base it on the **GD/JD line by line** to capture each game's events/components/requirements, then flag what the JD critically **omits** — the unwritten cross-game behaviours (e.g. win-size "big-win/epic" thresholds; on-screen message/cents display) that live scattered elsewhere — and pull them into one place. Val turned this into an open item: **how to organize the git so the spec/doc lives together with the code and grows with it** (to be worked out with Irina). [[raw/fast-pacing-stand-up meeting-part-1-october-10-2025.md]]
