# Incom (payment processor)

Incom is the third-party **payment processor** JVL is integrating with to activate and read the Georgia **COAM prize-redemption cards** through JVL's pay-kiosk. It supplies the card-activation/balance-check API and the test/production credentials; JVL's FlexPay/FlexPort kiosk is the client. Spelling appears as "Incom" in the meeting body (and "income" for the card VIN) and "incomm" in the source filename; kept both plus "InComm" as aliases pending confirmation (see Owner Decisions). [[raw/incomm_commissioning_plan_february-27-2025.md]]

Earlier appearances: on the Feb 11 and Feb 18 embedded standups Incom was named as the payment processor supplying the **test server**, with a **production contract awaiting Val's signature** and card-provider fields to fill in the FlexPay activation sequence. See [[wiki/topics/flexpay-mobile-app-and-service-advocates.md]] and [[wiki/topics/jvl-machine-lineup.md]]. [[raw/Embedded_Group_alignment_and_update_2025-02-11.md]]

### Test vs production environments
- JVL's current credential is a **development credential** that works **only in the test environment**; testing uses a **"flight" test card**. [[raw/incomm_commissioning_plan_february-27-2025.md]]
- Path to production: JVL submits Incom's **merchant setup form** → Billy + contract admin (said to take "a couple of weeks") → Incom assigns a **unique merchant ID for JVL** (transcribed "JBL") → Incom issues a production **user ID and secret** that work only in production, using a different endpoint → JVL configures its machines with the production credential and activates a **production Georgia Core card** (not the flight test card). [[raw/incomm_commissioning_plan_february-27-2025.md]]
- Incom wants to work with JVL **in the shop** on the first machine to confirm it is configured with the production credential and can activate a production card; after that, per-install testing can be streamlined, but the technician should still send a **test transaction from the location** so Incom can verify the machine is configured correctly. [[raw/incomm_commissioning_plan_february-27-2025.md]]
- Why per-location verification matters: Incom described a kiosk operator who shipped machines misconfigured with the wrong location's store ID, so all activations came in under the wrong location and the billing was wrong — Incom only knows the store ID it is told. [[raw/incomm_commissioning_plan_february-27-2025.md]]

### Balance-check API
- Balance check is currently **out of scope** for JVL's kiosk because it can't swipe cards yet, but Incom and JVL agreed to **test and certify the balance-check API now** by feeding a **PAN number** (Incom supplies test PANs) rather than a physical swipe; the test card already carries PAN data on track one plus the Incom VIN. A number "549345" was referenced for the test. [[raw/incomm_commissioning_plan_february-27-2025.md]]
- A standard **MAG card reader** (not EMV) is sufficient for the card. Test cards can be reset with a **reversal** or a **deactivation** transaction so the same test card is reusable. [[raw/incomm_commissioning_plan_february-27-2025.md]]

### The COAM / debit-card legal state (per Incom)
- The industry read Incom gave: using a **credit card** is prohibited, using a **debit card** is unknown, and using a **debit card issued as a prize redemption** is allowed — "the state of the market today." At least two operators are already doing this; one restricts to **COAM cards** only, the other may accept any debit card. Whether a regulator (the "GLC" — Georgia Lottery Corporation) would treat a Walgreens open-loop gift card the same is unclear. [[raw/incomm_commissioning_plan_february-27-2025.md]]

## Mar 19 2025 — card dispensing/activation user-cases walkthrough (Alan)

Alan took the JVL team step-by-step through issuing a prepaid card from the kiosk ([[wiki/meetings/2025-03-19-incomm-flexpay-card-user-cases.md]]; a **Susanne** on the Incom side handed him the sample card): [[raw/incomm_flex-pay_user_cases.md]]

- **Card data:** the test cards carry identical data on the **magnetic stripe** and a **30-digit activation barcode** — first ~11 digits are the product **UPC**, the last 19 digits the **VAN (Virtual Account Number)** (track-one number beginning "605812"/"605823" — both cited on the call), printed under the barcode. Incom recommends a **barcode reader** so the card can be read **while still in the dispenser** (less mechanism, no need to dispense before reading); if magstripe-only, the UPC must be configured on the kiosk since it isn't on the stripe. The kiosk should support **UPC configuration per product** (Pavel asked to write the requirement; Alan framed it as supporting both MagStripe and barcode). [[raw/incomm_flex-pay_user_cases.md]]
- **Two-step activation:** first a **pre-authorization** (non-financial — verifies connectivity, kiosk setup, card number and loadable amount), then — after redeeming the winning ticket — an **Activate** call with near-identical fields but a new transaction ID. The card must **never be handed to the consumer before activation completes**; failed cards go to an internal **escrow bin/tray** for troubleshooting, never to the player. [[raw/incomm_flex-pay_user_cases.md]]
- **IDs and reconciliation:** requests carry access ID (test credential "ICT test," lowercase i), **merchant ID** (assigned by Incom), **store ID** (assigned by the Incom merchant so their activation reports reconcile — not invented by JVL), and **terminal ID** (JVL's own kiosk identifier); a **machine setup form** per deployment tells Incom/the merchant who and where (MLH/LLH names, address). All fields must be kiosk-configurable. [[raw/incomm_flex-pay_user_cases.md]]
- **Fees and limits:** consumer pays a **$2 fee** (e.g. redeem $22 to load $20 — only the load amount is sent to Incom); the fee is revenue-shared down the chain location→merchant→Incom (Alan's split figures were explicitly "a sample value"). Card max is **$1,000**; the minimum he needed to re-check with Adam ("either $10, $20 or $1"). [[raw/incomm_flex-pay_user_cases.md]]
- **Downstream use:** at merchant POS only the **magstripe/track-two** matters — "MasterCard does not know anything about" the VAN or barcode, which exist solely for activation between JVL and Incom; the mobile number/email capture is **optional**, only for sending Ts&Cs ("no validation code required to use the card"). A returning player's card **cannot be deducted** by the kiosk — "there is nothing you can do with that card" (whether the card could fund more play is a question Alan would take to John). Incom doesn't care how kiosks reach JVL's gateway — only the gateway talks to Incom. [[raw/incomm_flex-pay_user_cases.md]]
- The product's UPC context: the card discussed is the "**COEM card**" (as transcribed — consistent with the Georgia COAM redemption card this integration serves). [[raw/incomm_flex-pay_user_cases.md]]

## COAM gift-card solution meeting — "JVL Payment Options" (John Houseal)

The market/solution meeting Val committed to on the Apr 2 SMIB call — owner Val, "Timeline: Today, tomorrow, or Monday," purpose "Discuss market dynamics and understand operator strategies" [[raw/SMIB_FlexPay_Action_Items_April_2_2025.md]]. The substance was first captured from a derived notes document (see [[wiki/meetings/2025-04-03-incomm-coam-gift-card-solutions.md]]); the **actual Teams recording** ("JVL Payment Options," ~36 min, **John Houseal** / **Allen Lee** InComm-side, with Val and Juan) is a fuller, speaker-labelled transcript of the same meeting and confirms every point below plus the detail in the next subsection. **Date discrepancy (see Open contradictions):** the recording header dates the meeting **April 3, 2025, 5:42 PM**, while the derived notes are headed **April 7** — recorded, not resolved. **John Houseal** (the Incom lead) and Val worked the merchant problem that **gift cards can't be used to play at COAM machines**, so merchants fear losing in-store spend (feedback "from multiple operators"; use case: a $100 win loaded onto a MasterCard can't fund further COAM play). [[raw/2025-04-07-COAM_gift_card_solution_incomm_notes.md]] [[raw/incomm_transcript_gacoam_payment_options-april-4-2025.md]]

- **Three solution options (John):** (1) player asks the **clerk to swipe the card for cash** (no system changes); (2) contract a **merchant acquirer** to put card readers on kiosks/machines — rejected as unattractive: **$50–$200/month maintenance + 3% transaction fee** (a $100 transfer nets the merchant $97); (3) **barcode on the card** processed **directly with Incom** — no merchant acquirer, no 3% fee, avoids **PCI compliance** ("the barcode is not considered payment card information"), only a modest **~$20–25/month** accounting/settlement fee. [[raw/2025-04-07-COAM_gift_card_solution_incomm_notes.md]]
- **Barcode security:** protected by a **PIN set on first use** (first PIN entered becomes the card's PIN); changeable anytime via **IVR or the website**. [[raw/2025-04-07-COAM_gift_card_solution_incomm_notes.md]]
- **Role model:** location houses the machines; machine owner manages them; **JVL supplies the machines/kiosks**; **Incom is the program manager and technology provider** (gift-card product + APIs, money movement, compliance) — Incom **does not build kiosks**; operators design their own kiosk configurations (card readers, digital wallets, etc.). [[raw/2025-04-07-COAM_gift_card_solution_incomm_notes.md]]
- **Incom's expansion plans:** targeting **Texas, Florida, Pennsylvania, Nebraska and Iowa** "to improve the player experience and reduce dependence on cash," with per-market product adaptations — ATM-usable cards in Pennsylvania, large-win payouts in Nebraska — plus a **print-on-receipt** product for merchandise markets (player picks among gift-card providers). [[raw/2025-04-07-COAM_gift_card_solution_incomm_notes.md]]
- **Follow-up:** Juan + Val to "regroup and think of a proper business model" for the discussed solution. The card-scanning prospect surfaced the same day in the FlexPort scanner ruling — see [[wiki/decisions/2025-04-07-flexsmib-modern-flexport-legacy.md]]. [[raw/2025-04-07-COAM_gift_card_solution_incomm_notes.md]]

### Detail the recording adds

- **How the money actually moves:** funds sit on a gift card held in an account at **Sutton Bank** that InComm manages. When a player scans/authorises a purchase, InComm confirms the balance and the merchant gives the player play-credit *immediately*; InComm then **wires the merchant whole (~a day later)** — the merchant extends credit on the belief InComm will pay, because InComm holds the card balance. InComm must now process not just gift-card activations but **redemptions/spend**, routing money back to the **7,000 merchants** in "Co-In." [[raw/incomm_transcript_gacoam_payment_options-april-4-2025.md]]
- **PIN mechanics:** the barcode balance-check can't be done today (Jared wants PIN-based for security, since the barcode is exposed and "roommates can take photos of it"); PIN is **set on first use** (whatever four digits are first entered), one PIN per barcode, changeable via IVR or website. **Cards are not reloadable** — a player gets a **new card each cash-out**; "those are the rules until 2026." Making cards rechargeable would require **KYC** on the player, "which I don't think anybody wants to do." [[raw/incomm_transcript_gacoam_payment_options-april-4-2025.md]]
- **PCI:** option 2 (mag-stripe reader) is in PCI scope because it reads real card data (16-digit number, expiry, CVV) sent to MasterCard; option 3 (barcode) is **outside PCI scope** because the barcode "means nothing to MasterCard… only to InComm" — InComm makes it payment information only inside its own wall, insulating the industry. [[raw/incomm_transcript_gacoam_payment_options-april-4-2025.md]]
- **The four participants (Val's framing):** the **location** (houses machines), the **master** (owns/routes the machines), **JVL** (supplies machines/kiosks), and **InComm** = "the **program manager** for the gift-card product and the **technology provider** for the APIs" and money movement (all regulated in the US) — InComm **does not build equipment** ("that will not happen"). Val questioned the point of a kiosk at all; John: most people want to limit clerk interaction and keep the gaming environment self-sufficient. [[raw/incomm_transcript_gacoam_payment_options-april-4-2025.md]]
- **Operators design their own flow** — John's examples: **Excel** (owns **Bulldog Entertainment** in Georgia) puts a kiosk in every location, using TITO + a digital wallet; **Intermax at Kroger** wouldn't pay **~$15,000** per kiosk so they hung cards and put optical readers on the machines (ran into problems, now looking at kiosks); **United** (~1,300 locations) is deploying handheld devices to associates rather than $10–15k kiosks. [[raw/incomm_transcript_gacoam_payment_options-april-4-2025.md]]
- **Juan's opening framing (from the pre-recording audio):** kiosk-product rollout is slow — "maybe three to 400 with thousands to go" — and someone at the GAMOA meeting asked "how does anyone expect us to do this in one year's time"; masters/locations are "savvy… used to skating around the letter of the law," hence the gift cards; Juan's worry is that an automated kiosk lets a player walk away, whereas a window redemption keeps the location owner able to upsell. [[raw/incomm_meeting—april-3-2025-1.md]]
- **Fannin County detail:** **Pace-O-Matic** sued the sheriff's office in **Fannin County, Texas** and a judge ruled its machines were **skill machines, not gambling machines** — "the first time a court in the state of Texas has ever issued an opinion on these devices" — driving InComm's Texas interest. [[raw/incomm_transcript_gacoam_payment_options-april-4-2025.md]]

## June 23 2025 — Nebraska/Georgia alignment; SkillPay, PrizePay, the card-back-into-machine flow

A weekly alignment call ([[wiki/meetings/2025-06-23-incomm-jvl-nebraska-georgia-alignment.md]]; [[wiki/people/val-levitan.md|Val]] + [[wiki/people/pavel.md|Pavel]] with InComm's **John** (Houseal), **Alan** (= Allen Lee) and **Adam**) covering the differences between Nebraska and Georgia and the still-unfinalized products. [[raw/incomm_jvl_alignment-june-23-2025.md]]

- **Product line (as described on this call).** In **Georgia** today there is one product — the **Georgia COAM PrizePay card** (orange or black wrap; **$2 activation fee**, single-load, up to **$1,000**, **no cash access** — Georgia bars a product with direct cash access from COAM winnings). The new product is **SkillPay**: **$3 activation fee**, **has cash access**, and a **unique kiosk-only activation** (the multi-step process below). InComm chose the name "SkillPay" for Georgia because the regulator lacks "the mental bandwidth to separate the two products" from PrizePay. [[raw/incomm_jvl_alignment-june-23-2025.md]]
- **SkillPay's two-step legal process.** To give the card cash access, InComm first redeems the COAM winnings to a **compliant product**, then uses that product to **purchase** the SkillPay card — so the direct lottery payout is the *third* step, not the initial load. The player experiences **one step**; legally it is two. This is why activation must be done **by the kiosk/system**, not by "an $11-an-hour employee." It took InComm "~12 months and a quarter-million dollars in legal fees" to get regulator sign-off (they signed an off-network agreement with MasterCard; final signature still pending), and the **secondary purchase API** JVL would call for the in-between step is **not yet finalized** ("we haven't finalized the product… we're still working that out"). [[raw/incomm_jvl_alignment-june-23-2025.md]]
- **Nebraska = a cash state → the original PrizePay.** For Nebraska (different from Georgia) InComm offers the **original PrizePay product**, used in **Pennsylvania** route gaming (e.g. Circle K), loadable up to **$2,500**. Two versions: a **no-activation-fee** version (free) and one with a **$3 activation fee** (cash access). Fee model: the card is free, purchases are free, grocery **cash-back** is free (buy a $2 Coke, pull $200 free) — only an **ATM withdrawal costs $2.50**, which is how InComm makes money ("we're gambling on the fact that you're going to use the ATM"). Nebraska's largest operator (JVL's long relationship) + one other control ~**70%** of the market and today pay out via **ATMs**; InComm supports a few Nebraska locations (M3T). A win too large for an on-site ATM (jackpots $2,000–$5,000) is a stated pain point the card solves. An optional companion app can send funds to a **bank account** (like Venmo: instant 1% or free ACH in 2–3 days). [[raw/incomm_jvl_alignment-june-23-2025.md]]
- **Not reloadable.** These cards are **not reloadable**; John's read is that "nobody actually wants a reloadable card" (operators/legislators talk about it, but no player has asked) — players care most about **privacy**. [[raw/incomm_jvl_alignment-june-23-2025.md]]
- **Using the card back at the machine.** A **$40 barcode scanner** at the machine or kiosk reads the card's back barcode; the player enters a **3-digit code** (proving ownership, since people can photograph the card) to spend it back into play. Each machine used as a payment endpoint must be **registered as a terminal** with a **separate location contract** (like accepting debit today), so each machine has its own **terminal ID** — **or** a single central screen/kiosk acts as **one terminal ID** for the whole location ("take $100 off this card, send it to machine one"). The barcode and the magnetic stripe carry the **same embedded information**, so either reads for activation/dispensing. Manual activation is possible (enter the amount, scan the magstripe) via InComm's standalone **TransAct terminal** (pre-kiosk); a 30-digit manual card-number entry is error-prone, so a scan is preferred. Same InComm API either way; locations still must be registered. [[raw/incomm_jvl_alignment-june-23-2025.md]]
- **Val's cheaper alternative to a full kiosk.** Val argued Georgia operators won't spend tens of thousands modernizing to kiosks; most run **MudaGoose** (the dominant RS-485 printer-per-machine system) with a cashier-printed ticket. His cheaper path: validate the MudaGoose ticket **without TITO or hardware change** and issue a SkillPay card **at the cashier**, using a **cage dispensing unit + POS** (split the printer from the machine, connect a POS to capture the signal, add a tabletop card dispenser with a small 5–8" player-facing touchscreen for terms) — no kiosk needed. Val's business aim is to **split the $3 service charge** with InComm and earn recurring processing revenue, providing whatever hardware an operator needs. John agreed InComm "makes no money on kiosks" and isn't in the kiosk/game-card-system business ("not Access, not MudaGoose") — only financial card products + moving money — and will target whatever architecture JVL builds. [[raw/incomm_jvl_alignment-june-23-2025.md]]

## July 1–2 2025 — in-person product-strategy meeting at JVL Toronto (2 days)

A two-day in-person working meeting at JVL's Toronto office ([[wiki/meetings/2025-07-01-incomm-product-strategy-toronto.md]]; primary July 1, day 2 July 2) between [[wiki/people/val-levitan.md|Val]] (+ JVL team) and **[[wiki/people/john-houseal.md|John Houseal]]**, InComm's product-development / route-gaming lead. John's goal: understand what JVL wants to build and pair it with InComm's card products + money movement, then "chart a way for JVL." Segments carrying unique facts noted on the stub. [[raw/incomm_product_discussion-july-1-2025-1.md]]

### What InComm is (John's framing)

- **Vanilla Direct** is InComm's US cash network — ~**100,000 retail locations**, processing **3–5 transactions per second**, taking cash in at retail and routing it to banks, wallets and sportsbooks; licensed money movement negotiated with Visa/MasterCard/banks. Route gaming is a small part of InComm's business (~**2,400 employees total**, only ~**4–5 on the route-gaming program**). [[raw/incomm_product_discussion-july-1-2025-1.md]]
- **Blackhawk** is InComm's chief rival. **Fraud scale:** organized bad actors "have mastered the art of industrial scale" — one year InComm lost "very low nine figures" in gift-card fraud; a Georgia hit (via a hacked upstream player-card system) ran **$80,000 in ~10 minutes**. InComm's standard gift-card limit is **$5,000/location** (some at $10–15k). This is why InComm is nervous about hanging cards on shelves rather than issuing at the point of pairing. [[raw/incomm_product_discussion-july-1-2025-1.md]]

### The PrizePay card, the crosswalk table, and the off-network API

- The **PrizePay** card carries an **activation barcode** (C128) and a magnetic stripe (activation barcode also placed in track-one data for kiosks that only read magstripe). Historically the activation barcode only ever turned the card on. [[raw/incomm_product_discussion-july-1-2025-1.md]] [[raw/incomm_product_discussion-july-1-2025-2.md]]
- InComm is building a **"crosswalk table"** that maps the activation barcode back to the card so that — hopefully by **end of 2025** — the same barcode can be **scanned to spend value back at the machine** via a **different API call** ("take $20 off the card and use it at the machine"). This is a **~300-hour development effort** and requires a new **payment-services agreement** with the location. It gives JVL a **backup revenue stream** (if a location stops paying for activations, JVL can recover charges from spend). [[raw/incomm_product_discussion-july-1-2025-1.md]] [[raw/incomm_product_discussion-july-1-2025-2.md]]
- **Off-network transaction.** Processing off the barcode is an "off-network transaction" — InComm had to **petition MasterCard** to run it across InComm's own network (it violates their agreement to route everything over MasterCard). Because the barcode is not payment-card data, it is **outside PCI scope** and no merchant acquirer carries it. Security to spend at a machine: the player enters a **security code — the last 3 or 4 digits** of the card number (undecided) — to defeat barcode-guessing (first 8–11 barcode elements are fixed routing identifiers). A **virtual card** (to the player's phone) is possible instead of physical plastic. [[raw/incomm_product_discussion-july-1-2025-2.md]]

### The broker / merchant / terminal model (who JVL's customer is)

- **Terminal-ID model** (Toast-POS analogy): a **location = a merchant number**; each machine = a **terminal number**; machines belong to a **master operator**. Every card transaction carries terminal + merchant + transaction-type. [[raw/incomm_product_discussion-july-1-2025-2.md]]
- For **gift-card activations**, **JVL = the broker**: JVL contracts with the location/merchant, InComm contracts with JVL, the merchant pays JVL and JVL pays InComm. For **spending the card back at the machine**, a different set of financial regulations applies — **InComm must hold a direct payment-services agreement with the location**. [[raw/incomm_product_discussion-july-1-2025-2.md]]
- **Who gets paid is driven by the credential that submits the activation request** — "everything is driven by the credential that submits the activation." If a location processes on a broker's **PAX** device it goes to that broker (e.g. RWJ); if on JVL's POS, it goes to JVL. **Georgia broker ecosystem:** **RWJ** (~2,400 signed location contracts; a "PAX/A80" device makes them June-1 compliant), **Yinlo** (InComm recruited him — built RWJ's software — to become a broker), **LUNIX** (InComm's least-popular program), **IFS** and **MIMS** (see "Bob" below). Broker contracts often carry a **one-year term with exclusivity for the prepaid products provided**; JVL's strategy is to install equipment, process under the incumbent broker's credential until the contract expires, then switch to JVL. [[raw/incomm_product_discussion-july-1-2025-4.md]] [[raw/incomm_product_discussion-july-2-2025-5.md]]
- **Master vs Access.** The largest master is **United** (works largely with **Access**, a Las-Vegas player-card system — ~**$0.12/day/machine** + ~$1/player card, judged expensive; player cards rarely reused); United is also exploring Tito via Easy Links. [[raw/incomm_product_discussion-july-1-2025-4.md]]

### "Bob" — enriched context (still queued)

The unresolved American "Bob" (§4 registry — owner-deferred, NOT Gottlieb) gained substantial context here: John described **Bob** as "a competitor, a partner, and a colleague all at once… He's **MIMS operator**. He runs their payments. He started a company called **IFS** where he sells kiosks. And he's done his time in Vegas." (Earlier: "Bob's [contract] is probably the most sophisticated… that's MIMS.") So Bob is a Georgia route-gaming figure tied to MIMS and IFS with a Vegas background — **still no surname; kept queued (Tier A).** [[raw/incomm_product_discussion-july-2-2025-9.md]] [[raw/incomm_product_discussion-july-2-2025-5.md]]

### InComm's product roadmap and the Redemption Center / mini-ATM

- **John's roadmap (~4 steps):** (1) today's PrizePay card; (2) a card with **cash access** (SkillPay); (3) send the prize straight to the player's **bank account** (esp. Nebraska high winners); (4) print a **cash-pickup code** on the game receipt → collect cash at an **ATM** (deal signed **last week with NCR**, service launching end of summer 2025; player's cell number = account number). [[raw/incomm_product_discussion-july-1-2025-4.md]]
- **SkillPay:** **$3 activation charge** (verbally approved, ~8 weeks into development), expected to be an official product by **end of 2025**; the JVL↔InComm split is **not yet decided** (Val wants 50-50, floated $3.50/$5). Legal theory reaffirmed: take a valid COAM redemption instrument (the **Georgia "353" gift product**) → **buy** the SkillPay card ($3, has cash access) → then redeem to cash — a purchase must be orchestrated (auto-converting would be illegal); the card need not be physically dispensed (a digital card can convert to cash via acceptance screens). InComm cites **three external legal opinions + internal analysis** clearing it. [[raw/incomm_product_discussion-july-2-2025-5.md]] [[raw/incomm_product_discussion-july-2-2025-8.md]]
- **"Redemption Center"** — John's naming for JVL's mini-ATM: don't call it an ATM (attracts regulatory attention); call it a Redemption Center. This anchors the bill-recycler mini-ATM concept detailed on [[wiki/topics/flexpay-business-architecture-payout-devices.md]]. A **Hyosung ("Heosung") Pivot / C-store-of-the-future** unit was shown as the closest existing hardware (~21-inch slimline, 3 recycling cassettes + 1 overflow, holds 9,000 notes, ~100 notes/transaction, receipt printer + bill-bunch acceptor/dispenser + barcode scanner; list ~**$8,500**; runs "Hyosung Pay"; used with **DraftKings** at Sports & Social venues). [[raw/incomm_product_discussion-july-2-2025-7.md]]

### Non-gaming cash-in services (extra revenue for JVL's device)

- John pushed JVL to make the Redemption Center a profit centre beyond COAM: **wireless top-ups** (Boost Mobile), transit passes, **utility bill-pay**, and **cash-in to bank accounts / wallets** — all barcode-scan based via InComm's API. Economics: a deposit costs **$0 to $3.95**; **Cash App** charges users $1 and pays InComm ~$1.50; **Capital One 360** is free (add cash at CVS, up to $99/day, 5/month = $4,995/month max). InComm has "the only pipe into Cash App to add funds" but isn't approved by Cash App for gaming use. **Chime** (the "largest bank that isn't a bank") killed InComm's old GPR-card business. Money flow: player scans app barcode at the device → InComm approves → device takes cash → InComm bills JVL next day less commission. **"Zillions"** = InComm's merchandise-state product (barcode receipt → pick from ~500 gift-certificate partners; big unspent-value commissions). [[raw/incomm_product_discussion-july-2-2025-7.md]]
- **Device-ownership regulatory note:** better if **JVL owns** the Redemption Center and licenses it to the master (~$50–100/month) so the master has no financial interest in the store (a regulatory concern). [[raw/incomm_product_discussion-july-2-2025-7.md]]

### GLC / Intralot serial-masking (day 1)

Georgia Lottery / Intralot **mask JVL's cabinet serial numbers** and assign their own numbers that JVL is "purposely not allowed to know" — so JVL cannot tell where its machines are, and the numbers change on relocation; JVL sees only enabled/disabled numbers appearing and disappearing on a report. [[raw/incomm_product_discussion-july-1-2025-3.md]]

## July 10 2025 — cloud-processing recommendation; the broker processing-arm referral

On JVL's [[wiki/meetings/2025-07-10-defining-product-capabilities.md|July-10 product-capabilities meeting]], [[wiki/people/nathan-carver.md|Nathan Carver]] relayed two Incom-shaped points that reshaped JVL's architecture (full device context on [[wiki/topics/flexpay-business-architecture-payout-devices.md]]). [[raw/Defining Product Capabilities.md]]

- **Do the processing in JVL's cloud, not on-site — because Incom disables by account, not by site.** Per the Incom API docs / prior-day call, Incom identifies the JVL **identity** on an incoming gift-card request and the **site ID** identifies the requesting site — but when Incom has to disable, it disables the **entire account**, taking down **every storefront** of that customer, and it **cannot pinpoint-disable a single Flex POS**. So Incom recommended that JVL's **cloud server perform the actual gift-card activation as a pass-through** (device → JVL cloud → Incom): the field device has no direct Incom communication, giving JVL precise control over the pre-authorize → transfer-money → validate → activate sequence and site-level disable, and leaving **no Incom knowledge on the hardware** if a device is compromised/stolen. Nathan and Pavel flagged this as "a **dramatic change** in our current architecture" (all issuance comms must proxy through JVL's server); Val: "it's the right approach… I am not willing to sacrifice security." [[raw/Defining Product Capabilities.md]]
- **The broker processing-arm referral.** Val recalled that "John from Incom" had pointed JVL to companies that specialise in **processing transactions** and offer that processing to third parties — he named **RWJ, "Lunix Telecom," and "Inlaw" (spelled with a Y)** as candidates for JVL to subcontract its transaction-processing module to (rather than approaching the aggressive mainstream casino processors and risking creating a competitor). These map to the **RWJ / LUNIX / Yinlo** Georgia broker ecosystem documented in the [[#the-broker--merchant--terminal-model-who-jvls-customer-is|Jul-1/2 broker/terminal model]] above ("in law with a Y" = **Yinlo**); Juan noted Lunix's reputation for bad customer service. [[raw/Defining Product Capabilities.md]]

## Sept 3 2025 — ACH provider recommended (Dwolla/Plaid), the batch-swipe model, dispute-resolution flow, API-endpoint limits

On the [[wiki/meetings/2025-09-03-flex-capabilities-weekly-ach-dispute-pos-design.md|Sept-3 Flex Capabilities weekly]] ([[wiki/people/val-levitan.md|Val]], [[wiki/people/juan-martinez.md|Juan]], [[wiki/people/nathan-carver.md|Nathan]], [[wiki/people/pavel.md|Pavel]], [[wiki/people/genadi-peari.md|Genadi]]) the InComm money-flow became concrete — the fund-flow between JVL, InComm, and locations, and how a player/fee dispute is handled. [[raw/Flex Capabilities Weekly Update-september-3-2025.md]]

- **ACH-provider recommendation (Nathan).** Nathan (using Claude to survey providers) recommended an ACH-focused API house — transcribed "Diwala/Duwalla/Dualla," **almost certainly Dwolla** (inference from the mangled name; a real ACH API), now integrated with **Plaid** (transcribed "plate/played"; Nathan: "I believe that's the name") to give **instant bank-account balance verification** before initiating a transaction — so JVL can **abort a gift-card activation if the location lacks funds**. Pricing (vendor economics): **0.5% per transaction, $5 cap, $0.05 minimum**; volume-negotiable with vendors. Val noted **JP Morgan / banks** are the traditional ACH route; Dwolla/Stripe-type houses are ACH-focused (like Stripe). This advances the Aug-27 "provider unchosen, Stripe as example only" state toward a specific candidate. [[raw/Flex Capabilities Weekly Update-september-3-2025.md]]
- **The batch-swipe model (Val's clarification).** ACH is a **once-a-day** debit of the location's **entire day's total** (e.g. 50 tickets → $5,000 swiped as one transaction), which also **caps the fee at $5** per location per day. The service cost must be **built into JVL's contract with the location**. InComm sets up the JVL-side ACH (JVL submits its banking info; InComm swipes JVL's account at a contractual frequency); JVL should draw from locations on the same pace but a few hours **ahead of** InComm's draw on JVL. Val estimated JVL will validate **~$2 billion in transactions/year** and is targeting **~$5 million of overnight deposit** volume. [[raw/Flex Capabilities Weekly Update-september-3-2025.md]]
- **Reconciliation must be near-real-time.** Because a gaming day may close at midnight with nobody to reconcile, reconciliation is post-withdrawal; Val wants each **validated transaction to add to the location's running total in real time** (an automated notice per validated transaction) so a location can reconcile the daily debit against its constituent transactions. Val ruled this its **own meeting series** (ACH / money transfer / contractual issues), split out of the POS meetings — it also drives CMS and cloud architecture. Juan to obtain a **sample InComm invoice** (customer redacted) as a template and a **contract template** between operator and InComm's partner. [[raw/Flex Capabilities Weekly Update-september-3-2025.md]]
- **Dispute-resolution use case (Nathan), location-first.** Primary case: a player thinks their $50 ticket only loaded $45 (the ~$5 activation fee). The cashier swipes the card on Flex-POS; via the **InComm API** JVL retrieves the transaction/activity and the device **shows the player** the fee and confirmation they accepted — "McDonald's-simple," graphical, get them in and out. JVL's own audit trail (card ↔ specific Mother-Goose ticket, terms accepted) lets it reconstruct the original ticket in the extreme case. Beyond the fee, the player is directed to **InComm's phone number printed on the back of the COAM card**; the cashier can also **block a card** via the InComm API (Val: "I know for sure that they provide this"; Nathan to locate the endpoint). A scanned-ticket "valid/invalid" check can catch photocopied/other-location tickets against JVL's controlling server. [[raw/Flex Capabilities Weekly Update-september-3-2025.md]]
- **API-endpoint limitation (Pavel).** JVL has had **one** meeting with InComm; of the many API requests tried, **only three were enabled for gift cards**. The API document contains much data not applicable to JVL's card types; Pavel wants a **list of questions to InComm** to confirm which endpoints are available for JVL's card types, and expects **future card types** to unlock more (balance reads, machine transfers) not available on the current gift cards. [[raw/Flex Capabilities Weekly Update-september-3-2025.md]]
