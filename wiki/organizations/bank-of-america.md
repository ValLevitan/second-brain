# Bank of America

Bank of America is one of the banks in the JVL group. The wiki records two long-standing uses of it before 2026: **JVL Systems** runs on a separate Bank of America account, which **Ina** releases payment-by-payment (she wanted batch payments as volume grew) [[raw/Finance_Operations_Banking_Procedures-september-2-2025.md]], and the **BOFA / BOFA credit-card** general-ledger accounts were part of the US chart of accounts built for Business Central (to be replaced by the Canadian RBC accounts on the Canadian side) [[raw/finance_meeting_gl_account-may-24-2025.md]]. See also [[wiki/organizations/jvl-gameworks.md]] (the Amazon/ECHO commerce banking) and [[wiki/organizations/cibc.md]] (the newer US receiving-account structure).

**A note on where the relationship stands.** On **March 31 2026** Val told [[wiki/people/felipe-miranda.md|Felipe]] that JVL was "changing the bank from Bank of America to" a smaller, friendlier bank (the new bank was not named) and was building an API between that bank and Business Central [[raw/Meeting_Transcript_Felipe_credit_terms_sales_strategy-March-31-2026.md]] [[raw/Meeting_Notes_Felipe_Credit_Terms_Sales_Strategy-March-31-2026.md]]. In between, on **June 8 2026**, JVL met its new Bank of America banker in person to put signatures on file, ask for a credit line and building financing, and reopen CashPro (see `## History`) [[raw/Meeting_Transcript_BofA_Lenin_Hernandez_Banking_Review_and_Georgia_Financing-June-8-2026.md]]. On **August 27 2026** Val told the bank's treasury side that JVL is "tying ourselves more and more with Bank of America" (see `## History`) [[raw/Meeting_Transcript_BofA_Treasury_MS_Dynamics_Integration-August-27-2026.md]]. On **September 8 2026** JVL was running an active Bank of America treasury engagement — a pricing proposal, an implementation path, and a technical API review (below) [[raw/Meeting_Transcript_Bank_of_America_CashPro_API_Integration-September-8-2026.md]]. **What JVL asked for.** Nathan set out two goals. Short term is **reconciliation**: verifying balances and that money actually transferred, then reconciling inside JVL's own applications and Business Central — "that would be a daily API call. So, not like an end of month." Longer term is **initiating** money movement from JVL's systems: today JVL's daily ACH debits from customers run through a third party and land in JVL bank accounts, and Nathan wanted to know what it would take to use Bank of America for initiating those instead. Val added that JVL has suppliers, many in China, paid by regular wire — always in US dollars — "For some reason, everybody demands U. S." [dollars]. - **Reporting is already built.** Bank of America has prior-day and current-day balance-and-transaction APIs. The prior-day call is "generally… around seven a.m." — the ERP makes the call, pulls the prior day's balances and transactions, and matching rules inside the ERP post them. [[raw/Meeting_Transcript_Bank_of_America_CashPro_API_Integration-September-8-2026.md]]
- **Authentication.** Token-based **OAuth**, running system-to-system — "It's not the person that is making the call. You're automating that in the system. But there has to be an active Cash Pro user in place for that connection to work." The customer ID, secrets and similar values are issued during setup by the bank's API developer studio and ops team. (§15 #9 — no such values appear in the source and none are recorded here.) [[raw/Meeting_Transcript_Bank_of_America_CashPro_API_Integration-September-8-2026.md]]
- **Administrators.** A designated **primary administrator** requests sandbox access through the bank's **API developer studio**, then production access later; Connie recommends JVL designate **at least two** primary admins for CashPro. [[raw/Meeting_Transcript_Bank_of_America_CashPro_API_Integration-September-8-2026.md]]
- **The pre-CashPro "pseudo sandbox," declined.** A developer can be let in before CashPro exists, via an **IP address whitelist** and without CashPro credentials, just to see what APIs the bank offers; sandbox access must then be requested again once CashPro is live. ### The constraint that shapes the architecture: no ACH-debit API

"At this time, Bank of America does not have an API for ACH debits." Debiting customers must therefore be done **file-based** — a **NACHA** file either transmitted over a **secure SFTP** connection or manually uploaded into **CashPro Online** — with an approval step before the bank sends the instructions downstream. Connie noted that Microsoft Dynamics Business Central can produce that NACHA file, and that if JVL already produces a NACHA file for its current third-party provider, the same file could be sent to Bank of America instead. Credits are different: there **is** an ACH crediting API (to people or companies) and an API for **international wire transfers**. [[raw/Meeting_Transcript_Bank_of_America_CashPro_API_Integration-September-8-2026.md]]

- **The hybrid pattern Connie recommended.** "I have a lot of clients do… that same hybrid scenario. They take advantage of the… APIs that are out there for reporting, but then… if there's limitations, then they do the file for payments." Other clients choose the file for everything simply to keep payments consistent. [[raw/Meeting_Transcript_Bank_of_America_CashPro_API_Integration-September-8-2026.md]]
- **You cannot mix a file in with an API status out.** "You can't do a file and get an API status." Send a file and you get a file status back, or alerts, reports and statements inside CashPro; send by API and you get status APIs and webhooks. [[raw/Meeting_Transcript_Bank_of_America_CashPro_API_Integration-September-8-2026.md]]
- **Remittance detail favours the file.** API credits carry **no addenda at all** — nothing telling the recipient why they were paid, no invoice number; the recipient is expected to know, or to be emailed separately. A NACHA file carries up to **80 characters** of addenda on "a TBD plus or a CCD plus" (CCD+ is clear; the first term is garbled in the transcript — the meeting notes guess PPD+, which the transcript does not say), or up to **9,999 characters** on a **CTX** file. [[raw/Meeting_Transcript_Bank_of_America_CashPro_API_Integration-September-8-2026.md]]
- **Lead times.** ACH is **next-day availability** as standard; a two-day or one-day lead can be set instead. **Same-day** ACH is possible if the file reaches the bank before "I want to say it's like two thirty Eastern time. Don't quote me on that" — Connie's own caveat, recorded as she gave it. ACH is a **US-only** rail. [[raw/Meeting_Transcript_Bank_of_America_CashPro_API_Integration-September-8-2026.md]]
- **Returns, NSF and rejects are mostly visual, not machine-readable.** On a returned debit (an NSF, say) Bank of America sends a returns notification, but "that again is more of a visual in cash pro, like in a PDF or a text format." File acknowledgements show "up to twenty rejects and the reason line," again "more of a visual than a parsing back into your system." Connie thinks a **NACHA-format return** may also be available to parse back into the ERP and will confirm. [[raw/Meeting_Transcript_Bank_of_America_CashPro_API_Integration-September-8-2026.md]]
- **File-upload testing is a different track.** Testing a transmitted file is **UAT** work with the bank's implementation team, not the developer-studio sandbox; a manually-uploaded file can simply be uploaded. Nathan said JVL would want an exploration phase first — "just understanding how that would work and if it works within our current systems." [[raw/Meeting_Transcript_Bank_of_America_CashPro_API_Integration-September-8-2026.md]]
