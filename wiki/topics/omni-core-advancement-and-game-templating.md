# Omni core advancement and game templating (DevOps container approach)

How JVL will structure repositories, versioning and pipelines so the Omni-era core technology advances continuously while game productions peel off frozen, tested snapshots. Worked out on a Miro board across two sessions (Mon **Mar 24 2025** and its next-day continuation, **Mar 25** — dates inferred; see the stubs [[wiki/meetings/2025-03-24-devops-container-approach-omni.md]] and [[wiki/meetings/2025-03-25-devops-container-approach-omni-continuation.md]]) between Val, [[wiki/people/aaron.md|Aaron]], [[wiki/people/anton-leshkevich.md|Anton Leshkevich]] (translating) and [[wiki/people/alexander-biratka.md|Alexander Biratka]] (Sasha). Builds on [[wiki/topics/continuous-delivery-pipeline-architecture.md]] and the graphics-side workflow ([[wiki/topics/graphics-team-git-workflow.md]]). [[raw/devops_container_approach_for_omni.md]] [[raw/devops_container_approach_for_omni_3.md]]

## The structure: yellow, red, and game lines

The Miro model that emerged (colors as drawn on the board): [[raw/devops_container_approach_for_omni.md]]

- **"Gold/yellow" lines = the source repositories**, each advancing on its own versioning path: LGS, framework, game mechanics, SAS, sound library, Linux, firmware/hardware libraries, jurisdiction requirement sets (Class 3 / Class 2 / HHR). Val: "these passages to have unique… versioning path for SAS separately… for game mechanics separately… for framework advancement separately… for LGS separately… and pull them in together only here." [[raw/devops_container_approach_for_omni.md]]
- **"Red" dots = gameplay-style templates** — assemblies of framework + DC + game mechanics you can always peel a game production from. Debated hard (Aaron warned each unique assemblage needs its own tests); the Russian continuation converged on **few templates by delivery type** — Alexander/Anton: an online template, a land-based template, and genuinely different styles like bingo/roulette, rather than dozens ("Лучше один шаблон, который содержит все… чем десятки шаблонов"). [[raw/devops_container_approach_for_omni.md]]
- Anton's technical correction: **there is no framework release artifact at all** — "our framework is a give [git — ASR slip] repository, which we use as a submodule"; versions are **git tags** on the master branch after tests pass ("this is framework version 1.2.3"). Alexander's parallel statement: "there is no point in releasing the framework because we don't need it as a product." A "core advancement" point is a **manifest of tags** — "a snapshot of things at that point in time" (Aaron) — reproducible later by checking out those tags. [[raw/devops_container_approach_for_omni_3.md]] [[raw/devops_container_approach_for_omni.md]]
- New game creation: **scripts create a new repository from the framework template** ("create repository from this framework") — the framework as a "Swiss knife" from which a game picks only the tools it needs; Alexander prefers a per-game repository over one repo of all games. A template may reduce to a **configuration file** (a JS config, like the V1000 framework's XML approach) that tells the framework how to assemble a given game. [[raw/devops_container_approach_for_omni.md]] [[raw/devops_container_approach_for_omni_3.md]]

## The rules of the road

- **Frozen capabilities for production** — see the decision [[wiki/decisions/2025-03-24-freeze-core-capabilities-before-game-production.md]]. A game in production cannot request engine changes; new capabilities land in core advancement and are picked up by the *next* game (or pulled in early, at known integration cost, if a production just started). [[raw/devops_container_approach_for_omni.md]]
- Aaron's image: "we're developing a **printing press for games**" — typeset the libraries once, then print many games; the flow is forward-only, and getting game-production code back into the core repos is deliberately hard (a bundle can go back only via a pull request into the main line). [[raw/devops_container_approach_for_omni_3.md]] [[raw/devops_container_approach_for_omni.md]]
- **Nobody commits to main** (Aaron: "I am never letting an engineer commit anything to main ever. It's like sacred"); engineering feature branches merge back only when all tests pass; the gameplay-template branch "has to be working all the time." [[raw/devops_container_approach_for_omni.md]]
- **CI/CD on every commit:** any commit to a source repo triggers the pipeline builders (parallel land-based and online tracks), assembling and running the full test battery; only when tests pass does the collection get its tag. The assembled "engine master" is "really just a testing artifact." A cloned game production carries the pipeline and tests with it and keeps testing until the game is done. [[raw/devops_container_approach_for_omni_3.md]]
- **Rebasing:** a production team can rebase onto newer core tags if the changes aren't breaking; breaking changes require deliberate accommodation work and are riskier the further a production has progressed. [[raw/devops_container_approach_for_omni_3.md]]

Graphic designers "want to sell us this magic, but there is nothing magical happening there." [[raw/devops_container_approach_for_omni_3.md]]

## Designer asset flow and the resource validation tool

- The artist pipeline (presented by Anton from the art board): artists assemble assets with their tools, use a JVL tool to insert/update scenes in the game repo, validate locally, run the game locally, commit to a **feature branch** (branch per feature, kept open as short as possible), and a CI/CD commit-triggered pipeline builds (e.g. a Docker image) and deploys for browser check. Formal approval of merges by **Lena or Michael** was debated and left unresolved (Aaron: require it and "they will freak out… it's too much responsibility"; don't, and there's no control — "So which is it?"). [[raw/devops_container_approach_for_omni.md]]
- The proposed **"JVL Resource Management" tool got renamed a "resource validation tool"** (Val: management implies GUI depth; "здесь просто resource validation… да-нет, да-нет"): its job is to let a designer validate an exported scene **locally, on their machine** (e.g. a missing balance field would crash the game) before committing — instead of waiting for the pipeline validator email. It can start as a command-line tool. [[raw/devops_container_approach_for_omni.md]]
- Alexander already built a **browser previewer** on OmniFramework ("создано как отдельная игра, просто она работает как превьюшка") — load an exported animation/scene, view, scale, toggle fields; already pushed to a repository, offered to Anton to look at. Visual checks also catch exporter breakage (Unity→Pixi) that structural validation misses. [[raw/devops_container_approach_for_omni.md]]
- Validation gaps named: **sound assets** are never validated today (IDs present, possibly length); land-based resource updates are not just file swaps — XML configs must be edited, which is what **Irina Makarych** does today, and no spec exists for the file organization. Val's requirements plan: take the most advanced game and **reverse-engineer it into requirements** (he told [[wiki/people/jason-qa-consultant.md|Jason]] this is the next stage) — turn its variables into "atomic binary requirements" that the validation tool enforces. [[raw/devops_container_approach_for_omni.md]]
- Ultimate goal (Anton): one button → an ISO image ready to install on a machine; too slow as a single operation (~2 hours), so small per-product iterations with a manifest file of repos+tags so a product can always be rebuilt at a point in time — avoiding the npm-style "залил новую версию библиотеки и у нас все нафиг сломалось" breakage of the online past. [[raw/devops_container_approach_for_omni.md]]

## The product re-carve — origin of the six-product structure (Apr 7 2025)

The product/repo carve-up the Apr 15–17 dailies below execute originated on an **Apr 7** meeting (Val, [[wiki/people/alexander-biratka.md|Sasha]], [[wiki/people/pavel.md|Pasha]], [[wiki/people/andrey-bosik.md|Andrei]] — [[wiki/meetings/2025-04-07-github-jira-reshuffle-products.md]]) that started from **git-submodule** merge pain (Omni-Core as a shared submodule inside Omni-LandBase/Omni-Online). The realisation — "we are confused between beauty and the fundamental truth" — was that "Gaming Platform" had been over-stretched to swallow LGS, RGS and an HHR overlay that are really separate products. Resolution: keep the **Gaming Platform (IP481)** initiative but re-carve into **six product-repos — OmniCore, OmniLandBaseFramework, OmniOnlineFramework, LGS, RGS, OmniMath** — each a repository, released (almost) independently; the machine's shipped software is a "package" assembled from them (Linux, games, LGS, libraries, hardware layer, math, framework). Full ruling + the deferred submodule/monorepo question: [[wiki/decisions/2025-04-07-recarve-gaming-platform-into-six-product-repos.md]]. [[raw/github_jira_reshuffling_products-april-7-2025.md]]

**Naming execution (Apr 8):** the follow-up working session ([[wiki/meetings/2025-04-08-github-jira-product-repo-naming.md]]) went product-by-product in Jira Plans to make every product name match its GitHub repo exactly, and refined the carve: Omni-prefix everything, **Omni LGS Setup Screen kept as a separate product** (different language/developers, versioned independently), **Miranda Asset Tools folded into OmniCore** (only an asset-loader module, not a product), **HHR became "Omni HHR Land Based Overlay"** (standalone app, regulator-recommended isolation, version-pinned artifact), and **Vivien** gets its own repo. Full rulings + the GitHub-org-vs-value-stream open question on [[wiki/decisions/2025-04-07-recarve-gaming-platform-into-six-product-repos.md]]. ## Aug 28 2025 — Omni animation architecture (Biratka, recorded for a spec)

On a call [[wiki/people/anton-leshkevich.md|Anton Leshkevich]] recorded expressly **to generate a technical specification** (the Aug-26/27 "record the conversation, AI drafts the spec" method — see [[wiki/decisions/2025-04-03-jira-capability-level-and-github-mapping.md]]), [[wiki/people/alexander-biratka.md|Alexander Biratka]] walked through how animation works in the Omni framework. [[wiki/meetings/2025-08-28-omni-animation-architecture-biratka.md]] [[raw/Anton_Liashkevich_Alexander_Biratko_about_OMNI-august-28-2025.md]]

- **Two animation types are used in the current game: Spine and video.** A third — **Unity native animations** — exists via a converter but runs slower than Spine, wasn't needed in the current game, and Biratka expects to drop it soon. Video plays through the browser; the Pixi engine has a video loader that turns each video frame into a texture fed to a sprite, so the sprite's source is the running video. [[raw/Anton_Liashkevich_Alexander_Biratko_about_OMNI-august-28-2025.md]]
- **The Unity→JSON scene exporter.** Designers build scenes in Unity; an added Unity script walks the scene's components and emits a **JSON file** in a JVL-defined format, which the Pixi-side engine parses and converts the (formerly Unity) objects into graphics (Spine, etc.). Custom element types can be declared on the Unity side with no Unity implementation — e.g. a **`spinner`** element: the designer just marks an object as a spinner, and the JVL engine, on import, sees the `spinner` type, builds it a container, fills it with number textures, and can spin it. [[raw/Anton_Liashkevich_Alexander_Biratko_about_OMNI-august-28-2025.md]]
- **Both Spine and video animations implement a common clip interface** (start / stop / pause methods). [[raw/Anton_Liashkevich_Alexander_Biratko_about_OMNI-august-28-2025.md]]
- **Animation controllers = a state machine.** Unity exports an **animation controller** as its own JSON format (variables, states, transitions); the JVL engine loads it and can be told to set a variable/state, and the machine transitions with the designers' timings. On completion a transition fires an **event** the code can subscribe to, so code can react when a state finishes. Biratka called the current implementation "workable, not very elegant" — the code deliberately doesn't know about the individual elements the controller drives (e.g. a background controller runs its own video + sprites independently), which is a plus for running several parallel animations. A separate class of purely **programmatic** ("chistoreal") animations also exists, unrelated to the shared animation types. [[raw/Anton_Liashkevich_Alexander_Biratko_about_OMNI-august-28-2025.md]]

### The resulting spec — "OMNI Animation System — Technical Specification" (written artifact, from the Aug-28 call)

The Aug-28 recording produced a written technical specification (§3 non-transcript artifact — the spec generated by the "AI drafts the spec from the recorded conversation" method; **not** a separate meeting). It codifies the same architecture Biratka described, with a few added specifics: [[raw/OMNI Animation System - Technical Specification.md]]

- **Pipeline:** a **Unity→web export pipeline** — a custom Unity exporter converts scenes/animations to a JVL **JSON** format; a **PIXI.js** engine (web renderer) interprets and plays them; an animation-controller state machine manages transitions; format converters bridge Unity↔web. Export steps: scene analysis → component mapping → asset bundling → JSON generation → validation. [[raw/OMNI Animation System - Technical Specification.md]]
- **Three animation types:** **Spine** (created in the Spine tool, imported to Unity, rendered via the **PIXI Spine plugin**; recommended/high-performance for characters); **Video** (MP4/WebM; each frame becomes a texture on a sprite; higher memory/bandwidth); and **Unity native** (bezier-curve property animations) — **deprecated / being phased out** in favour of Spine (slower, legacy support only). [[raw/OMNI Animation System - Technical Specification.md]]
- **Custom elements** not native to Unity are supported — **spinner** elements (rotating UI), custom containers, interactive elements (button/hover states). [[raw/OMNI Animation System - Technical Specification.md]]
- **Animation controller:** a finite state machine with **boolean/string/float** variables, condition-based transitions, parallel animations per state, and an **event system** (callbacks on state change / transition completion), all configurable through the Unity interface. All animation types implement a common interface (start/stop/pause/resume/time-control/duration). [[raw/OMNI Animation System - Technical Specification.md]]
- **Dependencies stated:** Unity side — **Unity Editor 2020.3+**, custom export scripts, Spine Unity Plugin; web side — **PIXI.js** (latest stable), PIXI Spine plugin, a modern browser with video support, **WebGL** required. Roadmap: optimize the controller, better events, enhanced Unity-editor integration, docs, and migration tools from Unity-native → Spine. [[raw/OMNI Animation System - Technical Specification.md]]

(Speaker labels in the source are sparse — only Efim's reply-blocks are marked — so several individual lines are of **unclear** attribution and are not force-assigned; the two clearly-anchored positions are given below.) [[raw/debate_with_Efim-March-26-2026.md]]

- **The two positions.** Val (the non-engineer voice — "to a non-engineer like myself this is very telling… like a conspiracy novel"; also the one who "was very efficient developing personas with Claude MPC using Cline in Visual Studio Code") argued from his **design-standards initiative**: *each language carries its own programming standards, and "each programming standard must coexist with the next" under one roof, so more languages = more standards = more incompatibility to manage* — the concern anchored to **unattended-machine reliability** ("a machine that breaks down in an unattended location is WORTHLESS"). The opposing position (the architect voice in the debate): *once the system is broken into modules that talk over well-defined, language-agnostic interfaces, the units are "black boxes to each other… all they know is how to send JSON messages," so the implementation language per module is "not relevant at all" — and using the best-fitting language per part is an advantage.* They ended "further apart" and unresolved. [[raw/debate_with_Efim-March-26-2026.md]]
- **The C++ Math Engine facts (stated in the debate).** The OMNI **Math Engine is written in C++**, is the **same math engine used for RAGE and the RGS**, and is roughly **50,000 lines of code**. C++ was chosen ~10 years ago (over Java, "supposed to be faster, but this isn't critical"); path dependency keeps it there. The concession reached: the Math Engine **does not have to be C++** — Java or Rust "could be a better choice if we do it from scratch" — but having it in C++ while LGS is in Java is **not** an architecture problem on its own ("a clear no"). It should be a language with solid type-checking and OOP; "wouldn't touch Python for it." [[raw/debate_with_Efim-March-26-2026.md]]
- **RAGE vs OMNI module topology (stated in the debate).** In **RAGE** the **Math Engine talks to the Framework directly**, while **Framework↔DC** and **DC↔Setup** communicate over **HTTP** (the DC is **Java**, not JavaScript — a correction of the freeze analysis's assumption); Setup has some callbacks to Framework to play sound. In **OMNI** the modules (Game/Framework, LGS, Setup, Math Engine, Progressive Controller) are agreed to sit in independent compartments (dockers) communicating via well-defined HTTP/JSON interfaces — Val liked this model but held it "has nothing to do" with his standards-clash point. If a system were designed cleanly from scratch it could have used only **3 languages** (C for drivers, JS for framework/games/LGS, Java for math) instead of the current spread. [[raw/debate_with_Efim-March-26-2026.md]]
- **The Georgia-freeze thread (the debate's reliability anchor).** An AI-generated analysis interleaved in the document diagnoses the Georgia "overnight freeze" as a **blocking socket/HTTP call with no timeout** (the C++ Framework hangs forever waiting on a DC that has stopped responding, with no heartbeat/monitor to notice). It argues the fix is a **contract at the module boundary** — explicit connection/response timeouts and defined retry/recovery — rather than a language change, and notes the watchdog is "suspenders" while design standards are the "belt" (Val's framing that "watchdog and design standards" should not be conflated: belt-and-suspenders = safety). The debate answer on why timeouts were absent: the assumption was that if the DC is down the machine can't proceed anyway and the framework watchdog would reboot. This is the same freeze the same-day [[wiki/meetings/2026-03-26-initiative-priority-schedule.md|Initiative Priority Schedule]] meeting scheduled the concrete kernel/watchdog fix for. The C/C++ migration splits into two projects: **math → Rust ([[wiki/people/efim-podvoiski.md|Efim]])** and **HAL → Rust (Anton, the engineering Anton — [[wiki/people/anton-leshkevich.md|Leshkevich]] by context)**; Val says both agreed (he describes them as having "signed on"). **Java stays for LGS** (the game server) because TypeScript can't drive native device interactions and rewriting LGS in Rust would be too large a project — and Biratka noted Java has strong AI-tooling support thanks to its strict typing. Val flagged **OMNI 2 as confidential** — not to be discussed with the wider team yet ("it will cause a whole panic"). [[raw/Meeting_Transcript_OMNI_Architecture_Biratko-March-30-2026.md]] [[raw/Meeting_Notes_OMNI_Architecture_Biratko-March-30-2026.md]]
- **Containerization.** The math module already runs in a container (it originated from a Julia container they realized could run directly on target). Val wants to extend this to **games for QA benefit**: games are TypeScript-in-a-browser and already platform-independent, but a Docker image lets QA test a production-like build without assembling a full machine — enabling **parallel testing while development continues**. Biratka called the work "small" and offered two paths (a decoupled game server in a container, or auto-mounting the Docker container as a filesystem directory LGS reads directly — to be discussed with [[wiki/people/pavel.md|Pasha]]). [[raw/Meeting_Transcript_OMNI_Architecture_Biratko-March-30-2026.md]] [[raw/Meeting_Notes_OMNI_Architecture_Biratko-March-30-2026.md]]
- **Peripheral-abstraction protocol + hardware-free automated testing (ADR direction).** Val proposed a **standard communication protocol** for all peripherals — each device connecting through a protocol layer instead of native libraries — so peripherals can be emulated/containerized and regression tested without physical hardware. His stated pain: shipping devices to Belarus routes through China, costs ~**$600 in taxes per shipment**, and takes ~**1–1.5 months**. The one hard concern is the **iBoard**: it uses a high-speed USB-connected memory chip (chosen by [[wiki/people/dima-pikulev.md|Dima Pikulev]] for speed) that must persist game/bet state the instant a player presses Spin, so a protocol layer's latency (Biratka's rough estimate ~10ms) could risk state loss on power-cut — Biratka wasn't certain and suggested experimenting. For all other peripherals (printers, validators, bill dispensers, buttons) speed is irrelevant. New-device adaptation would take longer under the abstraction (Val floated ~4 months vs ~1), which Val judged worth the long-term testing gain. The iBoard chip point is the same one confirmed the same day in [[wiki/meetings/2026-03-30-genadi-omni-board-communication.md|the Genadi board-communication call]]. ## Mar 30 2026 — machine-freeze bug: root cause + fix rollout (customer-facing)

On the [[wiki/meetings/2026-03-30-black-horse-invoice-payment-review.md|Black Horse invoice review (Part 2)]] Val gave Felipe the diagnosis and rollout plan for the machine-freezing defect — the customer-facing confirmation of the same freeze the Mar-26 debate ([[wiki/topics/omni-core-advancement-and-game-templating.md|Georgia overnight-freeze thread]] above) and the Mar-26 initiative-priority schedule had scheduled a kernel/watchdog fix for. The cause: **Linux kernel 4.5** does not work well with a particular microprocessor — it freezes the processor **and disables the processor's internal watchdog timer**, so the machine cannot even reset itself. Fix = implement the **new Linux kernel** Linux issued for the issue, plus a **second (added) hardware watchdog timer** that revives a machine that has gone fully dead. Val can reproduce the freeze on demand in Minsk (so the test doesn't worry him); [[wiki/people/pavel.md|Pavel]] is testing; Val will have Eclipse approve within a day or two (he'll show them exactly which software container the fix lands in); available in ~2 weeks. Every affected customer will be compensated case-by-case. Val's framing for the market: the fix is **"a source of pride, not shame"** — finding a kernel-level bug proves engineering depth. [[raw/Meeting_Transcript_Black_Horse_invoice_payment_review-2-March-30-2026.md]]
