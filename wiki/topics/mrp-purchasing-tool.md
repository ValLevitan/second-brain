# MRP purchasing-planning tool (Nathan Carver's MSBC purchasing tool)

The **MRP tool** ("material requirements planning" / purchasing-planning tool) is a purchasing-decision helper [[wiki/people/nathan-carver.md|Nathan Carver]] is building for [[wiki/people/mikhail-perelman.md|Mikhail Perelman]] (Misha), JVL's procurement manager. It connects to **Microsoft Business Central (MSBC)** through the BC API, takes **plain-language commands** (an item number and a quantity), reads what BC knows, works out what's short, and recommends what to buy — a talk-to-it dashboard/report that replaces the old Excel purchasing sheet Misha used to run. This page is the dedicated home for the *tool* itself; the broader BC/ERP context sits on [[wiki/topics/business-central-erp-implementation.md]]. [[raw/Meeting_Notes_MRP_Dashboard_Demo-June-10-2026.md]]

## What it is (architecture)

- **Built on the MSBC API.** The tool reaches into Business Central directly rather than pulling data out to Excel and pushing it back. [[wiki/people/val-levitan.md|Val]]'s rule throughout: MSBC is the single source of truth for vendors, prices, inventory and purchase orders — no Excel master file. [[raw/Meeting_Notes_MRP_Dashboard_Demo-June-10-2026.md]]
- **Plain-language / agentic interface.** You give it an item number and a quantity in ordinary language; it reads BC, sees what is on hand, computes the shortage, and recommends a purchase-order quantity. It is close to being able to **create the purchase order directly in MSBC**. [[raw/Meeting_Notes_MRP_Dashboard_Demo-June-10-2026.md]]
- **No data store of its own — it is an MCP server.** Because the tool holds no database, everything stays in MSBC, which is exactly the single-source-of-truth setup Val wants. This is the same **BC-API MCP layer** the material-requirements work rode on from May-11/May-21 (see [[wiki/topics/business-central-erp-implementation.md]]). [[raw/Meeting_Notes_MRP_Dashboard_Demo-June-10-2026.md]]
- **Dashboard first, Excel later.** Misha originally asked for the old Excel tool he was used to; Val directed Nathan to build the plain-language dashboard first and treat Excel only as a later view-only export. [[raw/Meeting_Notes_MRP_Excel_Workbook_Refinement-June-1-2026.md]] [[raw/Meeting_Notes_MRP_Dashboard_Demo-June-10-2026.md]]

## What it computes

- **Shortages and recommended POs** — for a planned quantity of an item, what is on hand, what is short, and how much to order. [[raw/Meeting_Notes_MRP_Dashboard_Demo-June-10-2026.md]]
- **Multi-level BOM explosion** — it must drill every bill of material all the way down to the **purchasable items**, not stop at an intermediate sub-assembly that shows stock on hand. In the demo a 5-level sub-assembly came back too short because the tool treated "buttons and counters" as a finished part; the fix is to keep exploding down to purchasable parts (Nathan to set it up to ~20 levels deep, though nothing at JVL goes near that — ~5 max). [[raw/Meeting_Notes_MRP_Dashboard_Demo-June-10-2026.md]]
- **Explode-or-not is driven by the MSBC purchase/assembly flag (June-12 resolution — not a bug).** The June-10 "it stopped exploding" behavior was traced to a Business Central flag: an item marked **"purchase"** is treated as one bought part and is **not** exploded; an item marked **"assembly"** is exploded into its sub-parts. So the flag works as intended. On June 12 Nathan's agent exploded the test component into ~120 purchasable parts grouped by category (cabinet, sheet metal, plastics, electronics, power, display, audio); Lev confirmed the data was correct. The one odd case — an assembly flagged as a purchase — was a historical part Misha explained: because electronics had long lead times, JVL bought the components early, shipped them to the vendor at **zero price**, and received the finished board back, so that bought-whole item still carries a BOM. The ~120 parts came back with **no vendors attached** — the same vendor/pricing gap from June 10, still open. [[raw/Meeting_Notes_MRP_Purchasing_Workflow_RFQ-June-12-2026.md]]
- **Vendor pricing (program economics).** To recommend *who* to buy from and *at what cost*, the tool needs vendor names and unit prices in MSBC. In the demo, planning 10,000 units of a test item, it found the shortage but had no vendor or unit price. Vendors *are* loaded in MSBC; **pricing is missing** — roughly 800–1,000 items still need vendor prices. Some prices exist in the old **Navision** system and can be exported but need validating (nobody knows which are still current); the rest must be keyed by hand, and some items carry tiered pricing (samples, 100/300/500 units), so it is not one clean list. Once real POs are placed, their prices become history the tool can use to estimate future costs. [[raw/Meeting_Notes_MRP_Dashboard_Demo-June-10-2026.md]] [[raw/Meeting_Notes_MSBC_MRP_Report_Vendor_Pricing-June-10-2026.md]]
- **Core report columns now, more later.** The demo showed only the core columns; even that already helps with inventory (a current pain point). More columns can be added on request cheaply; computed columns — payables and Misha's PO-status/comment fields — are deferred to a later phase. The bigger value comes when Nathan builds the BOM breakdown to the lowest level. [[raw/Meeting_Notes_MSBC_MRP_Report_Vendor_Pricing-June-10-2026.md]]

## The purchasing workflow and RFQ handling (June 12 2026)

On the June-12 follow-up Val laid out the full purchasing cycle he wants the tool to run, and the room agreed it is the right one: **Shortages → editorial review → RFQ → reply/negotiation → purchase order.** [[raw/Meeting_Notes_MRP_Purchasing_Workflow_RFQ-June-12-2026.md]]

1. **Say how many machines/items to build**; the agent pulls the shortages (needed vs on-hand and on-order). [[raw/Meeting_Notes_MRP_Purchasing_Workflow_RFQ-June-12-2026.md]]
2. **An editorial screen where Misha (Procurement) keeps the judgment calls** — change quantities, pick vendors, drop or add items. Val's point: Misha already does exactly this by hand (he calls his own draft PO an "RFQ"), so the steps are fixed and reproducible and can be automated, but the decisions stay with Misha, routed through the editorial screen rather than a separate manual process. [[raw/Meeting_Notes_MRP_Purchasing_Workflow_RFQ-June-12-2026.md]]
3. **The agent sends an RFQ (Request for Quotation) to each vendor** rather than going straight to a purchase order. Across sub-assemblies it consolidates the same part, totals by vendor, and combines parts under a set dollar value into one order; each RFQ shows the last price, the new quantity, and a DDP line. [[raw/Meeting_Notes_MRP_Purchasing_Workflow_RFQ-June-12-2026.md]]
4. **Vendor replies land in Outlook and the agent reads them and fills the editorial screen automatically.** Val demoed the auto-ingest live using his own travel email — the agent pulled flight and hotel confirmations from Outlook via the MS365 connection on its own — to show the same works for vendor quotes. [[raw/Meeting_Notes_MRP_Purchasing_Workflow_RFQ-June-12-2026.md]]
5. **DDP (Delivered Duty Paid — freight + duty + taxes) is captured as a single line** added after the vendor quote, not modeled per part. [[raw/Meeting_Notes_MRP_Purchasing_Workflow_RFQ-June-12-2026.md]]
6. **On approval the agent generates the purchase order**, which goes for approval and is emailed to the vendor. [[raw/Meeting_Notes_MRP_Purchasing_Workflow_RFQ-June-12-2026.md]]

Misha pushed back that too much data is missing today and that quantity decisions involve judgment (minimum order quantity, price breaks at 15/20/100/300/500 pieces, parts shared across products, family molds, choosing among vendors); he stayed skeptical that full PO automation is feasible yet. Val agreed the judgment stays with Misha but goes through the editorial screen, and both agreed to build it step by step and test as they go. Val directed Nathan to **break the workflow into Jira features with estimates** before building, and — since JVL runs a **physical inventory count in Georgia the week of June 15** and shortages are only as good as the on-hand count — told Nathan **not to hold for the count; keep building in parallel.** [[raw/Meeting_Notes_MRP_Purchasing_Workflow_RFQ-June-12-2026.md]]

## Create-PO agent (June 25 2026)

On the [[wiki/meetings/2026-06-25-mrp-create-po-agent-demo.md|June-25 demo]] (Val, Nathan, Lev, Misha) Nathan showed the tool now **creating purchase orders directly in Business Central** — the next step past the June-12 RFQ design. You give it a **top-level assembly and a quantity** (his example: 500 units); the agent explodes the BOM, computes the shortage net of on-hand stock and open POs, identifies the vendors, and **drafts the POs in BC** (he created two draft POs, including one numbered #303, for Lev to inspect). [[raw/Meeting_Notes_MRP_Create_PO_Agent_Demo-June-25-2026.md]]

- **The vendor-data gap, quantified.** Of the **32 component parts** in the test assembly, only **9 had vendor information configured in BC** and could be processed into POs immediately; the other **23 had no vendor item data** — still the main blocker (the same missing-vendor/pricing gap open since June 10). To close it, Nathan is to **load the vendor item catalog spreadsheet into the MSBC dev environment** so a full PO run can be tested. [[raw/Meeting_Notes_MRP_Create_PO_Agent_Demo-June-25-2026.md]]
- **Per-part vendor cost comparison.** Where two vendors are eligible for the same part, the agent **presents a cost comparison and lets the user choose** rather than picking one silently. [[raw/Meeting_Notes_MRP_Create_PO_Agent_Demo-June-25-2026.md]]
- **Missing PO fields — requested receipt date.** Lev flagged that the **"requested receipt date"** field (needed on every PO) is not currently populated by the agent; Nathan agreed to add it as an **interactive prompt** when the agent creates a PO. What other PO fields the agent must fill is still to be determined once Lev reviews the draft POs in the dev environment. [[raw/Meeting_Notes_MRP_Create_PO_Agent_Demo-June-25-2026.md]]
- **Multi-currency by vendor.** Misha confirmed some parts are bought in **Canadian dollars, not only USD**, so the agent must handle **multi-currency per vendor** when drafting POs. [[raw/Meeting_Notes_MRP_Create_PO_Agent_Demo-June-25-2026.md]]
- **No file-based batch input — Val's veto (reaffirmed).** Lev and Misha floated feeding the agent a **file of many part numbers and quantities** instead of entering them one at a time. Val pushed back firmly: a file intermediate **recreates the old Excel workflow he is trying to eliminate**. His position — users interact with the agent **conversationally**, applying the same logic they would in Excel (sort by vendor, add non-shorted parts) but spoken directly to the agent. The root fix is complete vendor data in BC, not a fallback to Excel. (Val took this data-discipline argument into the immediately-following [[wiki/meetings/2026-06-25-bc-single-source-of-truth.md|6:11 PM single-source-of-truth session]] — see [[wiki/topics/business-central-erp-implementation.md]].) [[raw/Meeting_Notes_MRP_Create_PO_Agent_Demo-June-25-2026.md]]
- **Screen-share failure (logistics).** Nathan's Teams screen share did not display for Val (a recurring issue); a switch to Google Meet failed for Misha. Val asked Nathan to keep working and moved the discussion to the separate Russian follow-up (the 6:11 PM session). **§15.8:** clear — MRP/PO/vendor/currency/tooling economics only, no named-person compensation. ## Full-loop demo (July 2 2026)

On the [[wiki/meetings/2026-07-02-mrp-full-loop-demo.md|July-2 1:47 PM demo]] ([[wiki/people/nathan-carver.md|Nathan Carver]], [[wiki/people/val-levitan.md|Val]], [[wiki/people/lev-rudky.md|Lev Rudky]], [[wiki/people/mikhail-perelman.md|Mikhail Perelman]]) Nathan ran the tool end-to-end and the room pinned down the tool's **input** and **output** contract. Nathan opened by listing the next backlog items he wants a thumbs-up on before building: **order efficiency** (MLQ/minimum-order-quantity awareness + price breaks), **vendor and item master record rights**, the **locked/committed inventory check**, and **PO release**. [[raw/Meeting_Transcript_MRP_Full_Loop_Demo-July-2-2026.md]]

- **Scenario tool — compare multiple build quantities side by side.** The tool can now take one part and compare building **250 / 500 / 750** at once, showing for each quantity how many parts are short and how many are covered, broken down by part number using what is in MSBC (on-hand and on-order). Nathan called this "planning the build," a step past a single short-count. It ran against a **development MSBC server**, so the data was stale relative to production. [[raw/Meeting_Transcript_MRP_Full_Loop_Demo-July-2-2026.md]]
- **Consolidated shortages, grouped by vendor, exported as CSV.** On request the tool rolls the three build quantities into a **total consolidated shortage**, makes observations on the data, and follows up with a question (group by vendor, or price out a consolidated PO run). It can generate a **report as a CSV** (viewable as a spreadsheet) with columns such as part number, demand, quantity on hand, quantity on PO, and quantity to order (Lev noted "net demand" and "quantity to order" are the same). [[raw/Meeting_Transcript_MRP_Full_Loop_Demo-July-2-2026.md]]
- **Input = a forecast/build list held in Business Central, not typed each time.** Lev and Mikhail worked through (with Val) that the input should be a **dedicated forecast-equivalent list of top-level assemblies with quantities stored in BC** (maintained by Mikhail), so the user selects part numbers and quantities from BC rather than re-keying them — "exactly like you operated before, but out of Business Central." The tool then explodes to the **consolidated list of purchase items** needed to build them. Mikhail's mental model: click a top-level assembly, put a quantity, get the components list with on-hand vs needed. [[raw/Meeting_Transcript_MRP_Full_Loop_Demo-July-2-2026.md]]
- **Output = repeatable saved prompts / skills, callable on demand.** Lev asked whether the "views"/prompts he types can be stored so they don't have to be re-created. Val's steer: saving prompts works, but **repetitive work is better given to an agent** — a daily/weekly report an agent produces on demand. Nathan explained the tool has **two sides** — a **software side** (procedural steps: how to pull and classify MSBC data) and a **skill side** (saved instructions the user invokes with a simple command, like a Claude `/`-command), and the two combined make agents that repeat a workflow quickly. Lev to send Nathan example prompts + the input location in BC + example output column headers. [[raw/Meeting_Transcript_MRP_Full_Loop_Demo-July-2-2026.md]]
- **Data completeness is a standalone track, not a blocker.** Lev flagged data cleanliness as its own topic that will take time to sort out, but agreed with Nathan that **functionality is not blocked by it** — the tool can be used now and improves as the data is cleaned. [[raw/Meeting_Transcript_MRP_Full_Loop_Demo-July-2-2026.md]]
- **Jira plan (DTP 941).** Nathan will work under **DTP 941**, rearranging its stories to fit the agenda: he adds a story to implement what Lev sends Monday, and the three review-first items (incl. **964** vendor/item master record rights) get **deferred to the backlog** (Val moved them during the call). Lev aims to send the input/output spec by the weekend; Nathan resumes Monday (a US holiday weekend), with a follow-up meeting the next Thursday. **§15.8:** clear — MRP / purchasing / tooling economics only, no named-person compensation. [[raw/Meeting_Transcript_MRP_Full_Loop_Demo-July-2-2026.md]]

## Calculations moved into code (July 14 2026)

On the [[wiki/meetings/2026-07-14-mrp-and-sales-watch-demo.md|July-14 1:03 PM demo]] ([[wiki/people/nathan-carver.md|Nathan Carver]], [[wiki/people/val-levitan.md|Val]], [[wiki/people/lev-rudky.md|Lev Rudky]], [[wiki/people/mikhail-perelman.md|Mikhail Perelman]]) Nathan showed a durable architecture change: he **added coding support so the calculations run in code and the AI agent only orchestrates** — "ideally the agent's doing no calculations at all, unless there's an edge case the user asks for." Responses come back much faster, and from Nathan's own checking the totals are accurate; his remaining accuracy worry is whether the tool reads the **MSBC configurations** correctly. (This is the same orchestration-vs-compute shift noted on [[wiki/topics/business-central-erp-implementation.md]].) - **Adjusted-quantity column defaults to empty.** A new column lets the purchaser override the suggested quantity. Lev had originally specified it default to the net-demand value (so only exceptions need editing) then reconsidered; Mikhail made the call — it should be **empty**. Lev flagged that yesterday's adjusted values may simply no longer be correct. Nathan said it is doable but the mechanism was not settled.
