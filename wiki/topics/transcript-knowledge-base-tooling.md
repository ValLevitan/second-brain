# Transcript knowledge-base tooling

Across three Mar 20–21 2025 working sessions, [[wiki/people/aaron.md|Aaron]] and [[wiki/people/val-levitan.md|Val]] worked on building a tool that turns Val's meeting recordings into a searchable, cross-linked knowledge base — the same idea that later became this second brain. The work spans three pieces: **transcription**, **tagging/classification into a database**, and **visualization**. (The transcription side is on [[wiki/topics/ai-assisted-development.md]]; the meeting-tracking motivation is there too.)

This is largely a two-person exploration; treat it as durable direction, not a finished system.

**Earliest ancestor (~2023–24):** the company-wide **JVL Insights** AI-knowledge-base proposal — "aggregating, categorizing, and sharing the relevant tribal knowledge… in real time," with Aaron already attached as Atlassian consultant — predates this whole 2025 tool thread. See [[wiki/projects/jvl-insights-knowledge-base.md]]. [[raw/jvl_insights_the_aidriven_knowledge_base_draft_2_2025-03-29.md]]

## Visualizing a document set (Mar 20)

- Aaron demoed a **3D force-directed graph** rendering hundreds of API endpoints of a software platform called **Target Process** (aka "TargetProcess"). Nodes cluster by artifact, by term, or by section links; he called the result "a really fancy three-dimensional table of contents" — visually striking but "impossible to use right now." [[raw/aaron_3d_force_directed_graph-March-20-2025.md]]
- The graph is built by scraping the platform's manual into markdown, indexing the terms into a **SQL database**, then forcing the terms together in 3D and drawing links between them. [[raw/aaron_3d_force_directed_graph-March-20-2025.md]]
- Aaron showed other **D3** visualizations as alternatives: squarified and cascaded **tree maps** (e.g. months → topics → people), a **chord diagram** (all terms in a circle, relationships drawn as chords), and a simple calendar strip of topics by date. The point: once the data is in a database correctly, many views are cheap. [[raw/aaron_3d_force_directed_graph-March-20-2025.md]]
- He was explicit this graph is **not** the target format — "I'm not saying you turn it into this… it's just a way to analyze it" — and that better-baked tools exist than building from scratch. [[raw/aaron_3d_force_directed_graph-March-20-2025.md]]

## The tagging science (Mar 20–21)

Aaron described the classification method he wants, using a **Chase bank-statement** categorization project as his working model (a personal project with the same shape as Val's transcripts):

- **Emergent tagging, no hints:** for each document, ask the AI to read it and return the top ~20 (or 50) pertinent terms with **no steering** — "read this document and give the top 20 pertinent terms." Attach those terms to that document in the database, then repeat independently for every document. [[raw/aaron_tagging_science-march-21-2025.md]]
- **Normalization:** an AI extraction produces near-duplicate variants of the same term (e.g. "FlexPay" / "Flex Pay" / "flexpay", or "Walmart" / "Wal-Mart" / "Walmart store 27"); these must be normalized to one canonical tag so search works. A category/subcategory/content structure links canonical labels to the raw documents. [[raw/aaron_tagging_science-march-21-2025.md]]
- **Rare tags are signal, not noise:** don't delete infrequently-used tags — reverse-sort them to find "departures from the typical discussion flow," which are exactly what a data scientist wants to investigate. (A tag seen once in 10,000 docs can be discarded; small clusters of infrequent tags should be examined.) [[raw/aaron_tagging_science-march-21-2025.md]]
- **AI as a first-order thinking tool:** once every tag has been shown to the AI, ask it what related themes a tag represents (his example: banana → Ecuador → radioactivity of potassium) and search on those — using the AI to surface connections faster than a person could. [[raw/aaron_tagging_science-march-21-2025.md]]
- **Under the hood** (from Mar 20): a **Markov / Bayesian n-gram** analysis with stop-words generates the top-20 weighted terms per document — "the same reason you have a spam filter" (Bayesian scoring). Storing the top-20 in SQL keeps it fast versus recomputing on every load; a balance of fast-versus-useful. [[raw/aaron_3d_force_directed_graph-March-20-2025.md]]
- **Endgame:** point an **MCP tool** at the database so an AI can query by tag/pattern and return the relevant documents; later **vectorize** the text for a vector database, then optionally fine-tune or build a custom agent. Aaron deferred the vector-database stage as "the next stages." [[raw/aaron_tagging_science-march-21-2025.md]]
- **Existing tools evaluated:** Aaron looked at an off-the-shelf MCP server (transcribed "**mcp-docs-req**", i.e. a RAG-for-local-docs server) and rejected it — "not really doing RAG," a single-file, non-persistent, inflexible implementation — so he is building his own. [[raw/aaron_tagging_science-march-21-2025.md]]

## Val's knowledge-use philosophy — "value streams," trends over retrieval (Mar 26)

On a follow-on Aaron session (see the date note on [[wiki/meetings/2025-03-26-aaron-knowledge-visualization-openwebui.md]]), Val spelled out *what he wants the knowledge for* — which frames this whole tool:

- **Direction, not evidence.** Val said he does **not** want to retrieve documents to prove "you said this" — that only matters as court evidence. What he wants is to extract **trends, directions, "hints, hues, shades"** — whether the business is deviating from or moving toward something. He owns **"value streams"** (which he also calls **"cash rivers"**) and his job is to "keep the ship on course" so those streams "remain fertile — plenty of fish, plenty of cash." He described running "a mini-government, a mini-country… a Levitan country, but extremely small." [[raw/aaron_visualization_making_use_of_knowledge-march-28-2025.md]]
- **The graph-database debate.** Aaron explained that loading the corpus into a **graph database** would count the **frequency of words and their relationships**, then follow the relative weights of terms to decide which document to retrieve. Val's reaction: retrieval isn't his goal — he'd rather load the files into ChatGPT (transcribed "ChatDBT") and ask it for, e.g., the **"10 most prevalent directions"** being discussed and the **"5 least discussed,"** then judge which match his value streams. [[raw/aaron_visualization_making_use_of_knowledge-march-28-2025.md]]
- **Val's AI thesis.** He assumes AI will become **smarter than any living human in about five years**, arriving **in steps**; within "a couple of years" it will give him something beyond his own brain or his employees — "on par or smarter than my entire organization." His plan: create an **open conversation environment** where the AI effectively sits in his meetings, then **subcontract work to it** (program a system, design a business model, research legislation "in Alabama and see how my product fits best"). His stated stakes: "if I don't do it and everybody else does, then I should quickly sell my business." [[raw/aaron_visualization_making_use_of_knowledge-march-28-2025.md]]

## The vector-database lesson (Mar 31)

A long (~139-min) Val-Aaron session (see [[wiki/meetings/2025-03-31-vector-db-second-brain-session.md]]) turned to how the transcript knowledge base is actually stored and searched: [[raw/vector_meeting_db-march-31-2025.md]]

- **Open WebUI already vectorized Val's corpus.** When Val created a knowledge base in the Open WebUI workspace, pointed it at a directory and hit synchronize, the platform vectorized every markdown file automatically — Aaron: "That is vectorizing the text inside of each one of those markdown files... It's creating a database a copy of all your markdown files." The knowledge base holds Val's **"JBL [JVL] alignment meetings."** Vectorized content is one-way: "once you've vectorized content you can't get it back... it's no longer a readable document." [[raw/vector_meeting_db-march-31-2025.md]]
- **Where it lives:** on Val's laptop disk, inside the Open WebUI Docker volume (they walked to `/var/lib/docker/volumes/...` as root and inspected a `vector_db` directory — `header.bin`, linked-list and "data level 0 bin" files of raw binary). Aaron said the internal system "is using SQLite and SQLite is a very valid SQL database system." New files require a periodic **directory re-sync** to re-vectorize. [[raw/vector_meeting_db-march-31-2025.md]]
- **Internal vs external vector DB:** replacing Open WebUI's internal store with an external service (**Pinecone** or **Chroma**, or AWS database services) would let **multiple people / any platform with an API key** use the same vectors — versus the current data being usable only by Open WebUI on that one laptop. Pinecone "exists because it's a software-as-a-service and you pay for retrieval." Val's answer to "who is your intended audience?" — "right now it's myself. I just want to learn how to use it" — so they **stayed with Open WebUI**. [[raw/vector_meeting_db-march-31-2025.md]]
- **Semantic search framing:** Aaron named what Val wants "semantic search" (meaning/context-aware retrieval) and taught that Val must define the semantic relationship "a file instance equals a meeting" — no software knows that by itself. Val's example queries: "what did I discuss in the last meeting with Pavel," "how many meetings I had with Pavel," "rate these ideas in terms of how symbiotic it is with JVL business." [[raw/vector_meeting_db-march-31-2025.md]]
- **Diarization:** Val asked for speaker recognition; Aaron: that is **diarization**, and "the Whisper model is not capable of diarization" — a common workaround is having a language model read the finished transcript and assign speakers, "but you have to now trust that that process isn't making shit up." He also corrected Val's learning assumption: "nothing is learned when you run stuff through a language model" — ChatGPT only *appears* to learn because the web interface retains conversation history/memory. [[raw/vector_meeting_db-march-31-2025.md]]
- **Open Semantic Search experiment (unfinished):** Aaron had Val stand up **Open Semantic Search** — "a collection of a whole bunch of different tools" with a workstation search UI, running as multiple orchestrated Docker containers — via a wget-fetched `docker-compose.yml`, a `neo4j.env` file, and **Cline** ("Client"/"Klein") driving the setup. The **Apache Solr** service (transcribed "Solar") kept returning **503 service unavailable** to the apps container (suspected start-order/permission issue); they stopped with `docker-compose down`, and agreed to pick it up later (Val was flying that afternoon 2–6). [[raw/vector_meeting_db-march-31-2025.md]]

## The Pinecone exploration — "buy a reliable car, don't build a hot rod" (Apr 12)

A follow-on session ([[wiki/meetings/2025-04-12-pinecone-vector-db-aaron.md]]) picked up where Mar-31 left off, this time looking at **Pinecone** as the managed vector store for the transcript corpus: [[raw/pinecone_vector_recordings_db__aaron-april-12-2025.md]]

- **Buy-don't-build framing.** Aaron walked Val through the "**awesome MCP servers**" list (a popular community aggregation of MCP servers) and pointed at paid document-management platforms — **Needle AI** (which Aaron said runs on Pinecone underneath) and **Firebase** — as the sane path: "you don't want to build a hot rod that works really well for you but nobody else can service. You want to drive a reliable car you bring to the dealership." Paying "$15 to $50 a month" for a platform that does the heavy lifting beats "running and operating the whole system yourself." [[raw/pinecone_vector_recordings_db__aaron-april-12-2025.md]]
- **Pinecone Assistant hands-on.** They opened the **Pinecone Assistant** playground, created an assistant ("doc search"), and dragged a file in to be vectorized; Aaron noted it "feels very similar to Open WebUI." The playground offered chat models (**GPT-4o**) and an **MCP environment link** — "you're assembling a low-code agent solution to manage documents inside of Pinecone." Pinecone "exists because it's a software-as-a-service and you pay for retrieval." [[raw/pinecone_vector_recordings_db__aaron-april-12-2025.md]]
- **The real problem is the ingestion path.** Aaron reframed the exercise: building a useful agent framework "doesn't happen in minutes… it's usually hours or days." The open questions he named are exactly this second brain's problems — "**what is the ingestion path for all of your content?**" (from recorded audio → transcript → markdown → into the store) and, with hundreds of files, "how do we search for them… what's the relevancy score" without loading every vector at once. [[raw/pinecone_vector_recordings_db__aaron-april-12-2025.md]]
- **Context saturation + the temporal-conflict question.** Aaron taught that an agent "can't have a conversation with all of your documents at once" — loading every vector causes "context saturation"; good context-management (why Cline worked well for Val) is what controls how documents load. He also posed the question that this engine's §11 temporal rule answers: "what happens when you have an earlier meeting and a later meeting and those two things are one direction [contradict] another?" — Val: "I don't have any answers. I need to play with it. I need to see the conflicts." Val's correction: Val misremembered that pointing Cline + the Pinecone MCP at a directory would load the data — Aaron: "No, it cannot… how do you load the data into Pinecone is the question." They ended leaning that Pinecone's raw playground was too low-level ("we need something more baked… a more prepared dish") and switched to drawing the architecture on a Google whiteboard (Teams screen-share kept failing). [[raw/pinecone_vector_recordings_db__aaron-april-12-2025.md]]

- **The load-bearing lesson (recurs in this engine):** the **embedding model must match on both sides** — "that model matches the database we used… This is important." - **Two second-brain-relevant gotchas:** (1) source files had to be **converted to Google Docs** (markdown files with kanji/Japanese leading characters **broke the OpenAI embeddings node** — "this is where sanitizing the input becomes important… you can't just throw anything at it"); (2) the corpus being fed in is Val's own meeting transcripts — one indexed file was literally the "**pinecone vector recordings DB Aaron**" transcript (the Apr-12 session), and a test query surfaced "**Estrella**," which Val identified as **a law firm**. ## Report-ingestion pipeline — turning by-state gaming reports into graph memory (May 14)

Two short May-14 recordings ([[wiki/meetings/2025-05-14-report-pdf-processing-pipeline.md]]; one session, §12) dictate a method to ingest an **arbitrary sectioned PDF report** — specifically a **yearly by-state gaming-market report** — into the same graph-memory / "terms" database as the transcript work. It is a concrete answer to this page's standing "ingestion path" question, applied to external reports rather than transcripts. Speaker not explicitly named (consistent with the Aaron AI-tooling thread / Val dictating — inference). [[raw/text_extract_pdf_process-may-14-2025.md]] [[raw/approach_process_large_reports-may-14-2025.md]]

- **Why PDFs are hard:** they are laid out "for humans reading them, not for machines" — text extracts backwards/out of order even though the page looks coherent. So the pipeline **renders each page to an image (PNG)** as an intermediary instead of pulling text directly. [[raw/text_extract_pdf_process-may-14-2025.md]] [[raw/approach_process_large_reports-may-14-2025.md]]
- **The tooling named (as transcribed):** **Pandas** (described as "a library from Pandoc" — likely a garble of Pandoc) to manipulate the document/render pages to images; **Tesseract** to roughly OCR text from the page images; a **local language model** to describe and **classify each page**, producing effectively a **machine-generated table of contents** of what every page is; then a **multi-modal model (ChatGPT or "CLAWS"/Claude)** reads two or three screenshots per state-per-year with a **structured prompt** (an example prompt was already shared with Val). [[raw/text_extract_pdf_process-may-14-2025.md]] [[raw/approach_process_large_reports-may-14-2025.md]]
- **Focus on the by-state sections:** the report opens with tables by state/sector, then a transformation analysis into per-state reports (the most valuable part, and the most consistent in format), so the pipeline extracts the **per-state sections** as the "data-rich" source. Each state's screenshots → a **markdown file tagged with that state and year**. The conversion prompt is aligned to the target dataset's **key entities** (states, casino properties, regulatory bodies, gaming types, revenue metrics, tax structures, market-performance indicators) and **relationships** (e.g. regulatory changes ↔ market impacts) so each markdown carries those sections. [[raw/approach_process_large_reports-may-14-2025.md]]
- **Bite-sized upsert into the graph DB:** you **cannot consume all 50 states in one shot** (too much context), so each state's markdown is processed **one at a time** — "run a process and exit, run a process and exit" — upserting into the **terms / graph database** using the specific memory domains repeatedly. The end state: **50 states of datasets with graph traversal across all of them**, so a reader can then ask, e.g., "what are the trends in the northeast quadrant of states." (This is the same **graph-memory / memory-domains** system as the May-9 memory-graph MCP on [[wiki/topics/ai-assisted-development.md]].) [[raw/approach_process_large_reports-may-14-2025.md]]

## The built PDFX tool + SurfSense (May 15)

Three short recorded segments of one [[wiki/people/aaron.md|Aaron]]↔[[wiki/people/val-levitan.md|Val]] session ([[wiki/meetings/2025-05-15-ai-aaron-pdfx-surfsense.md]]; the three files are **distinct segments of one session, not duplicates** — §12) show the May-14 dictated method now built into a working tool. (The task pointed this at [[wiki/topics/ai-assisted-development.md]], but the content is the direct continuation of the May-14 report-ingestion pipeline above, so it is recorded here per §4.) [[raw/ai_aaron-may-15-2025.md]] [[raw/ai_aaron-may-15-2025 (1).md]] [[raw/ai_aaron-may-15-2025 (2).md]]

- **PDFX / "PDF access" — the working tool.** Aaron demoed the tool's output on **four yearly by-state gaming-report PDFs**: it produces a **structured per-page index** (each page described and grouped by state — his example showed multiple Colorado pages, then Connecticut, Delaware, District of Columbia…) plus the roughly-extracted markdown text per page. That index is "not the final transcription… simply an index to know exactly what's in the page," which is then fed to the language model page-by-page/chapter-by-chapter to insert **terms into the memory-graph database**. The only remaining step was **spending tokens** to send content and do the DB insertion ("the easiest part"); the goal is that a user "only has to run the `process` command" and out comes "an actual memory graph from the PDF." [[raw/ai_aaron-may-15-2025 (1).md]]
- **Why a memory graph per PDF.** Aaron is "wrapping up the memory-graph generator for PDF documents" so each PDF becomes a queryable "sphere of information," because current models like "Cloud [Claude] and ChatGBT [ChatGPT] don't have enough context length" to consume a whole report at once; soft-links can be added between spheres. [[raw/ai_aaron-may-15-2025.md]]

## June 17 2025 — the "librarian" tool + the AI-agent/attractor theory behind it

Two segments of one [[wiki/people/aaron.md|Aaron]] ↔ [[wiki/people/val-levitan.md|Val]] session ([[wiki/meetings/2025-06-17-transcript-kb-tooling-librarian-attractors.md]]; the two files are **distinct segments of one session, not duplicates** — §12). - **Why chronological/date organization (the origin of this brain's structure).** The librarian "effector" is meant to **reinforce Val's own way of storing things** — "by date and by week and month and year" — so "when it follows things it thinks the same way you think about it." - **Aaron's mental model of an AI agent.** "An AI agent is fundamentally a **text inference engine operating within a game loop architecture equipped with effectors** to interact with its environment." The loop is a **perception → cognition → action** cycle that never ends until you exit; environmental data + user prompts enter, the inference engine processes them "through its knowledge landscape," effectors execute, and the cycle repeats without blocking. [[raw/managing_transcripts-june-17-2025.md]]
- **Attractors (the prompt-writing theory).** Aaron used a **Lorenz attractor** as the visual metaphor for token prediction ("the quick brown fox…"): there's never one fixed state, but "clearly defined regions it tends to inhabit." **Knowledge graphs create "behavioral gravity"** — **hubs** (dense concentrations of information), **semantic valleys** (long links between distant concepts), and **concept density**. [[raw/managing_transcripts-june-17-2025.md]]
- **The grounding technique.** Bring high abstract concepts down toward concrete instances; **putting the references at the end of a paper** keeps the model "grounded in the viscous region of information density… keeps us on topic." Aaron: "this is effectively a **white paper on how to write good prompts**." He **wrote this paper before refactoring text-flow** to bake the guidance into the tool, and says it gave him "a totally different perception of writing prompts." (Inference: this is the same "text flow" formatting tool referenced across the earlier sessions.) [[raw/managing_transcripts-june-17-2025.md]]

## Feb 2 2026 — the built knowledge-graph platform ("reasoning as a service"), handed to Andrei & Dima

Nine months on from the 2025 exploration, [[wiki/people/aaron.md|Aaron]] demoed a **finished platform** he had been building "for months and months" and handed it to [[wiki/people/andrey-bosik.md|Andrei Bosik]] and [[wiki/people/dmitri-kovalchuk.md|Dmitri Kovalchuk]] to deploy and run — the direct descendant of the whole 2025 transcript-knowledge-base thread and the closest sibling yet to this second brain. - **What it is — "reasoning as a service."** Aaron calls it a system that "provides additional thinking on top of" a language model's own reasoning — it extracts **concepts** and the **relationships/edges** between them out of documents and assembles them into a graph, de-duplicating repeated mentions into one node. The catalyst Aaron named: Val's "hundreds and hundreds" of dated transcripts turn into "transcript soup" where three or four topics per meeting are impossible to classify. - **Data model — ontologies, concepts, edges.** Data is organised into **ontologies** (Aaron's demo held "first principles" and "hooks and ways" ontologies, loaded from the Claude Code config "ways" documents Val keeps). A query traverses the graph like "subway/train routes," returning connected concepts. Aaron demoed asking Claude (via an MCP connector called "Knowledge Graph") to invent a new ontology ("emergent patterns") and write a concept ("code review as recursive governance") back into the graph, batching the concept + edge creation as queued actions. Edges are **typed** ("causes" vs "modifies" vs "evidence" — "the choice of words matters"). Result "gets more out of the data than actually exists in it" via emergent relational properties. [[raw/Introduction to Knowledge Graph Tool-part-1-February-2-2026.md]]
- **The tech stack (as transcribed).** Data store is **PostgreSQL** with custom extensions and a **graph extension — Apache Age**. The back end is **five Docker containers** (a web container, an API container, an operator container, an S3-style storage container — **garage** — and the Apache/Postgres container), orchestrated. The front end ships separately (can be on a different machine): a **command-line toolkit ("KG")**, an **MCP server**, and a **Fuse file-system driver** that mounts the graph as ordinary folders (so Obsidian can point at it and see the concepts + their links). There is also a **web workstation** UI for introspection (search / query-edit / ingest tools, a 3D graph view, an embedding-landscape view, path-tracing between two concepts), plus admin (OAuth clients, users, RBAC roles). Inference uses **Anthropic or OpenAI APIs**, or a **local Ollama-compatible** model for fully on-prem running; it runs on **CPU or GPU** (GPU optional acceleration). [[raw/Introduction to Knowledge Graph Tool-part-1-February-2-2026.md]]

It has OAuth/RBAC, ontology-level permissions (users can hide an ontology from others, but a super-administrator sees "the full truth"), and can also ingest **images** and (in progress) **live transcription** — assembling a concept graph word-by-word as a meeting happens so Claude can be an active participant. - **Current state:** JVL Minsk meetings are recorded via Microsoft Teams; transcripts currently live in **MS SharePoint**. The goal is an automated pipeline extracting engineering knowledge into actionable artifacts. [[raw/Engineering_Meetings_to_Knowledge_Extraction.md]]
- **The 5 layers:** (1) **Gathering** — a **daily scheduled job** (**n8n or similar**) pulls transcripts from SharePoint and runs AI extraction prompts; (2) **Review** — engineering leads validate the AI-extracted content before publication; (3) **Storage** — validated **ADRs / technical docs** land in a **dedicated GitHub repository with PR approval**; (4) **Graduation** — ADRs that **imply work** get promoted to **Jira Requirements** with assignees + dependencies, while pure decision records **stay in GitHub**; (5) **Visibility** — **Jira dashboards** give project managers and compliance a view of active requirements. [[raw/Engineering_Meetings_to_Knowledge_Extraction.md]]
- **The blocking open item — SharePoint transcript access must be resolved first.** Two options: (i) an **MCP server for authenticated SharePoint access** (keeps the pipeline self-contained, no manual transfers), or (ii) a **storage relay** — export/sync transcripts from SharePoint to intermediate storage (**Azure Blob, S3, or local filesystem**) the pipeline reads (simpler, but adds a moving part). The choice depends on IT/admin policy around SharePoint API access. [[raw/Engineering_Meetings_to_Knowledge_Extraction.md]]
- **The multi-facet labeling taxonomy (Pavel's addition).** Each transcript is tagged across **five independent facets** with a **controlled vocabulary** (no free-text, to prevent drift like `flex-pos`/`FlexPOS`/`Flex POS`): **Product/System** (e.g. `product:flex-pay`, `product:orchestration`, `product:auth`), **Domain** (`domain:registration`, `domain:payments`, `domain:security`…), **Concern / engineering-activity type** (`concern:architecture`, `concern:api-design`, `concern:dependency`…), **Decision Status** (`status:exploring`, `status:decided`, `status:action-items`, `status:blocked`), and **Cross-cutting Dependencies** — directional labels like `dependency:orchestration→flex-pos`. **AI proposes labels** (Layer 1), an **engineer confirms/corrects** them (Layer 2). [[raw/Engineering_Meetings_to_Knowledge_Extraction.md]]
- **Extraction categories** the pipeline pulls from each transcript: Decisions, Action Items, Risks Raised, Dependencies Identified, Technical Debt Acknowledged, Architecture Constraints, Open Questions, and ADR Candidates. Risks/recommendations flagged: transcript quality is the foundation (validate Teams transcription first); start with a **manual MVP on 5–10 transcripts**; **avoid premature Jira integration** (auto-ticket-creation risks spamming the backlog — start with manual promotion); use a **prompt chain, not a single prompt**; and AI can extract *descriptions* of architecture but **not accurate diagrams** without human refinement. [[raw/Engineering_Meetings_to_Knowledge_Extraction.md]]

[[raw/Engineering_Knowledge_Extraction-Architecture-February-12-2026.md]]
- **(c) Auto-surface recurring unowned items; archive the ones that go quiet.** Unowned GitHub items accumulate silently. ## Mar 17 2026 — requirements vs capabilities, and grounding the reference guides in INCOSE/ISO

Segments 1–2 of the [[wiki/meetings/2026-03-17-jvl-ways-on-github-setup.md|Mar-17 Aaron↔Val session]] opened the documentation-methodology layer that sits *under* the Mar-13/Mar-16 storage rulings above — how the capability/requirement **reference guides** themselves should be written and what makes a capability distinct from a requirement. - **Requirements vs capabilities (the nature of each).** Val's opening question — which comes first? Aaron's teaching (as Val restates it): **requirements are usually long-lasting** (they can be retired, but persist), while **capabilities are more per-product**, directly tied to a product; the two are linked but **not in a strict hierarchy**. Aaron's illustration — "the system has two 8K displays **capable** of driving at 120 Hz" reads as *both* a requirement and a capability depending on the audience, and how you ended up with two 8K displays is "a blend of limitations, cost, market desire." His **"market-driven capability" funnel**: start with a **goal** (e.g. sell 1,000 units in a market for a target revenue), define **business requirements** far out in "market territory," then loop inward — refining requirements ever closer to the core (can we reuse the software/hardware we have?) — and **requirements measured against the outside environment become capabilities**. The resulting **bundle** (business / non-functional / functional / technical requirements + capabilities) is applied to "a part of reality" (his example: Georgia operators) and operationalized into an architecture that fulfils the goal. [[raw/Requirements_Capabilities-March-16-2025.md]]
- **Acceptance as a gradient, not pass/fail — and Val's binary pushback.** Reviewing the engineering reference's definition of what files/structure belong in a repo, Aaron cautioned against a hard **pass/fail** acceptance test ("you will get people gaming it"): use a **soft "accepted / draft" mode with a threshold** — e.g. "80% or 90% of the itemized things we expect in a repo must be in an acceptable state." **Val pushed back**: he'd rather keep it **more binary** and "override it later and push them for the max," arguing gaming becomes "exponentially harder" once AI is invoked and the whole company wants to succeed — "Russians don't understand liberties."
