# NOVA platform architecture (JVL land-based gaming platform)

**NOVA** is JVL's software platform for the land-based EGM (electronic gaming machine) — the stack that runs on the cabinet's main processor under Linux. The name and the founding to-be design were set on a two-segment May 12 2026 working session ([[wiki/meetings/2026-05-12-nova-platform-architecture-overview.md]]) led by [[wiki/people/val-levitan.md|Val]] and [[wiki/people/alexander-biratka.md|Alexander (Sasha) Biratko]], with [[wiki/people/irina-shishko.md|Irina Shishko]] and [[wiki/people/anton-leshkevich.md|Anton Leshkevich]]. Until this meeting the platform had been called "Omni" as a working code-word; Val ruled the team would stop calling it Omni and named it **NOVA** (explicitly a "code-word," may still change pending [[wiki/people/pavel.md|Pavel]]'s input). This page is the software-platform architecture; the earlier "OMNI 2" language/architecture thread and the Rage→Omni *content* transition are on [[wiki/topics/omni-core-advancement-and-game-templating.md]]. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_1-May-12-2026.md]] [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

## As-is architecture (Segment 1 walkthrough)

Sasha walked the current on-cabinet architecture from a whiteboard (the visual layout lives only in the shared whiteboard/Miro file, not the transcript). [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_1-May-12-2026.md]]

- **LGS is the central hub** — all inter-component communication currently flows through LGS (e.g. the framework asks LGS for math, LGS asks the MathEngine, the answer returns through LGS). [[raw/Meeting_Transcript_nova_platform_architecture_overview-Segment_1-May-12-2026.md]]
- **Linux OS + HAL** (Hardware Abstraction Layer) is the lowest layer — scripts and system libraries (correct Java and Chrome versions, codecs, utilities) in a dedicated repository. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_1-May-12-2026.md]]
- **Setup UI / In-Setup UI** sit inside the LGS repository (they were briefly split out, but the separation caused UI-vs-LGS version drift and they have no use outside LGS). [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_1-May-12-2026.md]]
- **Arrange + MathEngine** run as Docker containers holding a *universal* math engine and arrange (RG) server usable for both online and land-base; the Arrange server is contacted only by MathEngine. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_1-May-12-2026.md]]
- **System libraries (SoundLib, PrinterLib, BillLib, BoardLib, etc.) are in-process Java-native modules loaded into LGS's memory — the known fragility: any library error crashes all of LGS.** This is the explicit driver for the to-be migration. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_1-May-12-2026.md]]
- **Firmware ownership:** JVL writes BillBoard/driver firmware; printer firmware ships on the printer and is not JVL's. **Tools:** Miranda (a Unity plugin for authoring JSON-described game scenes on the GameFramework) and TS-360 (a broad test tool spanning button-press → result → LGS history). **CMS** is an external service that configures LGS and collects statistics from it. **Flex-Pay / Flexport** were newly added to the diagram; Flex-Recycler/Dispenser/POS exist as variants but are not yet integrated. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_1-May-12-2026.md]] [[raw/Meeting_Transcript_nova_platform_architecture_overview-Segment_1-May-12-2026.md]]

Val's discipline through Segment 1: describe the as-is fully before any to-be design ("let's finish 'as is' first; then we'll go to 'to be'"). [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_1-May-12-2026.md]]

## To-be architecture (Segment 2 decisions)

**Library modules → standalone services.** Each in-process Java-native library becomes a **standalone service** — its own executable and repository, independently startable/restartable, whose failure cannot crash LGS. Sasha's definition: "a separately-executable application with an interface, performing a defined function … its failure does not affect other applications." [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

- **Service ↔ LGS communication = Unix sockets.** Justified by the BillBoard bottleneck (state must persist fast enough to survive a reboot on a button press; reaction time under ~10 ms) — Unix sockets give more than enough throughput at that latency. Anton supported this. [[raw/Meeting_Transcript_nova_platform_architecture_overview-Segment_2-May-12-2026.md]] [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]
- **Per-service data contracts + APIs.** Each service defines its own data contract with LGS over the socket interface. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]
- **Virtual/demo mode per service.** Each hardware-backed service has a "demo/virtual" implementation exposing the same interface to LGS (with extra control APIs, e.g. a virtual printer that can be told to "throw an error"), enabling end-to-end platform testing without physical hardware. Sasha estimated ~99% of real hardware behaviour is emulable; the last ~1% is fine mechanical detail not worth simulating. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

**Hardware boundary — what is inside vs outside NOVA.** Physical components (monitors, touchscreens, speakers, amplifier, button panel, IO/counter board, candle light, LED controller, printer and bill-validator hardware, boards) live **outside** NOVA, drawn in a different colour. **Firmware also lives outside** NOVA — even where JVL writes it (BillBoard, board driver), the firmware runs on a dedicated board, not on the Linux processor (Sasha conceded this after Val's pressing). **Inside** NOVA: Linux OS/kernel context, HAL scripts, services, LGS, Setup UI, Arrange, MathEngine, Progressive Controller, Miranda, TS-360, the CMS link, Flex-Pay and Flexport. HAL scripts (written by JVL) act as the platform entry point, launching LGS and the services in sequence. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

**Connectivity additions.** A combined **modem + GPS** device (sold as one) with its own Linux driver, for OTA game loading/replacement; and a separate **Wi-Fi module** so that at multi-machine locations only one machine carries the active GSM modem (cost) and the others connect to it via Wi-Fi — a leader-election mechanism (analogous to the MBD progressive-controller "master" logic) still needs designing. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

**Games as data, not applications.** Games today are directories of files; in NOVA they become **packaged archives** (paving Pasha's existing chunk-with-checksum packaging) delivered over the network. Each game gets a reserved **slot** on the machine (a configurable maximum, illustratively 12). Updating is a **CMS-triggered LGS operation** — CMS tells LGS "replace slot N with the game at this URL"; LGS downloads via the modem and swaps the slot. Games are **not Docker containers and not active Linux processes** — a game is a script in the browser, so a game error only restarts the browser and the OS is unaffected (Sasha's architect call: "a Docker wrapper for the games is excessive"). Each game keeps its own checksum/signature for certification; for **Florida-style whole-image-certified jurisdictions**, game replacement triggers recertification, and a dedicated **Updater** service was floated as a possible alternative path (not decided). [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]] [[raw/Meeting_Transcript_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

**Repository structure.** NOVA = **12 base repositories** (11 base + 1 games container), plus each game gets its own repo. It becomes 11 base if Arrange folds into the MathEngine repo (Sasha to confirm with [[wiki/people/efim-podvoiski.md|Efim]] — Arrange is "very small"). On the hard services (sound, printer, BB, board), Sasha used his architect authority to rule **one repository per service**, rejecting Anton's monorepo suggestion on release-ability/versioning grounds. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

**Language stack.** Java (LGS, Setup UI, In-Setup UI, TS-360, progressive controllers) + TypeScript/JavaScript (game framework and games) + **Rust** (the new direction: services, plus JVL-written firmware migrated to Rust where the controller supports it — older STM32-class boards stay as-is) + shell/bash (HAL) + C# (Miranda). The current **C++ MathEngine is to be re-written in Rust in a new repository**, leaving the existing C++ repo untouched. Three primary languages (Java, TS/JS, Rust) plus utility. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

**Browser engine — stay on Pixie/Phaser for now.** Anton raised moving off the browser stack to Unity/Unreal for graphics quality now that online is deprioritised; Sasha agreed in principle (more native, keeps the dev cycle inside Unity where Miranda already lives) but the choice is constrained by **free licensing** (Unity/Unreal are paid; Godot's video support is immature). Val's call: migration would be "a huge restructuring," so stay on the current engine — tracked as deferred-but-not-killed. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

**Math secrecy relaxed.** Sasha historically had no access to the MathEngine/Arrange repos (held closely by Efim). Val: "we are moving away from the secrecy … the math is very complex and we are opening it up." Sasha gets repo access and will write the math-side ADR in the new Rust MathEngine repo. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

**ADR governance.** ADRs live as files **inside the repository they describe**, owned by the Chief Architect, cross-referencing each other where they intersect the data contracts. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

**CMS ↔ NOVA protocol.** The communication protocol will be **AMQP-style messaging**, to be co-architected by Sasha and CMS-side architect [[wiki/people/dmitri-chudinov.md|Dima Chudinov]] — but the meeting cannot happen for ~1 month while the CMS team is overloaded. [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

## Governance model — use case → requirement → capability, with internal users

Because NOVA has no traditional operator/player persona, Val defined its "users" as the **internal JVL teams** that consume the platform. The chain: **use case** (why, and for whom) ← **requirement** (how it functions) ← **capability** (what must be built at platform level). [[wiki/people/anton-leshkevich.md|Anton]] (test framework / TS-360) is the first user — he splits his requirements into features and, when he needs a hook/API that does not exist, declares "I need capability X" to Sasha, who translates it into features (each a feature branch, merged to main when done). [[wiki/people/irina-shishko.md|Irina]] converts existing QA test cases into use cases → requirements → capabilities. **Kamin** ([[wiki/people/alexei-khamin.md|Alexei Khamin]], by QA context — spelling "Alexey Kamin" is a transcription variant, flagged for owner confirmation) is Anton's downstream customer. Val's rule: "Sasha doesn't write features unless someone asks for them" — without a demand declaration the architect has no client. And the hard gate: **no code is written until the requirements/capabilities/features model is in place.** [[raw/Meeting_Transcript_nova_platform_architecture_overview-Segment_2-May-12-2026.md]] [[raw/Meeting_Notes_nova_platform_architecture_overview-Segment_2-May-12-2026.md]]

## May 27 2026 — the cloud back-end tier: the ~15-service catalog and the "JVL Web Services" taxonomy

An architecture working session ([[wiki/meetings/2026-05-27-cloud-backend-platform-architecture.md]], 12:35pm ET, ~1h44m; [[wiki/people/val-levitan.md|Val]], [[wiki/people/dmitri-chudinov.md|Dzmitry Chudzinau]], [[wiki/people/andrey-bosik.md|Andrei Bosik]], [[wiki/people/pavel.md|Pavel]], [[wiki/people/sergey-tsymanov.md|Sergey Tsimanov]], [[wiki/people/irina-shishko.md|Irina Shishko]], [[wiki/people/igor-metelski.md|Igor Metelski]], [[wiki/people/alexander-biratka.md|Alexander Biratko]], [[wiki/people/anton-leshkevich.md|Anton Leshkevich]], [[wiki/people/evgeny-kharetski.md|Evgeny Kharetski]]) worked the **cloud/server tier** that pairs with the on-cabinet NOVA platform above — the dedicated cloud-architecture discussion the [[wiki/meetings/2026-05-13-nova-platform-briefing.md|May-13 briefing]] had flagged as coming "next week" (former CMS being decomposed under the NOVA umbrella). Dzmitry presented a proposed catalog of cloud services for the new land-based machine platform; the transactional half of this cloud thread is on [[wiki/topics/persona-driven-design-and-orchestration-platform.md]]. [[raw/Meeting_Notes_Cloud_Backend_Platform_Architecture-May-27-2026.md]]

- **The ~15-service catalog.** A **gateway** routing all incoming requests; **Keycloak**-based login; a **user-management** service (roles/permissions); an **operator-management** service pulling operator + jurisdiction data from an upstream source; **machine registration** (same pattern as the transactional side); a new **manifest registry** where each piece of machine software (game, math, theme, framework) publishes its own capabilities, so the server knows what the machine can do without anyone typing it in; an **RS-configuration** service that builds the recommended-settings file from the manifests; a **QR service** for offline machines; an **event collector** that captures data **per spin**, not just daily totals; a **progressive** service that runs across many locations; **financial reporting** (replacing today's "Palapku Bam" — transcribed, garbled — plus Tableau); **license management** (possibly Business-Central-driven); **jurisdiction rules**; and the on-machine client (**LGS**). [[raw/Meeting_Notes_Cloud_Backend_Platform_Architecture-May-27-2026.md]]
- **One user pool, separated by roles (Val, decided).** Land-based and transactional users are unified into a single pool, separated by Keycloak roles; if a product line is ever sold that is a one-time "divorce" — do not design for it now. [[raw/Meeting_Notes_Cloud_Backend_Platform_Architecture-May-27-2026.md]]
- **Registration source — neutral identity authority, not Business Central (Val, decided).** Dzmitry wanted Business Central as the source of truth for new operators; Val disagreed, wanting a **neutral identity authority with automated validation** (federal license lookups, Google/Microsoft SSO, SMS, etc.), with Keycloak likely holding the central data. Val will consult external advisors on automated customer-identity validation in North America. [[raw/Meeting_Notes_Cloud_Backend_Platform_Architecture-May-27-2026.md]]
- **Service-to-service protocol — pick per case (Val + team, decided).** REST for sync, browser-facing and internal calls; a message broker (RabbitMQ named in discussion) for async, encrypted, external ones; the front-end can only do REST. Kubernetes pings each container's health endpoint and restarts a dead container, with at least two copies of each service always running. [[raw/Meeting_Notes_Cloud_Backend_Platform_Architecture-May-27-2026.md]]
- **The taxonomy landed — "JVL Web Services" (Val, decided).** Everything sits under the umbrella name **JVL Web Services**, with two groups beneath it: **Gaming web services** (what Dzmitry presented, for new land-based machines) and **Transactional web services** (already in development). **Financial reporting is split between the two** — different data, independent deployment. About 90% of the patterns are shared; **transactional ships next week**, gaming-web-services planning is next. [[raw/Meeting_Notes_Cloud_Backend_Platform_Architecture-May-27-2026.md]]
- **Deferred problems.** (1) **Legacy migration** — Andrei asked whether old machines can be re-registered to retire legacy; Dzmitry: registration is easy but old software has no manifests and old data structures don't fit (a big lift; a possible mass case is Arc Pacific) — deferred, no commitment to retire the legacy CMS now. (2) **Server-side machine-registration barcode** — Dzmitry wants the server to generate the number, but metal plates are ordered before the machine exists, so the number must exist first; no solution today. (3) **Data retention** — Andrei flagged that financial vs event data need different keep-periods and possibly aggregation; not blocking, tabled for a future session. [[raw/Meeting_Notes_Cloud_Backend_Platform_Architecture-May-27-2026.md]]
- **Product owner for gaming web services is open (§15.8 clear).** [[wiki/people/andrei-klimovich.md|Andrei Klimovich]] (transcribed "Andrei Klemyel"; the transactional PM by context) is busy on transactional; [[wiki/people/igor-metelski.md|Igor Metelski]] has the knowledge but Val won't add to his load; Val proposed [[wiki/people/alexei-khamin.md|Alexey Khamin (Lesha)]], and [[wiki/people/evgeny-kharetski.md|Evgeny Kharetski]] declined to take on more. Val to decide. Undertakings: Dzmitry to build the gaming-web-services capabilities list and produce a diagram showing gaming and transactional services side by side with the shared parts called out. [[raw/Meeting_Notes_Cloud_Backend_Platform_Architecture-May-27-2026.md]]

## June 30 2026 — migrating to NOVA/Galaxy without freezing releases: two feasibility spikes, RAID kept for South Dakota

On the [[wiki/meetings/2026-06-30-nova-migration-and-autonomous-coding.md|Jun-30 12:33pm ET Nova-migration/autonomous-coding session]] ([[wiki/people/val-levitan.md|Val]], [[wiki/people/pavel.md|Pavel Frolov]], [[wiki/people/dmitri-chudinov.md|Dzmitry Chudzinau]], [[wiki/people/alexander-biratka.md|Alexander Biratko]], [[wiki/people/evgeny-kharetski.md|Evgeny Kharetski]], [[wiki/people/dmitri-kovalchuk.md|Dmitri Kovalchuk]], [[wiki/people/andrey-bosik.md|Andrei Bosik]], [[wiki/people/irina-shishko.md|Irina Shishko]]) the team decided **how** to migrate to NOVA/Galaxy given autonomous coding is now working. The autonomous-coding workflow is on [[wiki/topics/ai-assisted-development.md]] (Jun-30) and the standards rollout on [[wiki/topics/github-release-management-pipeline.md]] (Jun-30); this is the platform-migration decision. [[raw/Meeting_Notes_Nova_Migration_And_Autonomous_Coding-June-30-2026.md]]

- **No release freeze for a full migration.** Dzmitry estimated a full backend move (AWS, transactional system, machine registration, RAS, manifests) could run to **end of year** — Val read that as 4–6, maybe 8 months. Since transaction payouts on the **RK 35/68** machines must keep running, JVL **cannot freeze releases** for that long, so a full "vacuum" rebuild is **rejected** (team consensus, endorsed by Val). Releases continue while the migration proceeds piecewise. [[raw/Meeting_Notes_Nova_Migration_And_Autonomous_Coding-June-30-2026.md]]
- **Platform taxonomy (Val clarified post-meeting).** **NOVA** = the new on-cabinet **gaming** platform. **Galaxy** = the new **online** platform, incorporating the **Observatory** and **Orchestration** modules (each itself many services). The **CMS / Back Office migration target is Galaxy, not NOVA.** [[raw/Meeting_Notes_Nova_Migration_And_Autonomous_Coding-June-30-2026.md]]
- **RAID Studio kept for South Dakota; Georgia releases target NOVA.** Moving the **RAID game framework (C++)** to Git is hard — huge repo volumes (a NOVA game ~**500 GB**; RAID ~**5–40 GB**) with heavily duplicated assets (libraries, sounds, video). Direction: **keep RAID Studio for South Dakota** (the only market tightly tied to Class III regulation) and **move Georgia game releases to NOVA**; growth markets (Georgia, Nebraska, Texas) aren't regulator-bound, so they're easier to jump. Alexander argued to settle feasibility **empirically** — just try migrating one game and building it. [[raw/Meeting_Notes_Nova_Migration_And_Autonomous_Coding-June-30-2026.md]]
- **Two feasibility spikes (Jul 20 → end of July, ~10 days each), then assess.** #1 [[wiki/people/alexander-biratka.md|Alexander Biratko]] migrates a **RAGE-Studio-based game to NOVA** (assess volume/duplication feasibility); #2 [[wiki/people/dmitri-chudinov.md|Dzmitry Chudzinau]] migrates the current **CMS (Back Office) to Galaxy**. The team meets end of July to assess both. [[raw/Meeting_Notes_Nova_Migration_And_Autonomous_Coding-June-30-2026.md]]
- **Operator reports / modems — watch for CMS creep.** Pavel wants modems in the **2000-series** machines for Georgia: collect play statistics, give operators reports (popular games, revenue), possibly sell report subscriptions and do remote installs without USB sticks. Dzmitry warned this risks **rebuilding the old heavy CMS inside the new platform**. §15.8 clear — platform-migration engineering and market strategy only; no named-person compensation. ## Aug 10 2026 — architecture kickoff: rewrite the monolithic HAL as per-device Rust services (session 1 of the Aug 10–14 series)

The first of the [[#aug-5-2026--re-architecture-reaffirmed-independent-services-with-transparent-restart--health-check-per-repo-adrprose-aug-1014-meeting-series|Aug 5-planned]] Aug 10–14 sessions ([[wiki/meetings/2026-08-10-nova-architecture-kickoff.md|kickoff]], 5:15–7:16 AM ET, ~2h, in Russian; [[wiki/people/val-levitan.md|Val]], [[wiki/people/pavel.md|Pavel Frolov]], [[wiki/people/alexander-biratka.md|Alexander Biratko]], [[wiki/people/irina-shishko.md|Irina Shishko]], [[wiki/people/evgeny-kharetski.md|Evgeny Kharetski]], [[wiki/people/anton-seregin.md|Anton Seregin]], [[wiki/people/alexei-khamin.md|Alexey Khamin]]) worked the on-cabinet HAL rewrite in operational detail. [[raw/Meeting_Notes_NOVA_Architecture_Kickoff-August-10-2026.md]]

- **The problem restated.** Today one large **C HAL** bridges every hardware board (counter, IO, LED, printer, bill validator, sound, …) up to the Java **LGS** through JNI wrappers; because it is monolithic, any single module fault crashes the whole machine, and the C code has caused many threading/memory bugs. [[raw/Meeting_Notes_NOVA_Architecture_Kickoff-August-10-2026.md]]
- **The proposal (decided).** Break each hardware library into its **own separate service in Rust**, talking to LGS over a **Unix socket** (switchable to TCP/IP only in the dev build, or TCP limited to localhost — never exposed on the network in production, for security). A failed service can be monitored, restarted and recovered on its own without taking the machine down. [[raw/Meeting_Notes_NOVA_Architecture_Kickoff-August-10-2026.md]] [[raw/Meeting_Transcript_NOVA_Architecture_Kickoff-August-10-2026.md]]
- **Common base API.** Every service exposes the same base API — identify itself (**info**), report **state/health**, and **list the specific APIs (capabilities)** it supports for the exact version installed — on top of which each service adds its own device APIs (e.g. bill validator "enable money intake," printer "print ticket"). The value Pavel and Alexander defended: LGS **and Claude** can query a machine, walk its real services and capabilities, and produce a fast accurate report of what actually works — instead of trusting documentation. [[raw/Meeting_Notes_NOVA_Architecture_Kickoff-August-10-2026.md]] [[raw/Meeting_Transcript_NOVA_Architecture_Kickoff-August-10-2026.md]]
- **Management service (walked back from "mega service").** A small supervisor/management service lists the services, health-checks them, restarts them, and manages logging levels. Pavel first floated a "mega/super service"; the team reduced it to a **small, mostly informational** service, not a controller of everything. [[raw/Meeting_Notes_NOVA_Architecture_Kickoff-August-10-2026.md]]
- **Minimum service set + fixed at setup.** Printer, bill validator, IO board, counter board, LED board, sound; optional/next: QR scanner, LTE modem. The **digital amplifier / media player folds into the sound service** (it monitors the amplifiers and can restart them). The service set is **fixed at setup time from the RIS config**, not dynamically detected, so a missing/failed service shows up against the expected list. [[raw/Meeting_Notes_NOVA_Architecture_Kickoff-August-10-2026.md]]
- **IO board stays ONE service (decided; Val skeptical).** The longest debate: the IO-board library holds the passport chip, Dallas chip, storage/memory, door, battery/time, cooler and a passed-through bill validator. Alexander, Pavel and Evgeny concluded it must **stay as one service** because everything on it runs off a **single on-board processor sharing one firmware** and must be tested together — you cannot restart or test the Dallas chip or passport independently. Val was skeptical ("60% sure you're wrong") and pushed to split by device responsibility rather than by shared processor/USB port, but did not overrule. The **bill validator becomes its own separate service** (logically independent, it just mirrors a protocol); the **passport stays a dependent sub-module inside the IO-board service**, with its own logging. [[raw/Meeting_Notes_NOVA_Architecture_Kickoff-August-10-2026.md]] [[raw/Meeting_Transcript_NOVA_Architecture_Kickoff-August-10-2026.md]]
- **Rust goes in the ADR, not as a formal requirement (Val).** The requirement is "reliable, and convenient to develop and test with Claude Code"; Rust is a stack decision recorded in each service's **repo ADR** so Claude knows what it is working with. Each service gets its **own Git repository** with its own ADRs. [[raw/Meeting_Notes_NOVA_Architecture_Kickoff-August-10-2026.md]]
- **Val's throughline — "for whom, and where's the money?"** Val repeatedly pushed the team off "how" onto who the change is for and how it turns into money; the concrete benefits defended: auto-restart without kicking the player out; a common interface + AI access enabling automatic testing; per-service releases with their own checksums so only the changed service is retested on hardware; a **hardware emulator** that can test a single device (e.g. take money / count / return money) without launching the full LGS; and better diagnostics (isolate the failed service, auto-enable trace logs on reconnect, push small fixes remotely). The team's split of beneficiaries: ~80% LGS developers/framework, ~15% QA/testability, ~5% technicians. **Logging:** each service gets its own logging, a controllable level (whole-system and per-part), and multiple sinks (local file, remote, console), with collection via USB stick / Setup button / QR for offline machines. **Firmware updates:** add the ability to flash device firmware through the services, on-the-fly for machines with a modem, but a firmware-version change also changes the passport (a "register new passport" risk to think through). **Multi-platform:** services must build for both x86 and ARM. [[raw/Meeting_Notes_NOVA_Architecture_Kickoff-August-10-2026.md]]
