# OLAP / Power BI / Active Directory architecture (machine-data visualization)

Two linked working meetings (part 1 internal/Russian, part 2 broader with Aaron, held on consecutive days — [[wiki/meetings/2024-sql-olap-visualization-architecture-1.md]] and [[wiki/meetings/2024-sql-olap-visualization-architecture-2.md]]) where Val and the Minsk team mapped JVL's **machine-data / BI architecture** and how to modernize it. Dated ~2024 by content ("В 2010 году, 14 лет назад"; developers were still to "commit … в BitBucket" — i.e. before the Jan-2025 GitHub decision [[wiki/decisions/2025-01-15-adopt-github-over-bitbucket.md]]). [[raw/architecture_sql_olap_visualization_1_2025-03-29.md]] [[raw/architecture_sql_olap_visualization_2_2025-03-29.md]]

## The stack as it stood (~2024)

- **Flow:** JVL's machines feed a **SQL database server in a remote hosting facility** ("via direct connection or through QR code"); that data goes into **OLAP**, is converted **manually into Excel**, and presented in **Tableau**. Val: "This doesn't work for us anymore. It requires manual labor… it occupies **one and a half person permanently**." [[raw/architecture_sql_olap_visualization_2_2025-03-29.md]]
- **Physical layout:** the application database runs **MS SQL Server on a physical server in the data center**; a second, similarly-configured server beside it runs the MS SQL reporting service that JVL calls "**OLAP**" — internal-only, not reachable from outside. IT does backups; database changes are made by "программисты Сергея и Дима" (programmers — Sergey and a Dima; which Dima is not stated). [[raw/architecture_sql_olap_visualization_1_2025-03-29.md]]
- **Licensing:** the MS SQL license was bought once, long ago — "В 2010 году, 14 лет назад… больше 20 тысяч долларов"; a new license was quoted at ~**$35k** ("вот 35 тысяч"). Day to day JVL leans on a long-standing **MSDN-type development subscription** (~$1,500–1,800 Cdn/yr, "в районе 1000 долларов американский") — a "**grace license**"/"серая лицензия" that formally covers development/testing use only, which Microsoft tolerates. [[raw/architecture_sql_olap_visualization_1_2025-03-29.md]]
- An existing portal, **backtogaming.com**, already has external (non-employee) users provisioned. [[raw/architecture_sql_olap_visualization_1_2025-03-29.md]]

## Tableau → Power BI

- JVL has **no Tableau expertise**, and learning either tool costs the same time; being "a Microsoft house more or less," the lean is to **Power BI** ("in terms of cost it's about the same"), which pulls the stack toward **Azure**. Power BI mirrors Tableau's two-tier model: author in a desktop app, publish to a **report server** (local, or the Azure cloud service) through which users get access. [[raw/architecture_sql_olap_visualization_2_2025-03-29.md]] [[raw/architecture_sql_olap_visualization_1_2025-03-29.md]]
- External/partner access would use **Azure AD B2B**-style external-user features, with the admin restricting visibility per user; a subtlety flagged: users added to AD **groups** may inherit access via group policies, so third-party users should be added individually, not into groups. [[raw/architecture_sql_olap_visualization_1_2025-03-29.md]]

## Active Directory (the part Val probed hardest)

- **Local AD:** two domain-controller servers in **each of three locations — the data center, the Toronto office, and the Minsk office** (per-site so logins don't wait on remote policy checks; two per site for failover). All replicate among themselves; used to authorize computers/internal services and apply policies ("чтобы убедиться, что Сергей Цимонов — это Сергей Цимонов"). [[raw/architecture_sql_olap_visualization_1_2025-03-29.md]]
- **Azure/cloud AD** (recently renamed by Microsoft — "Майкрософт -энкро -ид", i.e. Entra ID) is a **completely separate, unsynchronized** service that arrived "как побочное" when JVL moved mail to Microsoft; it authorizes mail/Teams/Office. Adding or removing a person means touching **both** systems (any one local DC + Azure). Andrey (Bosik): the local and cloud user sets "плюс -минус повторяют друг друга." [[raw/architecture_sql_olap_visualization_1_2025-03-29.md]]
- **Val's challenge:** why run two directory services — "это стандартная архитектура или мы пытаемся раскраить платье и выжить костюм?" Answer: consolidating onto Azure alone means standing up a **new domain**, re-joining every computer/server, and migrating user profiles — "работа… не простая и она очень окромная"; the drift to cloud is gradual. Val's stated target architecture: every developer works in a **local sandbox** and commits to the cloud repo (**BitBucket**, at the time), which he argued needs one centralized directory. [[raw/architecture_sql_olap_visualization_1_2025-03-29.md]]
- Moving the application database itself to cloud would require rework of the applications that use it, and Microsoft's DB-hosting cost "невозможно посчитать заранее" (depends on size, query volume, indexes); the cloud's real win named was **fault tolerance** (today one burned motherboard = rebuild from scratch). [[raw/architecture_sql_olap_visualization_1_2025-03-29.md]]

## The 2026 driver, and the SAS-host / cloud "casino-as-a-service" sketch (part 2)

- **Why this matters:** the FlexPay kiosk + **FlexPort** roll-out is tied to **June 2026** Georgia legislation ("all winnings must be converted into a prepaid card") — Val explicitly corrected his own earlier "2025" deadline to **June 2026** on this call. Separately he said **Incom validation** would be "converted into validation and **digital wallet**, as of June 2025," while Incom itself told JVL the wallet transition would be slow — "it will take time, **over 10 years** they say" — so card dispensers (or no-value cards hung on the wall and validated manually) remain necessary. [[raw/architecture_sql_olap_visualization_2_2025-03-29.md]]
- **Pavel's SAS options:** all machines (JVL and third-party) speak **SAS** (RS-232 at hardware level, a limited command set; in the field usually wired through 4/8-port serial→Ethernet converters or per-machine **Windows micro-PC player-tracking units** with touch screens and player cards). Option A: connect JVL's kiosk to a **third-party SAS host / back office**. Option B (Pavel's preferred): **JVL implements its own SAS host**, run as separate hardware or **inside the FlexPay kiosk** — "saves money for operator… cheaper solution… with minimal hardware overhead." "**FlexPay with integrated SAS**" would keep speaking the existing **WSS** (WebSocket Secure) protocol upward. **Known blocker even then: SAS needs 9-bit serial operation** ("we need to use 9 bits operation… quite different" — the parity bit used abnormally), which ordinary converters don't do; converters were to be bought and tested. [[raw/architecture_sql_olap_visualization_2_2025-03-29.md]]
- **Aaron's alternative:** minimize custom hardware — commodity serial→Ethernet boxes on the floor, and on the server side a **container host** running **virtual serial-adapter drivers** (a "serial frame mux") that route SAS traffic to a SAS server, a local accounting host, or the cloud; capabilities licensed / turned on per service ("turn everything into **casino as a service**"), following the containerized pattern of modern multi-function devices (he cited Cisco) and cloud-tethered POS terminals (**Clover, Stripe, Square**). Team caveat: **SAS-to-cloud conversion won't work directly on Azure because of a time limitation** — a local buffer / stripped-down "SAS helper" is needed. [[raw/architecture_sql_olap_visualization_2_2025-03-29.md]]
- **Val's close:** JVL is "sandwiched between two established methodologies" — the retail-driven **Incom-settled products** world and the machine-manufacturers' **SAS and Tito** world; "the two eventually will merge into one service and whoever will find … the cheapest solution for a location and an operator will win." Homework for **Dima, Andrei, Sergei, Pavel**: research Incom products and SAS/TITO, and revise the schematic (today: kiosk + TITO + SAS; future: digital wallet + cloud) for a follow-up that Friday, which Val named "**architecture of SQL OLAP visualization**." [[raw/architecture_sql_olap_visualization_2_2025-03-29.md]]

> **Forward link:** the Option-B design — FlexPort as the in-machine SAS-speaking unit, a JVL SAS host, WSS up to FlexPay, and the 9-bit adapter problem — is essentially what JVL decided to build on **Mar 28 2025** as the FlexPort-as-SMIB + "Flex SAS server" MVP: [[wiki/decisions/2025-03-28-flexpay-support-tito-non-jvl-locations.md]].
