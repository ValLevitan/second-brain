# AI-assisted development adoption

JVL's push to get its engineers using AI coding tools. Aaron led a hands-on workshop on Jan 14 2025 with the Minsk team (Pavel, Andrei, Anton, Sasha); Val framed it as a company direction, tied to the build-pipeline debate the day before.

## The tools shown

- **Visual Studio Code** as the editor, with two AI tools: GitHub **Copilot** (built in) and **Cline** — an Anthropic-based agentic coding tool (spelled "Climb"/"Clang"/"Klein"/"C-line" in the transcript). [[raw/ai-assisted_development_with_vs_code_git_and_mcp_january_14_2025.md]]
- **OpenRouter** to abstract API access to many AI models (skims ~10% and gives access without per-model rate limits); Andrei distributed OpenRouter API keys. The model used was Anthropic Claude 3.5 Sonnet (~$3 per million tokens, supports images, computer use, prompt caching). [[raw/ai-assisted_development_with_vs_code_git_and_mcp_january_14_2025.md]]
- **Model Context Protocol (MCP)** servers: Aaron built a Bitbucket MCP server live from a TypeScript template so the AI could talk to Bitbucket directly (code reviews, pull requests). He noted MCP could also talk to the local gaming server (LGS). [[raw/ai-assisted_development_with_vs_code_git_and_mcp_january_14_2025.md]]

## Key lessons Aaron taught

- Two usage modes: **bootstrapping** (start something from nothing, get a prototype in hours) and **iterating** (gradually improve an existing codebase). [[raw/ai-assisted_development_with_vs_code_git_and_mcp_january_14_2025.md]]
- The **"maximizer" / paperclip** warning: AI tools over-optimize the task you give them — infinitely refactoring, writing giant monolithic modules, or breaking working code. The engineer's job is to steer it ("the AI is the horse"). [[raw/ai-assisted_development_with_vs_code_git_and_mcp_january_14_2025.md]]
- The **70% problem / paradox of knowledge**: senior developers use AI to accelerate what they already know; juniors use it to learn what to do. QA engineers are "juniors" here, and the tools can help them learn Git through repetition. [[raw/ai-assisted_development_with_vs_code_git_and_mcp_january_14_2025.md]]
- The **`.clinerules`** file gives the AI standing instructions for a project; keep guidelines minimal (an MVP approach) rather than over-detailed and brittle. [[raw/ai-assisted_development_with_vs_code_git_and_mcp_january_14_2025.md]]
- Bigger, more monolithic codebases are harder for the AI (and humans) to work with — a reason to keep modules small and documented. [[raw/ai-assisted_development_with_vs_code_git_and_mcp_january_14_2025.md]]

## Val's personal knowledge-base method (Jan 20)

Coaching Andrei, Val described the workflow he uses himself and wants his managers to adopt: record every meeting (any language — ChatGPT moves between Russian/English easily), turn it into a transcript, feed it to ChatGPT, have it summarize and propose a title and ~20 tags, pick the tags to use, tell it to update memory, and derive a taxonomy — then circulate the conversation. This lets someone with limited English/vocabulary produce a correct taxonomy through dialogue with the AI. Val frames refusing to adopt these tools as a 1990s "knowledge-tribune" mindset he will progressively replace. Aaron separately demoed using Claude prompt styles ("explanatory", "intellectual dissector") to draft and critique JIRA features — see the DTP-53 section of [[wiki/topics/build-pipeline-parameterization.md]]. ## MCP to automate engineering work — "replacing Pavel" (Feb 21)

- In a short Feb 21 call, Aaron extended the MCP idea to **automating an engineer's role**. The simplest MCP is point-to-point (the AI sees raw API endpoints and connects the dots), but you can build **flows/actions with business logic inside the MCP** — e.g. a single "deploy a new machine to an environment" or "reconfigure" tool that internally calls many endpoints and reports each step. Aaron noted CI/CD build automation in GitHub follows the same convention, so the same pattern applies to integrating assets, deploying SQL, scaling environments, or configuring Kubernetes. ## Self-hosted Open WebUI + the good-vs-bad MCP lesson (Mar 27)

- On Mar 27 [[wiki/people/aaron.md|Aaron]] screen-shared and walked Val through configuring a self-hosted **Open WebUI** instance running as a local server on Val's laptop (localhost:8080) — a multi-model LLM chat UI. He toured its settings: themes, a **system prompt**, **memory** (turned on), audio TTS/STT, per-user API-key connections, model list (turn off the dated duplicate models to declutter), document handling (PDF image extraction, embedding model, full-context mode), **web search** (enabled with **DuckDuckGo**, chosen because it needs no API key), a code-execution sandbox, image generation (OpenAI / ComfyUI / Stable Diffusion, Dall-E 3), and a database export. See [[wiki/meetings/2025-03-27-openwebui-aaron-setup.md]]. [[raw/OpenWebUI_aaron_march-27-2025.md]]
- **Multi-user / JVL deployment angle:** Aaron flagged that Open WebUI is built as a **multi-user** system and can connect to an **LDAP / Active Directory** identity server — so it could be hosted on **JVL's infrastructure** (not Val's laptop) and give every JVL user an account with API keys, **replacing individual ChatGPT accounts**. [[raw/OpenWebUI_aaron_march-27-2025.md]]
- **Both providers behind one UI:** the speech-to-text engine was switched from **Whisper (local, slow)** to OpenAI **Whisper-1** using Val's own API key (the same endpoints as Aaron's Whisper service). Aaron imported the community **Anthropic** function so Open WebUI can serve **both Claude and GPT models at once** — needing an Anthropic API key with console billing set up. [[raw/OpenWebUI_aaron_march-27-2025.md]]
- **OpenAI adopts MCP:** Aaron noted OpenAI had just announced it will incorporate **MCP** into all its products (adopting the Model Context Protocol as its tool-use standard) and had significantly improved its image generator; he demoed GPT-4o's precise image generation (a dimensionally-correct fence elevation from a prompt). Val remarked he now uses natural language for ~**60–80%** of his tasks. [[raw/OpenWebUI_aaron_march-27-2025.md]]
- **The good-vs-bad MCP lesson:** Aaron taught three levels of MCP-server design using JIRA as the example — (1) a **lazy** MCP that just exposes each raw API endpoint as its own tool (100 endpoints → 100 tools); (2) a **consolidated** tool (e.g. one "manage JIRA issue" tool with transition/comment/edit sub-operations); (3) a **stateful** server that remembers context and offers the AI a suggestion (e.g. "you last searched this JQL — save it as a filter?") so the AI just says "yes" instead of regenerating everything. A good MCP does the work internally in the developer's best order; a bad one forces the user to read the docs and think through every step. [[raw/OpenWebUI_aaron_march-27-2025.md]]

## Aaron's adoption thesis — farmers, combines, and the dark forest (Mar 31)

- **The farmer/combine analogy:** software engineers are "like highly paid specialized farmers" tending crops by hand for 20 years; AI tooling is Aaron arriving "with a fucking combine and a huge tractor... It'll take me 10 minutes. Usually it takes you a month." "The farmers that do want to learn how to drive it are the successful ones and the ones that do not, no longer farm." The combine won't pick the crops or read the market — that engineering judgment stays human; the tool is for "writing the code faster." [[raw/vector_meeting_db-march-31-2025.md]]
- **Timeline claim:** asked how far away the shift is, Aaron: "I'd say a year. Give it 12 months. It's happening right now." They just pick a couple good people that know how to use this, and they replace five, ten people with that." (Source claims, recorded as said.) [[raw/vector_meeting_db-march-31-2025.md]]
- **Dark forest theory:** companies succeeding with AI tools "are not telling anybody... they don't want to let their competitors actually let them understand what's going on" — so the revolution looks quieter than it is. [[raw/vector_meeting_db-march-31-2025.md]]

## May 8 2025 — internal MCP servers as production tooling (Aaron deep-dive)

A long May-8 segment (part of [[wiki/meetings/2025-05-08-capability-compass-mcp-aaron-session.md]]; the transcript internally duplicates — facts taken once) where [[wiki/people/aaron.md|Aaron]] pitched [[wiki/people/val-levitan.md|Val]] on JVL **writing and maintaining its own MCP servers**. Aaron's framing: writing MCP servers is "very analogous to writing continuous integration code or DevOps engineering code" and should be **maintained and managed as a set of production-system tools** for the team. He credited an aha moment tied to **"Dima Handoff"** ([[wiki/people/dmitriy-khandov.md|Dmitriy Khandov]], garble — consistent with the May-7 suggestion that Khandov, with Unity tooling experience, could build/clone JVL's MCP servers), while noting he wasn't saying Dima "should be developing MCP servers." [[raw/mcp_servers_for_jvl-may-8-2025.md]]

- **MCP is a specification, not a product.** Aaron stressed **"MCP is not a piece of software. It is a specification for communication like [SaaS/HTTP] would be"** — an agent = a **model** (Anthropic Claude 3.7, GPT-4o, Grok, etc.) + a **container/host** (Cline, Claude Desktop, Goose) + **tools**; the host talks to a tool over the MCP protocol like a browser talks to a web server over HTTP. MCP servers can be written in **any language** (TypeScript, Go, Rust, C#) as long as they speak the protocol (JSON-RPC). He wrote a LinkedIn article on it, deliberately titled a tongue-twister: **"context for the model context protocol."** [[raw/mcp_servers_for_jvl-may-8-2025.md]]
- **Three classes of access to an application** (Aaron's commercial prediction): the classic **human UI** (e.g. the Jira UI), the **application API** (deterministic programmatic control), and a **third interface for AI/robot agents** — all three maintained by the software maker to "retain control of the narrative of their own product." He foresees vendors eventually **charging a separate licence/fee for MCP-agent access** to their tools (his examples: Atlassian, Salesforce). The build-vs-buy balance for JVL: writing/managing your own MCP servers over the existing API costs no subscription fees but is work you carry yourself. [[raw/mcp_servers_for_jvl-may-8-2025.md]]
- **System-interface adapters (the high-value idea for JVL):** bridge MCP to existing OS interfaces — **D-Bus on Linux, COM objects on Windows, AppleScript on macOS** — "unlocking thousands of existing applications without modification." Aaron demonstrated **D-Bus** live on Val's screen (`busctl`, `busctl tree`), showing every system unit (Docker, Bluetooth/BlueZ, policy-kit, printer/CUPS, login, audio) as controllable endpoints. Because "a lot of the JVL systems that run on Linux — the game host and the tools — talk on D-Bus," an MCP server aware of **JVL-specific D-Bus endpoints** could interrogate/test/manipulate running JVL software (e.g. **RGS/Focus** modules that talk to each other); this is the **Test-360 vision** revisited (see [[wiki/projects/jvl-2025-plan-and-jira-roadmap.md]]). Dumping the *whole* D-Bus tree to an agent "would blow out the context immediately," so coverage must be scoped. [[raw/mcp_servers_for_jvl-may-8-2025.md]]
- **In-stack MCP via a code class (the Omni example).** Alternatively, embed an **MCP-server class inside the software itself** — e.g. a Java class packaged into the **Omni framework** that, at runtime, has global access to the other modules' classes/variables and exposes tools like **"list classes" / "enumerate class"** and invoke-method (play a sound, run an animation, switch state) back to the agent. Aaron said **[[wiki/people/alexander-biratka.md|Alex Baratka]]** (Omni platform) would need to write "a special adapter that… responds in JSON-RPC" over how he already inspects objects/properties (breakpoints/debugger) — effectively an AI-drivable debugger written before/with the code. If all components share a language, one MCP class copies across them; if they differ (Java vs C# vs TypeScript) each needs its own, or a shared D-Bus-level one. The **class properties already exist** for free ("just the nature of writing software… there's nothing extra you have to do"). [[raw/mcp_servers_for_jvl-may-8-2025.md]]
- **AI-augmented QA / Gherkin test-driving.** The payoff Aaron sold: QA engineers who aren't deeply technical could hand an agent a **Gherkin** test spec ("make all the sounds play") and have it discover classes, enumerate methods, and **invoke** them — catching methods that pass unit tests but do nothing / error / return the wrong data at runtime — reducing manual test activity and making the JVL stack a "first-class" AI-drivable system rather than "some bullshit interface with screen capture." His proof anecdote: he couldn't install a **Canon inkjet printer** driver on Linux for two hours; he had **Cline** use his D-Bus-style MCP tool to inspect the CUPS printer service and it "just fixed it… in about two minutes." He also flagged that many companies with pre-MCP specialized test frameworks now have "their entire business model… at risk." Val said he now uses natural language for a large share of his work. [[raw/mcp_servers_for_jvl-may-8-2025.md]]

## May 26 2025 — Aaron's LaTeX/printer document tool + an Ollama primer

An [[wiki/people/aaron.md|Aaron]] ↔ [[wiki/people/val-levitan.md|Val]] session in **two recorded segments** ([[wiki/meetings/2025-05-26-ai-aaron-latex-printer-ollama.md]]; §12 — one session, two segments). **Segment 1 — the printer/document tool via LaTeX.** Aaron demoed a tool he built (specifically "for Claude to do this") that lets an AI **print research output directly to his physical printer**, or save a **well-formed PDF or markdown into a local documents folder without extra steps**; it can also read the files in a folder and print them. The value: it gives any coding tool (e.g. Cline) the ability to **create and synthesise a printable document meant to be consumed directly**, rather than dumping code. [[raw/executive_summary_LaTeX_aaron-may-26-2025.md]]

- **LaTeX as the intermediary format.** The pipeline generates content through a **LaTeX** stage before rendering to PDF or the printer — it can produce dynamic **mathematical graphs in scientific notation**, formulas, plain PDFs, and images, and render **Mermaid** diagrams automatically (solving the "markdown/mermaid renders badly" problem). Example output: an "instant research paper" on flight (lift/gravitational functions, force relationships) and an elegant blue birthday card with stars/hearts. [[raw/executive_summary_LaTeX_aaron-may-26-2025.md]]
- **What LaTeX is (Aaron, in layman's terms).** "A language that can be understood by humans to write well-formatted articles… like Markdown before Markdown"; spelled **L-A-T-E-X**, pronounced "LaTeX," around since the **early 1980s** (active since **1984**), used for **formal/academic/research/engineering/medical** writing. Its benefit over Markdown/HTML: LaTeX is more strongly defined, gives more control, lets you insert graphics directly, and has **many clean converters to Word and other formats** — versus HTML (not editable in Word) and PDF (rendering "baked in," not reusable). Markdown is "more for programmers"; LaTeX captures scientific/medical/engineering content better. Val is not meant to consciously prompt "in LaTeX" — it's an internal stage of the tool. [[raw/executive_summary_LaTeX_aaron-may-26-2025.md]]

**Segment 2 — an Ollama / local-inference primer.** Aaron explained **Ollama**: a platform for running language-model **inference locally**. Lineage: Meta "accidentally" released **Llama** (weights + code) in 2024; people wrote **llama.cpp** (a compiled C package) to run the model locally on a big-enough computer; that was repackaged as **Ollama**, a software suite that runs any model in the Ollama format; **Hugging Face** began promoting Llama-format models and an ecosystem grew. Ollama runs as a **Docker image**, locally or scaled into a commercial service. [[raw/executive_summary_ollama_aaron-may-26-2025.md]]

- **Inference defined:** the process of **predicting the next token of text** — Ollama loads the trained model into memory and calculates the most likely next sequence. **No internet connection needed.** [[raw/executive_summary_ollama_aaron-may-26-2025.md]]
- **Size vs capability:** "**Llama Core is 245 gigabytes**" → needs 245 GB of GPU RAM/VRAM (far beyond any desktop); "**Code Llama, 3.8 gigabytes**" fits and runs on a normal computer. "**The smaller the Llama, the stupider it is**" (Aaron: an unfair but simple way to think). [[raw/executive_summary_ollama_aaron-may-26-2025.md]]
- **Practical use for Val — cheap local semantic work.** For **semantic extraction/summarisation** it's valuable to run locally because cloud calls are expensive: using "**Anthropic Cloud 4.0**" to summarise a document "would cost me a dollar every time I made a call," whereas "**with Llama locally, it costs me nothing**." Small models handle simple jobs well — e.g. "read these two simple statements and make your best guess as to whether it's true or false." Pick the right size tool: "you don't need a huge bulldozer where you could use a rotor." [[raw/executive_summary_ollama_aaron-may-26-2025.md]]

## Feb 3 2026 — Claude Code integration workshop (the "AI sandwich" + live LGS run)

A ~2h24m hands-on session ([[wiki/meetings/2026-02-03-claude-code-integration-continued.md]]) in JVL's Claude Code rollout — [[wiki/people/aaron.md|Aaron]] coaching the Minsk engineers ([[wiki/people/pavel.md|Pavel]], [[wiki/people/irina-shishko.md|Irina Shishko]], [[wiki/people/alexander-biratka.md|Sasha Biratka]], [[wiki/people/evgeny-kharetski.md|Evgeny Kharetski]], [[wiki/people/ihar-hrybko.md|Ihar Hrybko]], [[wiki/people/andrey-bosik.md|Andrei Bosik]], Val present) on *how to actually work with a coding agent*. It is the **"continued"** of a prior Claude Code onboarding session **not present in the vault** (where Aaron had prompted Evgeny to "write unit tests first"; distinct from the Jan-29 Clayton MCP session). Aaron generated his slides live in Claude Desktop while teaching, "using Cloud Desktop right now in a similar way that I'm telling you about doing it." [[raw/Claude Code integration - continued.md]]

- **The "AI sandwich" (the core model).** Every interaction with a coding agent is three steps: **define → execute-and-generate → review-and-decide** — the human sets constraints, context and **success criteria early** (define) and reviews/accepts at the end (review-and-decide); the AI "lives the best" in the middle (generate incremental changes). "Setting constraints, providing context and defining the success criteria early" is "the most difficult part of working with a coding agent." The mental model for the agent: "an extra person who's kind of unskilled sitting next to you" whom you must instruct in tight detail — but who iterates far faster. [[raw/Claude Code integration - continued.md]]
- **The velocity target (with direction, not for speed's sake).** A human does ~**2–3** pull-request iterations a day; with AI-to-human review you can do "**5–10, maybe even 12**" code reviews a day. Aaron set **~12 pull requests/day** as an aspirational target for some — but "using it because it's fast is not actually something that's going to be helpful"; the point is **goal-oriented outcomes with direction**, or "you'll have chaos." [[raw/Claude Code integration - continued.md]]
- **Tests + developer experience as engineered guardrails.** "Tests are absolutely vital… if you do not have software tests, integration tests, unit tests, specifications, performance tests… you're going to have generation that doesn't work." Build scripts, linters, type-checkers, doc strings, unit/integration tests are **"engineered developer experience"** — they *carry the context* so the framework, not the person, steers the agent. The progression: **heavy prompting** (no guardrails, all burden on the human, output feels unusable) → **bootstrap mode** ("make a test script… set up a make file… write a pipeline" — building the tools to build the tools; "you don't butcher the meat with dull knives — sharpen your knives first") → the **mature end** ("add a /users endpoint" just works because linters/doc-strings/type-checks/integration-tests already carry the context). [[raw/Claude Code integration - continued.md]]
- **Human context as guardrails — the whiteboard→Claude→git flow.** The agent never hears the hallway/tea/whiteboard discussions that are humanity's real context. Capture them: after a whiteboard session, **each participant runs the same photo through their own Claude session**, produces their interpretation, then **one responsible person combines all viewpoints into a single decision document committed to the git repo** — "co-locate the decisions with the code." Distribute the **interpretation, not the raw photo** (the agent "was not in that conversation" and reads a whiteboard "as if they'd never seen it before"); keep the photo only as a human memory aid. This "averages the intentions of everybody," does the bureaucratic product-owner work cheaply, and lets people **attend fewer meetings** (review the photo + the digested outputs in ~10 min instead of an hour). Aaron tied it to Val's own record-everything habit — "he's found the value in keeping the human part of the interaction… and using that to steer the systems." (This is the same conversation→decisions→git idea behind [[wiki/topics/transcript-knowledge-base-tooling.md]].) [[raw/Claude Code integration - continued.md]]
- **JIRA as the planning layer, GitHub as the decision layer.** Keep decisions in git — GitHub issues, **Architecture Decision Records**, READMEs, CONTRIBUTING, technical chat — because it is fewer steps from the code than JIRA; "think of JIRA not so much as the technical layer, but as the planning… administration layer." ## Feb 11 2026 — GitHub front-end Waze setup: the compiler-stack model + the "ways" system

A single ~2h11m morning working session in four recording segments ([[wiki/meetings/2026-02-11-github-front-end-waze-setup.md]]) aimed at the **front-end developers** [[wiki/people/anton-seregin.md|Anton Seregin]] and [[wiki/people/vladimir-samusenko.md|Vladimir Samusenko]], with [[wiki/people/pavel.md|Pavel Frolov]] translating (he left partway to help another team) and Val present. A language model is "**a machine that compiles natural language into source code**" — it "takes the same shape as a compiler, but takes input that you speak naturally," builds an intermediate representation, optimises it, and emits structured output; "it's not deterministic, it's probabilistic, and there's no formal correctness guarantees." Because you can create "10 variations of the same thing" faster than doing it once by hand, and each iteration filters/refines the output, the net effect accelerates intentions. The short ~11m49s follow-up session ([[wiki/meetings/2026-02-11-github-ways-repository-structure.md]], 3:20 PM) [[wiki/people/val-levitan.md|Val]] set up so [[wiki/people/evgeny-kharetski.md|Kharetski]] could get his question answered directly, with [[wiki/people/aaron.md|Aaron]] and [[wiki/people/pavel.md|Pavel Frolov]]. It fills in the mechanics behind the "ways" system introduced earlier the same day.

- **The question (Pavel).** Where should the ways JVL's developers write be kept — in **one separate repository holding all the ways**, or in a **special `.claude` directory in each repository** with ways designed for and relating only to that repo? [[raw/GitHub_Ways-February-11-2026.md]]
- **Aaron's answer — `.claude` in the repo root.** "In the root of each repository, or technically in the root of every directory you want guidance in, you have a `.claude` directory… that's where **project-scope ways** can exist and are sensed and used." A **`.gitignore`** rule commits the ways into the repo while **ignoring developer-local files** (e.g. personal to-do lists), so "the ways make it into the repo" but local scratch work does not. [[raw/GitHub_Ways-February-11-2026.md]]
- **User scope vs project scope (Anthropic's model).** `.claude` in your **home directory** is **user scope**; `.claude` in a **project directory** is **project scope**. "A lot of the consistency of ways actually lives in user scope." Waze **reads and incorporates both** at session time. In Aaron's setup the Waze machinery lives as a **submodule of `hooks`** inside home `.claude` (not directly in `.claude` "because of the way Claude has to execute"), with scripts running under the hood via the hooks, and **sub-modules for each ways group** — software-dev, SSH, ADR, GitHub. [[raw/GitHub_Ways-February-11-2026.md]]
- **A way has two components: the text way + macros.** The first component is "just the way" — a text file / **prompt injection, just like a skill** in Claude Code. The second is **macros**: e.g. a `macro prepend` directive that "executes any macros for this way at the **beginning** rather than the end of the context." A macro can **detect whether the tooling exists in a project** and tell the way (Aaron's example: the ADR way) whether it is "ready to go" or say "tooling declined for this project — remove the no-cloud-tooling flag to enable." Aaron called it "a **programmatic, responsive, deterministic prompt** that creates things on the fly." [[raw/GitHub_Ways-February-11-2026.md]]
- **The GitHub way's config-scoring macro.** The GitHub way has both a general way (works the same for all GitHub projects) and a macro that **uses the GitHub command-line tool to count the number of users** in a repo and decide whether it is a **solo or collaborative project**, plus scores the repo's configuration (has a **license, description, topic, code of conduct**, etc.). For a poorly-configured multi-user repo it will "**harass** the coding agent a lot" to fix it. These are **user scope** — they apply to every project the developer touches, "whether you have rights to do it or not." Aaron's rationale: "as a professional software engineer, I hate working in GitHub repos that aren't well configured, so I'm forcing Claude to take on my way of doing things — and my way is the user way." [[raw/GitHub_Ways-February-11-2026.md]]
- **The JVL rollout plan (agreed).** Pavel's summary, confirmed by Aaron: take the **general part of all the ways as a separate repository JVL syncs with Aaron** (the user-scope Waze, which Aaron commits to "about every day"), and each project keeps **its own set of ways in the project layer**, living in the project but **injected into the session** at run time. Aaron stressed keeping the forked copy of the whole Waze repo up to date so JVL has "a **consistent expectation of what a developer should do at JVL** who are using the AI tools." For specialty needs a team can fork internally — e.g. **ways for non-developers** — and can **activate/deactivate whole sub-areas** (deactivate the software-engineering ways group, enable a legal or finance ways group). ## Feb 17 2026 — the Acceptance-Criteria migration written up as a JIRA feature/task brief (v1→v2)

A **written task brief** (not a meeting) that turns the Feb-16 Aaron method into a concrete, buildable JIRA feature — "Acceptance Criteria Field Migration — Task Brief & Jira Feature Draft," dated Feb 17 2026, based on the Feb-16 Aaron Bockelie consultation and prepared for Val. It exists as a versioned pair of documents (§12 derived-document family): an engineering-facing **task brief** [[raw/acceptance_criteria_migration_brief_v2.md]] and a **JIRA feature-and-stories draft** [[raw/acceptance_criteria_migration_JIRA_task_automation-February-17-2026.md]] to be posted under parent **IP-807** only after Val's explicit approval.

- **Why the field existed, why it is now a liability.** The brief records that ~five years ago acceptance criteria was deliberately put in its own custom field because the only way to pull structured data out of JIRA was the API, which works best when each datum has its own field, and there was no AI to parse a combined text field. With MCP/AI now able to read a single **Description** field and distinguish context from requirements from acceptance criteria, the separate field only adds cost: every MCP integration must be taught a non-standard field, team members must check two places, and every new tool needs custom setup. [[raw/acceptance_criteria_migration_brief_v2.md]] [[raw/acceptance_criteria_migration_JIRA_task_automation-February-17-2026.md]]
- **The method, made concrete (enumerate → download → transform → verify → delete).** Identify the field ID (`customfield_10XXX`); export a full **CSV + JSON backup** of every issue with the field populated (the safety net); run a migration script that **appends the acceptance-criteria content to the end of each issue's Description** behind a clear visual separator ("Acceptance Criteria (Migrated…)"), in **batches** to avoid API rate limits, DRY-RUN first then live, logging every success/failure; then remove the field from all screens/configurations and **permanently delete** it — only after verifying and only with Val's explicit confirmation. This is the same **enumerate → download → transform-in-batches → verify-via-local-checklist → delete** shape Aaron sketched on Feb-16. [[raw/acceptance_criteria_migration_brief_v2.md]] [[raw/acceptance_criteria_migration_JIRA_task_automation-February-17-2026.md]]
- **The two-track guiding principle.** "We accept mediocrity and incompleteness for the past. We focus on perfecting the future." **Track A — completed/terminal issues** (Done/Closed/Resolved): the append runs with **no human review**. **Track B — active/upcoming issues** (In Progress/To Do/Backlog): the same append runs automatically, then a filtered report goes to **team leads** who confirm the merged text reads correctly and fix anything off, marking each reviewed. The feature draft breaks this into five stories — (1) extract & back up, (2) migrate into Description for all issues, (3) generate the active-issues review report, (4) team-lead review, (5) retire and delete the field. On a short evening call ([[wiki/meetings/2026-03-13-capabilities-requirements-adr-storage.md]], 9:33pm; [[wiki/people/aaron.md|Aaron Bockelie]] ↔ [[wiki/people/val-levitan.md|Val]]) Aaron settled the storage/source-of-truth question that had been implicit in the Aaron-"Ways" **ADR** / **Capabilities** documents (`Aaron_Ways-ADR`, `Aaron_Ways-Capabilities`, `Aaron_Ways-Capabilities-from-Decisions`) and the [[wiki/topics/transcript-knowledge-base-tooling.md|knowledge-base pipeline]]'s "ADRs land in a dedicated GitHub repo" storage layer. [[raw/Capabilities_requirements_ADR-storage-March-13-2026.md]]

- **Jira is not a source of truth.** Val proposed keeping the unchangeable source of truth **in Jira** ("there you cannot change it"). Aaron rejected it: Jira is an **issue tracker** — one person can delete an issue, it lives in a cloud with **no way to cryptographically ensure integrity**, and "frankly I just don't trust it." A capability *can* be copied into Jira as an issue **to be tracked**, but that copy is a tracker entry, not the record of record. [[raw/Capabilities_requirements_ADR-storage-March-13-2026.md]]
- **The source of truth lives in a git repo; Jira holds a shadow copy.** Aaron's rule: write the capability / requirement document **in a git repo** (cryptographically tracked, and copyable locally), then "bubble it into Jira" as a **shadow copy** with a reciprocal link (e.g. the repo text records that PRD-123 maps to a Jira issue). If someone edits the Jira issue and it then differs from the repo, the **repo is right and Jira is wrong** — a blanket "only the git copy is the source of truth" rule removes the "who's right?" question entirely. Aaron corrected Val's "keep it in GitHub" to **"keep it in a git repo"** — training Val to think in the elemental tool (a git repo, which GitHub happens to host and which can also live locally). This is the integrity mechanism behind the [[wiki/topics/transcript-knowledge-base-tooling.md|Feb-12 pipeline's]] GitHub-repo storage layer. [[raw/Capabilities_requirements_ADR-storage-March-13-2026.md]]
- **Capabilities sit with a business-operations model, not a product.** Aaron framed capabilities as the company's **controlled-document "original copy under lock and key"** — not prevented from being *seen*, but prevented from being *changed* — kept in a "data lake / big book" that in small companies is just in someone's head or on a whiteboard/Confluence. Requirements are managed the same way. [[raw/Capabilities_requirements_ADR-storage-March-13-2026.md]]
- **Requirements stay in Jira *for now*; they graduate into the repos as JVL matures.** Aaron's target end-state: requirements should eventually **exfiltrate out of Jira into each product/project's git repo**, with Jira only the place you **debate, discuss and accept** them (a company-wide "bazaar" of reusable requirements you copy into a repo, then write the **ADR against them**). ADRs are **kept with the repo** — decoupled from the project, **never in Jira or Confluence** (Val confirmed he understood this from Aaron's earlier hammering). But JVL "lacks the maturity" for a dedicated requirements tool, or even for full requirements discipline in Jira — so requirements stay as **informal large text blobs in Jira** (which "functionally works well"). If [[wiki/people/juan-martinez.md|Juan]] is now curing/accepting the requirements data set, that is the first step toward that maturity. [[raw/Capabilities_requirements_ADR-storage-March-13-2026.md]]
- **The flow (Aaron's mental model).** **requirements → capabilities → architecture decisions (ADRs) → specification → code**, with **tests as the contracts** that verify the spec and requirements are met. "For now" JVL can already keep **both capabilities and ADRs in the git repo**. Simplified conclusion agreed on the call: **requirements in Jira for now, capabilities in the git repo (via GitHub).** [[raw/Capabilities_requirements_ADR-storage-March-13-2026.md]] **(Evolution — see Mar-16 below: Aaron reversed the "capabilities in the git repo" half three days later, moving capabilities into Jira for referential integrity while ADRs stay in the repo.)**

**Code-to-prose methodology (segment 2).** Aaron laid out a conceptual method for understanding and refactoring code — the reverse-requirements direction that continues his "intention developers" thesis.
- **Translate code into prose.** Describe each piece of code in plain words ("this function does this thing"), and you produce a **miniature specification**: if you deleted the code but kept the prose, you could rewrite the code from it. Collect the descriptions across a codebase and they roll up into a **hierarchy** (function → module → system). [[raw/Meeting_Transcript_Code_to_Prose_Methodology-April-3-2026.md]]
- **Val's reverse-ladder framing.** Val recognized the prose as the reverse of top-down build flow — **requirements, capabilities, ADRs, spec, architectural/schematic diagrams**, the "decision ladder taken from an executive order saying build me this thing." Aaron: "we're reverse engineering the code." (Ties to the [[wiki/topics/transcript-knowledge-base-tooling.md|requirements-vs-capabilities]] and ADR-storage threads.) [[raw/Meeting_Transcript_Code_to_Prose_Methodology-April-3-2026.md]]
- **Prose = intent in human language; the Jacquard-loom lineage.** Nobody speaks in "open curly brace for I equals 1 to 27… semicolon"; you say "let's go through these 27 items" — same intent, different language. Programming has always been (since Jacquard looms with punch cards) **feeding human intention into a pattern-following machine**; converting code back to prose brings it "back to the human element." Many engineers dismiss this ("the best description is the code itself") because they were trained in code, not humanities/philosophy — but the **semantic intent** is what actually describes the system, and you could just as well target assembly if you have the prose. [[raw/Meeting_Transcript_Code_to_Prose_Methodology-April-3-2026.md]]
- **The LLM as "Tower of Babel."** An LLM understands code-as-prose and prose-as-prose equally, so it can translate between programming languages, **math notation** (summations/sigmas/integrals — symbols with no English equivalent), and human language. Each target language has **less or more fidelity** for a given concept, and there's a cost: a 10-line function might need ~100 lines of descriptive prose. The engineer's job is deciding **which language describes the intent most clearly** and how much description to keep. [[raw/Meeting_Transcript_Code_to_Prose_Methodology-April-3-2026.md]]
- **The team-coordination payoff.** When two developers write code with different mental models, the pieces may not fit. **Decompose both into prose** — the common language — see where the intentions diverge *without parsing each other's code*, each rewrite their part, reconnect, and it works. "That's basically a specification… that's what a team of programmers is doing." - **Agent-performs-QA, not agent-writes-test-code.** Pavel's proposed direction is to move beyond using AI to *help write* test code and instead use AI as an agent that *does* the QA job: a QA or developer describes a test intent in **plain language** ("validate JIRA-X using test plan Y"), and the agent proposes a plan, **generates whatever skills or tools it needs**, runs the tests, and writes a report — keeping a **history of prior test sessions** so earlier solutions can be reused. [[raw/Meeting_Notes_E2E_Testing_CICD_Contract_Analysis-June-5-2026.md]]
