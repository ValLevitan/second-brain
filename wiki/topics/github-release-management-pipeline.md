# GitHub release management and the CI/CD release pipeline

How JVL turns committed code into a certifiable, shippable release inside GitHub — the repository lineage, the automated lint→test→build→release pipeline, the artifact/manifest model, and the human **release-manager** role ([[wiki/people/ivan.md|Ivan]]) that carries a build through to **GLI** certification. This is the "new ecosystem" replacing the legacy Jenkins/Dropbox flow for Omni games. Worked out across three late-October 2025 sessions (Val, [[wiki/people/aaron.md|Aaron]], [[wiki/people/andrey-bosik.md|Andrei Bosik]], [[wiki/people/pavel.md|Pavel Frolov]]). This topic is the **sequencer** for that thread; the individual meeting stubs stay thin.

It sits downstream of the repo-structure decisions ([[wiki/decisions/2025-02-21-separate-game-and-design-repos.md]], [[wiki/decisions/2025-03-12-fork-game-repos-from-generic-template.md]], [[wiki/decisions/2025-04-07-recarve-gaming-platform-into-six-product-repos.md]]) and the Jira↔GitHub mapping ([[wiki/decisions/2025-04-03-jira-capability-level-and-github-mapping.md]]); artifact storage overlaps [[wiki/topics/jfrog-artifactory-artifact-management.md]].

## The repository lineage: concept → design → production

- A single **game-concept repository** holds every game concept ever, and **lives forever** — JVL keeps adding to it. When a concept is promoted, JVL **sparsely forks just the one directory** for that game into a new **game-design repository** (the path is carried over so lineage is visible), and the design work is built out there. [[raw/releases_github-october-21-2025.md]]
- The **production repository** is created from a **master production template** (a generic template "with no colors in it"); the design work is attached to it as a **git submodule** — a reference/symbolic link back to the still-standing design repo, so nobody commits a separate copy and traceability runs production→design→concept. (Andrei noted JVL's practice is to create the production repo from a clean template rather than fork the design repo, since it doesn't need most of the design history — either way is fine; Aaron's priority is clean separation + traceability.) [[raw/releases_github-october-21-2025.md]]

## The automated pipeline (GitHub Actions)

- The production repo carries a `.github/actions` directory of actions that **watch for pushes**. On every commit the pipeline runs in order: **linting** (fails fast and stops everything else) → **tests** (run on every commit) → **build** (rebuilds on every source change) → and, if all pass, **deploy/release**. [[raw/releases_github-october-21-2025.md]]
- **Artifacts are separate from the action pipeline.** GitHub stores release artifacts (gzip/zip, ISO image, EXE, etc.). A release can bundle **multiple artifacts simultaneously**, all tagged with the **same version** — e.g. an EXE, an ISO, a zip, a **PDF instruction book compiled from the markdown docs**, and a link to an online-play build. [[raw/releases_github-october-21-2025.md]]
- **Every release is an immutable, uniquely-tagged version.** Each artifact ties to a commit hash / version tag that can never be reproduced-and-altered (re-running the action reproduces the identical checksum; any change changes the checksum). Aaron showed **OBS Studio** and **RustDesk** GitHub release pages as the model for what JVL's game releases should look like. [[raw/releases_github-october-21-2025.md]]
- **Continuous delivery via cascading integrator repos.** Each piece (a game, the Linux OS, the back-end/CMS) is individually runnable and has its own releases; an **integrator repository** watches for new release tags from the pieces and auto-assembles them into the bigger ISO. A new release tag on one game ripples up the assembly chain automatically — Aaron's "north/south assembly line" and factory-sub-assembly analogy. [[raw/releases_github-october-21-2025.md]]

## What a "release" is (worked examples)

- A **release is a collection of artifacts** answering an initiative. For a **Class-3 single game**, that is one game — **Calle Ocho** (the first Omni game; transcribed "Kaya Ocho"/"Kayocho"/"Calle Ocean"). For **Georgia**, the release is a **multi-game package**: a **multi-game selection screen** component plus several games (Val's example: six games), each with its own checksum, all under one version number. [[raw/releases_github-october-21-2025.md]]
- The final deliverable is an **installable ISO image** built from many constituent artifacts (game(s), OS, drivers, etc.) — not the same as a lightweight EXE that Michael/Juan double-click to preview a single game. [[raw/releases_github-october-21-2025.md]]

## The final-image installer and its manifest (Oct 22)

- The **`platform flex os installer`** project performs the final assembly of all components into the installable machine image. It holds a **manifest file** (still an early seed) declaring **which components make up the final product**. This is the installer layer of the "platform flex back end" system. [[raw/artifacts_assembly_GitHub-october-21-2025.md]]
- On each release, [[wiki/people/ivan.md|Ivan]] fills the manifest with the **specific version of each component** for that build. Components vary by package: a single game reuses the same components; a Georgia multi-game package lists a distinct component per game (likely including the multi-game screen). [[raw/artifacts_assembly_GitHub-october-21-2025.md]]
- The manifest can pin the **checksum of each binary artifact**; if the build can't find an artifact by checksum, it **errors** — so components placed on the agreed "shelf" assemble deterministically. [[raw/artifacts_assembly_GitHub-october-21-2025.md]]
- Val's view: a mature release-management **methodology/standard already exists** in industry (designers put artifacts on a shelf, the release manager takes from it) — JVL just needs to read and adapt it. [[raw/artifacts_assembly_GitHub-october-21-2025.md]]

## The two build actions and the release-candidate gate (Oct 22 practice run)

- JVL distinguishes **two build actions**: (1) build **binary files from text/source files** — done by the developer during assembly of game pieces (specialists like [[wiki/people/irina-makarych.md|Irina Makarych]] help); (2) assemble the **ISO game image from the binaries**. [[raw/practice_release_calle_ocho-github-october-21-2025.md]]
- **Marking a build field-ready is [[wiki/people/ivan.md|Ivan]]'s job.** Any developer can build sources and download the artifact, but Ivan marks the artifact — or runs a separate build action with the **full test list** — and only after all tests pass is the build tagged a **release candidate**. [[raw/practice_release_calle_ocho-github-october-21-2025.md]]
- A **practice release of Calle Ocho** was planned as a dry-run: assemble the game in its current state, driven by Ivan (not Pavel), with Pavel checking the repo organisation; a review meeting was set for the following Wednesday with Ivan invited. [[raw/practice_release_calle_ocho-github-october-21-2025.md]]

## The release-manager role (Ivan) and the GLI handoff

- [[wiki/people/ivan.md|Ivan]] watches for a release that passed lint/test/build, judges whether it is genuinely ready, hands the candidate to human game-play testing, then packages the exact tagged version and takes it to **GLI** for certification (a manual email/phone process). He is the **liaison** between JVL and GLI and manages the **cost of each submittal**. Aaron noted **Eclipse** is an organisation similar to GLI. Ivan's old habit of tracking release numbers in Jira plans is being dropped — he now references GitHub. [[raw/releases_github-october-21-2025.md]]

## Legacy vs new ecosystem

- JVL runs **two parallel ecosystems**: a **legacy** one (games built on **Jenkins**, previews shared via **Dropbox**) and the **new** one where Omni games are compiled *and* distributed in GitHub. Dropbox was "a gut measure" until GitHub is implemented; **Jenkins goes away** once all production moves to GitHub. Val's rule for these discussions: define the new ways only — the old ways will "live themselves out of relevance." [[raw/releases_github-october-21-2025.md]]

## Mar 4 2026 — the single-source-of-truth push: Jira↔GitHub, feature-branch discipline, sprints→kanban

On the [[wiki/meetings/2026-03-04-schedule-review.md|Mar-4 schedule review]] ([[wiki/people/val-levitan.md|Val]], [[wiki/people/pavel.md|Pavel Frolov]], [[wiki/people/irina-shishko.md|Irina Shishko]]) Val worked to close the gap between Jira and GitHub as JVL's system of record — continuing the [[wiki/meetings/2026-02-27-nebraska-release-schedule.md|Feb-27]] requirements→features-workflow discussion. [[raw/Schedule_review-March-4-2026.md]]

- **"Two sources of truth" is the problem to kill.** Pavel framed it plainly: JVL runs **two sources of truth** — **Jira** (requirements, features, stories) and **GitHub** (the code, branches, and the architecture/design decisions made while coding). They intersect but a change in one does **not** propagate to the other: an architecture decision (an "EDR") made in GitHub while building a feature is invisible in Jira, so the Jira feature can diverge from what the code actually does. Val's counter-principle: there is **only one source of truth — the product/code and "the one truth"**; everything written around it (requirements, feature descriptions) is "decoration on a Christmas tree… the truth is stubborn, heavy, unpleasant, and nobody likes it." The fix is to make the written layer faithfully track the code, not to pretend there are two independent truths. [[raw/Schedule_review-March-4-2026.md]]
- **Feature-branch discipline + a GitHub-branch field on every feature.** Val's target model (Pavel confirmed the expectation is right): each **product** is one long-lived trunk (e.g. **IP 902** = the **FlexPos** product, "one big trunk"); each **feature** taken into work (e.g. **FP 519** = "FlexPos software update") gets its **own feature branch**, with commits/stories under it, and is merged into main under the product when its acceptance-criteria/integration tests pass. The concrete ask: add a **GitHub-branch/repo link field** in the Jira feature's details that is populated **when the feature flips to In Progress**, so a reader can jump from a Jira feature straight to its GitHub branch. FP 519 exposed the anti-pattern — [[wiki/people/alexander-biratka.md|Sasha Biratka]] had built its little Python auto-updater (lives in the RK3568 root, watches for an update file, unpacks, swaps the link, reboots) as a **standalone repo committed to root, not under a feature branch**, so nothing linked it back to Jira. Val will run **Claude** against the board to flag features that are In Progress but have **no feature branch**. [[raw/Schedule_review-March-4-2026.md]]
- **Requirements-before-discussion ("hygiene").** Val's recurring complaint: developers read a requirement/spec **once** (if at all) and then, after a single verbal discussion, "form their own truth" and never look at the written feature/acceptance-criteria again — so the code drifts from the docs. Pavel largely agreed (real specs rarely exist at discussion time). Val wants a proactive **"culture of information hygiene"**: requirements and capabilities written **before** the project is discussed, developers reading acceptance criteria before moving a story to In Progress, and a recurring **~15-minute "global plan overview" meeting** (every few days) where the whole company plan is presented and transcribed so developers see the big picture — kept **separate** from the daily stand-up (which Val insisted not be changed). He also floated a dedicated hire focused on capabilities/requirements. The management-culture angle ties to [[wiki/topics/jvl-operating-principles.md]]. [[raw/Schedule_review-March-4-2026.md]]
- **Sprints vs kanban (unresolved, leaning kanban).** Pavel argued JVL's **sprints** never land cleanly — an urgent unplannable task always bumps planned work, so sprints "were never ideal"; **kanban** would absorb the churn more naturally. To switch, [[wiki/people/dmitri-kovalchuk.md|Dima Kovalchuk]] would reconfigure the Jira board from sprint to kanban and Pavel would learn to work it. Left as an action-item to action from the transcript, not decided on the call. [[raw/Schedule_review-March-4-2026.md]]
- **The custom-field "MP" server tool.** The server-side "MP" tool that reads Jira custom fields (now trimmed to **14 fields** after the Feb custom-field cleanup — see [[wiki/topics/ai-assisted-development.md]]) is being fixed by an engineer (transcribed "Иран"/"ера"; the Jira-tooling name cluster is queued, not force-matched) and should work correctly **during March**, after which it can be pointed at each task to flag where required data is missing. [[raw/Schedule_review-March-4-2026.md]]

## Mar 6 2026 — the GitHub dashboard problem, and building the reporting tools GitHub lacks

[[raw/GitHub_dashboard-March-6-2026.md]]

[[raw/GitHub_dashboard-March-6-2026.md]]

It invites/removes/audits/checks/lists users, cancels invites, manages Copilot, and does repo management (`enterprise pi list orgs`, `repo list --org …`). He built it on the **GitHub CLI (`gh`)** — the same tool the DevOps side ([[wiki/people/andrey-bosik.md|Andrei]]/"Andres") already uses. [[raw/GitHub_dashboard-March-6-2026.md]]

- **Ties to the "intelligence center" mandate.** Growing homegrown GitHub-reporting tooling — with [[wiki/people/andrey-bosik.md|Andrei]] named to take it over — is the concrete shape of the per-developer GitHub-productivity system Val told [[wiki/people/pavel.md|Pavel]] to own on [[wiki/meetings/2026-02-09-claude-code-onboarding-chudinov.md|Feb-9]]. ## Mar 9 2026 — the Jira↔GitHub enforcement loop: container design vs GitHub Action

Two same-day calls worked the concrete mechanism for enforcing the [[wiki/meetings/2026-03-04-schedule-review.md|Mar-4]] rule that every In-Progress Jira feature must have a linked GitHub branch (and no untracked branch should exist).

- **The design ([[wiki/people/andrey-bosik.md|Andrei Bosik]], 3:58pm — [[wiki/meetings/2026-03-09-it-github-jira-infrastructure.md]]).** Andrei laid out two automated checking "loops": **(1)** any Jira task in-progress must have a GitHub branch — run **nightly at 21:00 Toronto time**, emailing the task's assignee; **(2)** a Jira start-date/timeline check — if a story's start date has passed but it (or its parent) is not moved to In-Progress, notify the assignee — paired with a reverse check for a **GitHub branch that has no matching Jira issue** (Val's "ghost branches" carrying code with no issue linkage — a sign something is "logically broken"). Andrei's plan was to run the loops in a **Docker container on JVL's own Docker machines in the Toronto office data centre**, not on Amazon ("why pay for it?"). [[raw/IT_GitHub_JIRA_infrastructure-March-9-2026.md]]
- **The critique ([[wiki/people/aaron.md|Aaron Bockelie]], 7:14pm — [[wiki/meetings/2026-03-09-jira-github-enforcement-aaron.md]]).** Aaron called the container design "unusually prescriptive" and over-complicated: there is **no need for a Docker container or the cloud spend**, and a container holding rights to both the codebase and Jira is a **high security risk**. It should be a **GitHub Action** — the action's runtime is seconds, and GitHub holds the permissions/keys in escrow. His model: an Action per repo checks each opened branch — any branch other than a few reserved names (e.g. `main`, `published`) must carry a **Jira issue ID pattern** in its name; the Action looks that issue up in Jira, confirms the **reciprocal GitHub link back** to the repo, and if it fails can **block the commit / delete the illegal branch** — or, less aggressively, **block the merge to `main`** unless a valid, reciprocally-linked Jira issue exists. [[raw/Aaron_Val-March-09-2026.md]]
- **Per-repo, not one central system.** Aaron rejected building "one giant thing to solve it all" (his Tetris analogy — waiting for the one piece that never comes) — putting all repos in one basket to force consistency "massively complexifies" the whole environment. Do it **per repository**, even at hundreds of repos ("500 repositories… who cares?" — no processor burden). Val accepted this. [[raw/Aaron_Val-March-09-2026.md]]
- **Central quality control by trust-and-verify, not lockdown.** For company-wide consistency Aaron endorsed a **special repository whose tools query every other repo** for the presence of the enforcement Action and **flag noncompliant repos tied to real work** — but never *prevent* people from editing Actions (there are "100 legitimate reasons" to disable Actions temporarily; git history always shows who changed what, maliciously or accidentally). His closing point on why the maintain-everything-centrally model fails: "there's only one Andrei and there's thirty other people." [[raw/Aaron_Val-March-09-2026.md]]

## Mar 10 2026 — the transparency problem statement: visibility as the real goal

The [[wiki/meetings/2026-03-10-jira-github-transparency.md|Mar-10 ~50-min call]] ([[wiki/people/val-levitan.md|Val]] ↔ [[wiki/people/andrey-bosik.md|Andrei Bosik]]) plus Val's same-day written **"JIRA & GitHub Transparency — Problem Statement Draft"** reframe the whole Mar-9 enforcement thread: the mechanism (loops, Actions, branch rules) is means to an end, and the end is **visibility**. Val insisted on separating the two — "I describe the problem I want solved; how to solve it I leave to the specialists" — and pushed back on Bosik whenever Bosik answered with a mechanism (e.g. blocking a Story going In-Progress while its parent Feature is still To-Do). [[raw/Transparency_alignment_JIRA_GitHub-March-10-2026.md]]

- **The JIRA workflow validator (Bosik + "Dima").** Bosik reported he and "Dima" (IT/Jira-board context → [[wiki/people/dmitri-kovalchuk.md|Dmitri Kovalchuk]]; inference) had tested a **JIRA "workflow validator"** in the JIRA sandbox: if a user moves a Story to In-Progress while its parent Feature is still in To-Do, JIRA refuses and tells them to move the Feature first. Val agreed the rule is sound but called it "one small part" — and questioned its value in isolation ("congratulations, and what?"), since JVL has no scenario where a Story is In-Progress under a To-Do Feature anyway. This can be applied per-project (configured on the specific projects' workflow), not globally. [[raw/Transparency_alignment_JIRA_GitHub-March-10-2026.md]]
- **The GitHub-linkage validator Val actually wants.** Val proposed a second validator: when a **Feature** is moved to In-Progress (for **select, forward-looking projects only** — not legacy, which JVL should walk away from rather than retrofit), the developer must **open a GitHub branch/repository linked to that Feature**. Bosik clarified that JIRA's board "strips"/swimlanes Val kept pointing at are only **visual formatting** applied per-project workflow, which Val accepted. [[raw/Transparency_alignment_JIRA_GitHub-March-10-2026.md]]
- **Un-linked branches and repos get tracked, noticed, then deleted.** The core anti-pattern Val wants killed: a developer opens a GitHub repo/branch and commits code with **no JIRA linkage at all** (no task/issue number to tie it to). JVL cannot technically *prevent* an engineer creating such a branch, but it can **track the action, send the developer a note, and forcibly delete it if not corrected**; Bosik added JVL can also **block a pull request to `main`** if the branch has no corresponding JIRA issue. Val's principle: "if we didn't ask you to do something, don't do it — don't spend our money on work we didn't request." He stressed nobody is dishonest; it is a **work culture** grown over years, not malice. [[raw/Transparency_alignment_JIRA_GitHub-March-10-2026.md]]
- **The "Story complete ⇒ code in the feature branch" milestone.** Val's key check is at the Story-completion level: when a developer marks a Story complete, **new code must appear in the feature branch** — for Val this is the important "milestone" that aligns all levels of the company. He accepts developers commit at the Story level (a few hours of work each) and only the **Feature branch** is merged to `main`, not each Story commit — but he wants the commits to *exist and be visible* as work progresses. [[raw/Transparency_alignment_JIRA_GitHub-March-10-2026.md]] The written draft states the standard plainly: a developer committing code early — **even imperfect code — is the professional standard, not the exception.** [[raw/JIRA_GitHub_transparency-Draft-March-10-2026.md]]
- **The developer black box vs. the graphic-designer precedent.** Bosik's objection — developers only commit code once it is tested and working locally, so early "garbage" commits just inflate commit count and hurt "repository cleanliness." Val rejected this: developers doing all work privately means JVL **never knows how long a Story took, how many Stories run in parallel, or what goes in which repo**, and cannot ask why a Story has been "open 8 days" or took "20 commits." He contrasted this with the **graphic-design workflow**, where JVL now knows how many review iterations a task took and how long — which lets leadership ask *why* (bad task definition, unclear requirements, an unqualified person, or constantly-changing scope). Visibility exists to **expose the problem and enable the honest question**, not to punish. [[raw/Transparency_alignment_JIRA_GitHub-March-10-2026.md]]
- **The dashboard demo — no equivalent from GitHub.** Val screen-shared the **"Game production examples dashboard"** (JIRA, project **IP 89**), which he judged ~75% accurate, and pointed to **464 open tasks** and a velocity line implying barely ~1.5 tasks resolved per week. Bosik diagnosed a **bottleneck** ("either we generate too many tasks or people handle them poorly"). Val's pointed question: can Bosik provide the same analytics **from GitHub right now?** Bosik: no — he has personal scripts producing some analytics, but tied to his own engineering interests, not this. Val: exactly — that missing transparency is the whole point. With it, he could ask a qualified person (e.g. [[wiki/people/lena.md|Lena]]) an intelligent question: why 464 open — are they actually complete but never moved to Done status? [[raw/Transparency_alignment_JIRA_GitHub-March-10-2026.md]]
- **The report parameters to nail down.** Bosik's practical ask: agree the metric — **Stories with no commit over an interval** (per day, per week, or **two indicators** at both intervals). Val's framing of the deliverable: build a **framework that surfaces this data**, then start asking why — maybe Stories are written badly, maybe work JVL thinks takes hours actually takes weeks. [[raw/Transparency_alignment_JIRA_GitHub-March-10-2026.md]]

## Mar 16 2026 — tearing down the Jira "ISO" release project; git tags become the release record

A short segment of the [[wiki/meetings/2026-03-16-release-procedure-and-eng-documentation-flow.md|Mar-16 Aaron↔Val call]] (recording header 12:07pm, 7m35s) turned the "git is the source of truth" principle into a concrete teardown procedure. This is the practical follow-through on the Oct-2025 note that [[wiki/people/ivan.md|Ivan]]'s old habit of tracking release numbers in Jira "is being dropped — he now references GitHub." [[raw/Aaron_Val-release_procedure_GitHub-March-16-2026.md]]

- **The thing being killed.** JVL had built a Jira "patch" for releases — an **ISO-related project** where [[wiki/people/ivan.md|Ivan]] created an ISO issue and attached tasks to an IP. Val had earlier complained to Aaron that it didn't work; Aaron's answer at the time was that it wouldn't, "because it's not how it's done" — once you convert to GitHub, releases should be done in GitHub. The ISO project has since sat un-administered and is "polluting Jira." Val's two asks: a course of action for [[wiki/people/dmitri-kovalchuk.md|Dima]] to disable it, and how releases should instead be managed/supervised in GitHub. [[raw/Aaron_Val-release_procedure_GitHub-March-16-2026.md]]
- **Don't just delete — dump first.** Aaron's warning against the "natural instinct" to delete the ISO issue type outright: some of the information in it is helpful. First **export/dump all the ISO issue types and all their issue properties**, so JVL can see all the connected-issue relationships — that dump becomes a **data source** for cleaning up and populating GitHub directly. [[raw/Aaron_Val-release_procedure_GitHub-March-16-2026.md]]

[[raw/Aaron_Val-release_procedure_GitHub-March-16-2026.md]]
